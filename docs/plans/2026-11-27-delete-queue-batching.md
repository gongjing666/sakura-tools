# 删除队列「发车」调度方案（WP-Cron 批量参数）

状态：待评审 · 目标版本 1.29.x · 作用页面：对象存储 → 删除队列（`storage&t=deletes`）

## 1. 一句话

让云端删除像物流发车：任务先攒在候车区，**凑够一车就走**；凑不够就**等到最长等待时间再走**。

## 2. 现在是怎么跑的（事实）

- 删除任务写进 `wp_sio_s3_deletes`（`Delete_Jobs`），字段里有 `state`、`next_at`（何时可执行）、`attempts`、`lease_until`。
- `Delete_Worker` 挂两条定时：一条**每分钟**的周期事件 `sakura_imgopt_s3_delete_tick`，一条「有活时立即跑一次」的单次事件（`schedule()`）。
- 每次运行 `run()` 在自己的时间预算内循环取任务：`MAX_SECONDS = 20` 秒、每轮 `due(5)` 取 5 件（`Delete_Worker.php:104/120`）。
- 失败按 `attempts` 退避重试，8 次后标 `dead`（`Delete_Jobs::MAX_ATTEMPTS`）。
- 结论：**现在是「来了就跑」，没有攒批概念**；`next_at` 只服务重试退避。

## 3. 想加什么

在「队列明细」卡片上方加一张「发车设置」卡片，三个参数 + 一个开关。

### 发车判定（三个条件，满足任意一个就走）

1. **够数就走**：候车区里「可执行」的任务数 ≥ 每车件数。
2. **够重就走**：候车区累计体积 ≥ 每车最大体积（0 = 不限）。
2. **等够就走**：候车区里最早一件已经等了 ≥ 最长等待秒数（哪怕只有 1 件）。
3. **兜底**：候车区非空且系统兜底检查到期（防止定时器丢失）。

### 关键概念区分（这是整个设计的核心）

| 概念 | 字段 | 用途 |
|---|---|---|
| 候车时间 | `created_at` | 判断「等了多久」，攒批用这个 |
| 可执行时间 | `next_at` | 判断「现在能不能跑」，重试退避用它 |

**必须分开算**：否则一个退避中的重试任务会把「最早等待时间」拉得很长，导致整批永远不发车。

## 4. 参数表

| 参数 | 说明 | 默认 | 范围 |
|---|---|---|---|
| `enabled` | 是否启用攒批；关闭 = 现在行为（来了就跑） | 开 | 开/关 |
| `batch_size` | 每车最少件数，凑满立即发车 | 20 | 1–200 |
| `max_wait` | 最长等待秒数，到点即发车；0 = 立即发车（等于关攒批） | 300 | 0–86400 |
| `batch_time` | 每车最长执行秒数（防止 PHP 超时） | 20 | 10–60 |
| `batch_bytes` | 每车最大累计体积（MB），达到即走；0 = 不限 | 500 | 0–10240 |

**体积参数需要改表**：`wp_sio_s3_deletes` 目前没有体积字段，攒批算不出「一车多重」。两种做法：

- 方案 A（推荐）：给删除队列表加一列 `object_bytes`，入队时从同步索引的 `remote_size` 写入；取不到写 0。
- 方案 B：判定时 JOIN 同步索引求和，不改表，但依赖索引行存在，且多一次聚合查询。

取不到体积的任务按 0 计（不算重量），但**计入件数**；全是未知体积时退化为纯件数 + 最长等待触发，不会卡死。

## 5. 实现落点

1. **选项**：新增 `sakura_imgopt_s3_delete_batch`（`[{enabled,batch_size,max_wait,batch_time,batch_bytes}]`），走 `Uninstaller` 清理清单。
2. **判定**：`Delete_Worker::run()` 开头调 `Gate::should_dispatch()`：读「可执行件数」+「累计体积」+「最早 `created_at`」；不满足则 `return`，并按「距离下个触发点还差多少秒」安排单次事件（精度到秒，不再依赖 1 分钟周期）。
3. **体积落库**：`Delete_Jobs::enqueue()` 增加 `object_bytes` 入参；两个调用点（同步中心、`Storage::delete_remote_attachment`）从索引行/附件取体积传入；`Delete_Jobs::VERSION` +1 并通过 `install()`/`maybe_install()` 补列。
4. **定时器**：入队时不再无条件立即 `schedule()`，改为「确保有一个到期检查」。周期事件保留作为兜底（防丢事件）。
4. **状态展示**：payload 增加 `dispatch` 段：候车件数、发车阈值、最早等待秒数、下次检查时间；卡片直接读，不额外请求。
5. **保存**：REST `POST /storage/deletes/dispatch`，返回同上快照，页面内联更新。
6. **只读展示**：重试次数上限（8）、完成记录保留（7 天）只在卡片里展示，不给改。

## 6. 边界情况（必须按这几条验收）

1. **重试中的任务**不算候车件数，也不参与「最早等待」计算。
2. **攒批不影响同步中心那条路径**：带附件的删除是内核同步删的，只有「纯云端对象」进这个队列（现状如此）。
3. **WP-Cron 靠访问触发**：站点没流量时，`max_wait` 会「到点但没人触发」。卡片上要写明这一点；同时保留每分钟周期事件 + 单次事件双保险。
4. **暂停/停用 S3**：候车区保留不丢；恢复后继续。换桶时沿用现有 reconcile gate，直接拒绝执行。
5. **正在跑的车**：参数改动**不打断**当前批次，下一批生效。
6. **时钟**：库存 UTC（`gmdate`），页面显示本地时间；等待秒数用时间戳差，不受时区影响。
7. **并发**：同一个批次用 `lease_until` 防重入（现有机制），攒批不新增并发面。
8. **极端值**：`batch_size=1` + `max_wait=0` 等价于现在的即时模式；`max_wait` 很大时靠周期事件兜底，不会永久挂起。

## 7. 卡片长什么样

标题：**发车设置**；副标题一句话解释规则。

- 开关：启用攒批（关闭后每件立即处理）
- 每车件数：`[20]` 件
- 最长等待：`[300]` 秒（0 = 立即）
- 单次运行上限：`[20]` 秒
- 每车最大体积：`[500]` MB（0 = 不限）
- 实时状态一行字：「候车 12 件（阈值 20）；最早一件已等 45 秒，再等 255 秒发车。」
- 底部右侧：保存按钮（卡片内的保存条，遵循插件按钮位置约定）
- 小字提示：删除任务由 WP-Cron 触发；站点无访问时可能延迟到下一次访问。

## 8. 验收清单

| 场景 | 期望 |
|---|---|
| 入队 5 件、每车 20、等待 60s | 60 秒内自动执行 |
| 入队 25 件、每车 20 | 第 20 件入队后立即执行 20 件，剩 5 件进入下一窗口 |
| 每车 1、等待 0 | 与现状行为一致 |
| 3 件共 800 MB、每车体积 500 MB | 第 3 件入队后立即发车（按体积触发） |
| 体积未知（`object_bytes=0`） | 不算重量、照常计件，靠件数或等待触发 |
| 有 1 件在退避重试中 | 不影响其他任务发车 |
| 改参数 | 当前批次不受影响，下一批生效 |
| 关闭开关 | 恢复即时模式 |

## 9. 已定稿（2026-11-27）

1. 默认值：**20 件 / 等待 300 秒 / 单次 20 秒**。
2. **要**「每车最大体积」参数，数值由使用者自己填（服务器性能不同），默认 500 MB、0 = 不限。
3. 关闭开关 = **立即处理**（等同现在的行为）；暂停另有入口。
4. 文案用**中性词**：批量调度 / 批次；「发车」只留在文档里帮助理解，不上界面。

## 10. 风险

- 攒批会让「点删除后马上看到云端对象消失」变成「最多等 max_wait」；需要在删除结果提示里写明「已进入候车区」。
- 参数调大（如每车 200 / 运行 60 秒）在小内存主机上可能撞 PHP `max_execution_time`；默认值保守。
- 依赖 WP-Cron 触发，站点几乎无访问时延迟不可避免——这是既有架构限制，不是本功能引入的。
