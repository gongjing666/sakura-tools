## 1. 结论摘要

**先看这十条，能省掉 80% 的翻文件时间。**

1. **双轨架构，且短期内不会合并。** `includes/` 是 1.3–1.9 的旧层（14 文件 / 6,192 行 / 14 类），`src/` 是 1.10 之后的新层（160 类，含 7 个接口）。两层的通信方式是**构造函数注入 + 类直接调用**，没有中间容器；唯一共享的抽象是 `src/Contracts/` 的 5 个接口。旧层没有被淘汰，反而承载了图片优化的核心链路（`includes/class-image-processor.php`）。
2. **全插件的装配只有一个入口。** `src/Plugin.php:70-206` 的 `boot()` + `build_modules()` 能看到**所有**依赖关系：先建 5 个仓储，再按固定顺序 new 出 20 多个模块/服务，最后 `Admin\Menu` 必须最后注册（`src/Plugin.php:195`）。读代码从这里开始，比按目录读快得多。
3. **模块契约极窄。** `src/Contracts/Module.php:23-31` 只有一个 `register_hooks(Hook_Loader): void`，且明确禁止在构造函数里挂 WP 钩子。所有钩子集中到 `src/Support/Hook_Loader.php`，先入队、`register()` 时一次性交付，**注册后新加的钩子立即生效**（`register_frontend` 依赖这个行为）。
4. **后台信息架构是静态声明的。** `src/Admin/Registry.php:41-101` 用一张常量数组声明「模块 → tab → 权限门 → renderer key」；`Menu` 只做建屏与分发，`Shell` 只画外壳。**加一个 tab = 改 Registry + 注册 renderer 两处**，不需要动菜单代码。
5. **功能面是 5 个子系统 + 3 条横切。** 子系统：图片优化管线（§4）、缩略图 URL 重写（§5）、对象存储 S3（§6）、同步索引 Sync（§7）、用户文件空间 UserFiles（§8）。横切：数据落点（§9）、钩子索引（§9.2）、REST/CLI/Cron（§9.3）。
6. **代码量集中在两处。** UserFiles（46 文件 / 22,305 行）与 S3（37 文件 / 11,924 行）合计占生产代码的 52.6%；两者也是自定义表、加密凭据与补偿队列最集中的部分。
7. **运行时可访问性已验证，生产写路径仍保持只读。** 11 条后台路由全部 200 且无 fatal（h1 是模块名，与 tab 子页名不完全相同）、45 条 `/sufm/v1` REST 路由（51 个端点）全部注册、7 个插件 cron 事件已排程、12 项函数级探针结果符合预期（§10）。**未验证**的是生产环境的写路径（配额扣减、删除审核、卸载清理）——生产保持只读。测试站上补做了六批：5 张并发上传（§10.6）跑通「上传 → 压缩 → S3 PUT → 索引落库」，4×200 条并发指标写入（§10.11）验证事件表零丢失，1.24.0 的对账失败退避与历史 grant 回填（§10.14）验证了退避序列、租约与字段白名单，1.24.1 的快捷多选（§10.15）在用户中心与编辑页分别通过 17/17、24/24 项浏览器断言，1.24.2 的运维观测（§10.16）验证 health、守卫分页/计数与 Prometheus gauge，以及 1.24.2 的三条空白补测（§10.17：Quota 提交/回滚、删除审核→Executor、卸载两轨、扫描游标三种损坏、编辑器覆盖与插入顺序）。**补测发现的一项缺陷已在 1.24.3 修复**：显式删除数据的卸载路径曾漏删 `file_tokens` 表；现在改为遍历 `Schema::tables()`，并在隔离环境复跑 15 张表→0，见 §12.7。
8. **两张"文档"已经过期，不要当作事实源。** `DEVELOPMENT.md` 第 1 节的"当前文件结构"停留在 1.3.3 的 6 个文件；`/root/WordPress/docs/sakura-image-optimizer-代码分析报告.md`（本机历史报告，未随仓库分发） 停在 1.9.0 之前的命名。本报告与 3D 图谱是当前唯一同步的产物；`DECISIONS.md` 仍然有效（记录的是"为什么"，不是"现在有什么"）。

### 2.2 模块总览

{{MODULES}}

**怎么读这张表**：行数不等于复杂度——`src/UserFiles` 20k 行里有 40% 是 REST 控制器与视图模板（重复度高、改动风险低）；`src/Sync` 只有 5.8k 行却包含状态机与 SQL 层，是改动风险最高的模块。

### 2.3 历史分层：includes 与 src 的边界

| 维度 | `includes/`（旧层） | `src/`（新层） |
|---|---|---|
| 时间 | 1.3–1.9（2023–2024） | 1.10+（2024–2025） |
| 命名 | `class-foo.php` + `Foo`，无命名空间 | PSR-4 + 命名空间 `Sakura\ImageOptimizer\…` |
| 装配 | 在各自构造函数里挂钩子 | 实现 `Contracts\Module`，只在 `register_hooks` 里挂 |
| 视图 | `includes/views/*.php` 直接 require | renderer key 注册 + Registry 分发 |
| 依赖注入 | `new` 具体类 | 构造函数注入接口（`Contracts\*`） |
| 现状 | 仍在承重：图片优化链路全部、缩略图装配、S3 设置页、媒体库批量 | 新增能力的默认位置 |

**边界的实际形状**（从依赖矩阵 §11.1 读出）：

- `includes` → `src`：138 条边（S3 40、Image 22、Contracts 17、Admin 14、Thumbnail 10、Support 9、Backup 7、Settings 6、Stats 5、Sync 4、Filesystem 3、Oss 1），说明旧层大量调用新层的服务；
- `src` → `includes`：仅 27 条边（src 10、Image 9、S3 8），集中在 `src/S3/Storage.php` 与 `src/Image/` 对 `Image_Processor`、`Backup`、`File_System`、`Stats` 的复用；
- 结论：**新层不依赖旧层的业务逻辑，只复用它的基础设施**（备份、统计、文件系统、处理器门面）。这条边界是安全的，重构时优先动 `includes` 的 `*_Module` 类。

> 注：上表两处"以矩阵为准"的数字在 §11.1 的矩阵里可直接核对；若矩阵与本段不一致，以矩阵为准（矩阵由脚本生成，本段为人工概述）。

## 3. 启动、装配与后台路由

### 3.1 入口文件

`sakura-tools.php` 只做四件事：定义常量（版本、路径、URL）、注册 PSR-4 自动加载、加载 `includes/` 旧类、调用 `Sakura\ImageOptimizer\Plugin::boot()`。**没有业务逻辑**，改动入口的风险极低。

### 3.2 `Plugin::boot()` 的七步（`src/Plugin.php:70-114`）

| 步骤 | 位置 | 做什么 | 为什么重要 |
|---:|---|---|---|
| 1 | `src/Plugin.php:71-74` | 防重入：`booted` 标志 | 防止 `plugins_loaded` 被多次触发时重复挂载 |
| 2 | `src/Plugin.php:76` | `Credential_Cipher::migrate_legacy_option()` | 把明文凭据迁移为 `sio1s:` 前缀密文 |
| 3 | `src/Plugin.php:77` | `Options::migrate_legacy_profile()` | 单配置 → 多配置档（profile）迁移 |
| 4 | `src/Plugin.php:81-86` | `Upgrade_Guard::maybe_upgrade()` → `Activation::run()` | 覆盖升级不会触发 activation hook，这里按版本号补跑建表、默认值与排程 |
| 5 | `src/Plugin.php:89` | `Sync\Schema::maybe_install()`（仅后台或 WP-CLI） | 6 张 `sio_sync_*` 表的版本化建表 |
| 6 | `src/Plugin.php:92-95` | `build_modules()` 后逐个 `register_hooks($hooks)` | **唯一的装配点**，顺序即依赖 |
| 7 | `src/Plugin.php:113` | `$hooks->register()` | 把排队的钩子一次性交给 WordPress |

另外三处旁挂（同函数内）：`admin_init` 补挂扫描/动作的排程（`:97-100`）、`WP_CLI` 时 require `class-s3-cli.php` 并注册 `wp sakura-sync` / `wp sakura-thumb`（`:102-108`）、每日备份清理 `sakura_imgopt_daily_backup_cleanup`（`:110-112`）。

### 3.3 `build_modules()` 的装配顺序（`src/Plugin.php:126-206`）

顺序不是随意的，注释与代码共同说明了两条硬约束：**仓储先于消费者**、**菜单最后注册**。

```
① 5 个仓储（无钩子）
   Backup_Repository · Stats_Repository · File_System_Repository · Settings_Repository
   Image_Processor(backup, null, null, stats, files, settings)        src/Plugin.php:124-129
② 后台基础
   System_Settings_Module · Image_Optimizer_Module                    :134-138
   renderer: system:settings · image:rules · image:backup · image:stats  :142-145
③ 缩略图与处理器
   Thumbnail_Manager · $processor · Media_Library_Module · Admin\Layout  :148-154
④ 缩略图子系统（is_admin 时注册 image:thumb 渲染器）                    :156-161
⑤ S3 旁支（12 个服务，按 配置→仓储→扫描→队列→监控→索引 顺序）
   Options → Storage_Adapter → Index_Repository → Scan_Service → Scan_Worker
   → Action_Worker → Alerting → Prometheus → Attachment_Indexer → Verify_Worker  :163-174
⑥ S3 后台（is_admin）：S3_Storage_Module · Sync_Center_Module · Delete_Queue_Panel
   renderer: storage:connection · storage:sync · storage:deletes          :176-188
⑦ Admin\Menu（必须最后）                                              :190-192
⑧ 后台/前台共用：Delete_Worker · Upload_Observer · Storage
   · \Nboke\UserFiles\Module                                       :195-200
```

> 依据：`src/Plugin.php:123-203` 的实际代码顺序；`:190` 上方注释写明"菜单最后注册，保证 WordPress 取屏时渲染器都已存在"。

### 3.4 Hook_Loader 的延迟注册语义（`src/Support/Hook_Loader.php:55-108`）

```
add_action/add_filter  → 入队（未注册前）
register()             → 置 registered=true，把队列一次性交给 WP
register() 之后调用     → 直接 add_action/add_filter 到 WP（不再入队）
```

这个"注册后立即生效"的行为被前台缩略图装配依赖（`register_frontend` 在 `after_setup_theme` 才执行，此时 loader 早已 register）。**改动 Hook_Loader 前必须确认这一点**，否则前台缩略图会静默失效。

### 3.5 后台路由：Registry → Route → Menu → UI → renderer

| 环节 | 位置 | 职责 |
|---|---|---|
| 声明 | `src/Admin/Registry.php:41-105` | 4 个顶级模块、13 个 tab、权限门、renderer key |
| 取页 id | `src/Admin/Route.php` | `page_id()` 把 module/tab 拼成 `image-rules` 这类稳定 id，供资源白名单与布局引擎使用 |
| 建屏 | `src/Admin/Menu.php:46-88` | `admin_menu` 建菜单与子菜单；旧 slug 在 `init`/`admin_page_access_denied` 上先跳转 |
| 分发 | `src/Admin/Menu.php:94-127` | `Route → 模块 caps → tab_gate → renderer`，缺 renderer 时渲染占位 |
| 外壳 | `src/Admin/Shell.php:33` | 页头、模块切换、tab 条 |
| 版式 | `src/Admin/Layout.php` | 每页的卡片分组与右侧工具坞（`DEFAULT_LAYOUT`，11 页） |
| 资源 | `src/Admin/Page_Assets.php:79` | 按 `LAYOUT_PAGES` 白名单加载 tokens/base/components/layout + 分页 CSS 与脚本 |
| 渲染 | 各模块 `register_renderer(key, callable)` | 真正的页面内容，正文一律由 `UI::page()` 开壳 |

**四个模块与 13 个 tab**（`src/Admin/Registry.php:41-105`）：

| 模块（slug） | 能力要求 | tab |
|---|---|---|
| 系统设置 `sakura-tools` | `manage_options` | settings（环境自检） |
| 图片优化 `sakura-tools-image` | `manage_options` | rules · thumb · backup · stats |
| 对象存储 `sakura-tools-storage` | `manage_options` | connection · sync · deletes |
| 文件空间 `sakura-tools-files` | `review` | settings · users(gate:execute) · queue(execute) · log(execute) · zibll(gate:zibll+manage) |

权限门有三种：`manage_options` 直接放行、`review`→`UserFiles\Capabilities::can_review()`、`execute`→`can_execute()`（`src/Admin/Registry.php:257-345`）。`legacy()` 把 6 个旧 slug（如 `sakura-tools-optimize`）重定向到新路由，**验证 §10.3 里出现的那 1 次 `page=sakura-tools-optimize` 就是这条跳转链**。
