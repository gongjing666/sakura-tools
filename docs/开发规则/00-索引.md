# 00 索引

插件文档的入口。**先看这一页，再决定读哪几篇。**

## 5 分钟上手

如果你要在这个仓库里改代码，按顺序读这三段就够开工：

1. **[01-架构与装配](01-架构与装配.md) 的 §2–§4**：插件怎么启动、模块怎么装配、`Hook_Loader` 的语义。
2. **[02-新增功能](02-新增功能.md) 的 §0–§1**：判断你的改动属于哪一类，落到哪个模块。
3. **本篇的「十条铁律」**：下面这些是踩过坑之后写下的，违反任何一条都会返工。

要改后台界面再加读 [03-后台UI](03-后台UI.md)；要动数据再加读 [04-数据与存储](04-数据与存储.md)；要动 S3 存储的启用、切换、锁定或删除，再加读 [07-S3存储生命周期](07-S3存储生命周期.md)；要把对象从旧桶搬到新桶，再加读 [08-OpenList迁移通道](08-OpenList迁移通道.md)。

## 十条铁律

抄自各篇最贵的那几条。**任何一条被违反都要在评审里说明理由。**

1. **新代码写 `src/`。** `includes/` 是 1.3–1.9 的兼容层，仍在承重；删任何一个类都会在运行时 fatal，而平时不报错。
2. **模块的构造函数只赋值，不挂钩子。** 钩子全走 `register_hooks( Hook_Loader $hooks )`，否则组合根无法决定装不装，测试也无法检查钩子面。
3. **`Admin\Menu` 永远最后装配。** 它要遍历已注册的 renderer；早装会拿到空表，菜单里点进去就是白页。
4. **一张卡一个表单一个 option group 切片。** `Card_Form::guard_options()` 不能省——`options.php` 会保存整个 group 的所有 option，没有守卫就是「保存一张卡，清空另一张卡」。
5. **新增 cron 必须同时写进 `Deactivation::run()`。** 否则停用后它还在跑。
6. **新增表/option 必须同时进 `Uninstaller` 的清理清单。** 否则卸载后留孤儿。
7. **版本号写在激活流程的最后。** 前面的建表/排程失败时，升级守卫下次请求还要重跑。
8. **颜色只用令牌，不加第二种粉、第二种红。** 全局强调色只有 `--g-accent`（`#9d3452`）。视觉修改只写 `assets/ui/`。
9. **业务代码不直接 `get_option()`。** 设置读写走 `Settings_Repository`；表名一律走各自的 `table()`。
10. **后台视觉改动必须在 1440 与 390 两个宽度看过，并走完「保存一次 → 开一次弹窗 → 关一次弹窗」。** 自动化测不到这些。

### 关于 history/

`docs/history/` 里是**归档**，只用于追溯「当时为什么这么做」：

- `DEVELOPMENT.md`：早期开发流水，**文件结构章节停在 1.3.3**，与现在的 `src/` 完全不同；
- `后台UI重构方案.md`：2026 年那次后台改版的分阶段方案，已完成；
- `sakura-tools-代码结构-1.25.9.md` 与 `sakura-tools-图谱同步-1.25.9.md`：1.25.9 时期的产物。
- `sakura-tools-代码结构-1.27.6.md`：1.27.6 时期的代码结构产物，1.28.0 换版时归档。
- `sakura-tools-代码结构-1.28.0.md`：1.28.0 时期的代码结构产物，1.28.3 换版时归档。

**这些文件里的路径、行号、类名一律不可信**，需要现状就看最新的代码结构文档或直接读代码。

## 文档怎么维护

- **规则只有一个出处。** 新增一条规则就写进对应那一篇；推翻旧规则时**删掉旧的**，不要两份并存。
- **改代码要顺手改文档。** 判据是：如果这次改动会让一个新人按文档操作失败，就必须改。
- 代码结构文档是**生成的**：`docs/tools/` 下的五步管线（scan → comments → build → graph → assemble）。改了类、钩子、文件结构後重新生成，不要手改。
- 打包脚本会排除 `docs/`，所以文档不会进发布包，可以放心写细节。
