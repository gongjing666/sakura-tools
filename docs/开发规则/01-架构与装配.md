# 01 架构与装配

读完这一页你应该能回答：**代码在哪里、插件怎么启动、后台页面怎么路由、我该往哪儿加东西。**

> 版本基线：1.28.3。详细到每个类与方法的清单见 [代码结构文档](../sakura-tools-代码结构-1.28.3.md)；本页只保留改代码时必须知道的骨架。

## 1. 代码在哪里

```
sakura-tools.php        入口：常量、手写 autoloader、生命周期挂载
uninstall.php           卸载入口（必须自己 require 主文件，见 §6）
fast-search.php         前台快速检索入口
src/                    新代码，PSR-4 风格（Sakura\ImageOptimizer\ → src/）
  Plugin.php            组合根：决定装载哪些模块
  Activation.php        激活：默认 option、建表、排程
  Deactivation.php      停用：清 cron、撤能力
  Upgrade_Guard.php     版本升级守卫（带锁）
  Uninstaller.php       卸载：按开关清数据
  Admin/                后台信息架构与视图组件
  UserFiles/            用户文件空间（命名空间 Nboke\UserFiles\）
  S3/                   对象存储
  Sync/                 持久化同步索引
  Image/ Thumbnail/     图片与缩略图管线
  Backup/ Oss/ Settings/ Stats/ Support/ Filesystem/ Contracts/
includes/               1.3–1.9 时代旧类，仍在承重（见 §2）
assets/ui/              后台样式与脚本（见 03-后台UI.md）
tests/                  PHPUnit
docs/                   文档（不打进发布包）
```

规模参考（1.28.3）：生产 PHP 210 文件 / 74,641 行，其中 `src/` 179 文件 61,187 行、`includes/` 28 文件 12,989 行（含 `includes/views/` 14 文件 6,249 行）；后台 CSS+JS 42 文件 37,037 行。

### 两个命名空间

| 前缀 | 先找 | 找不到再找 | 说明 |
|---|---|---|---|
| `Nboke\UserFiles\` | `src/UserFiles/{rel}.php` | — | 用户文件空间，历史原因独立命名空间 |
| `Sakura\ImageOptimizer\` | `src/{rel}.php` | `includes/class-{lower_snake}.php` | 插件主体；回落才是老的兼容类 |
| 其它前缀 | — | — | 直接返回，不做任何事 |

autoloader 是 `sakura-tools.php:58` 手写的 `spl_autoload_register`（`sakura-tools.php:58-87`），不是 Composer。**新增类只要路径和命名空间对得上就会被自动加载**，不需要注册。注意回落只对 `Sakura\ImageOptimizer\` 生效：`Sakura\ImageOptimizer\Foo_Bar` 在 `src/` 里没有对应文件时，会去找 `includes/class-foo-bar.php`。

### includes/ 不是死代码

主文件里有一段 15 行的 legacy 清单，改之前必读。原文警告：

> ⚠ `includes/class-*.php` 仍在生产承重，不是死代码……删掉任何一行都会在运行时 fatal，而平时不报错。

各文件的职责：backup→每日清理 cron；file-system→压缩管线的移动/删除/路径校验；gd-handler / imagick-handler→图片转换压缩；image-processor→处理器工厂；media-library-module；image-optimizer-module；thumbnail-optimizer-module；thumbnail-manager；animation-detector；stats；s3-storage-module；s3-doge-cloud；s3-cli→WP-CLI 迁移命令。

新代码一律写 `src/`。要动 `includes/` 先问「能不能先在 src/ 包一层」。

### 迁移评估：不搬（2026-11-18）

有人会问「为什么不把 `includes/` 搬进 `src/`」。已实测评估过：**不为整洁而搬**。

- 只搬 14 个类拿不到「删掉 `includes/`」——14 个视图 6,249 行还在，`SAKURA_TOOLS_INC` 与 8 处 src 侧 `include` 都指着它；连视图一起搬，失败面会从「类加载」扩到每个后台页签与用户文件前台面板。
- 真正的坑不在搬文件：autoloader 是命名空间→路径映射、没有 classmap（文件位置就是类契约，挪进子目录不改命名空间会静默失效）；3 个类用 `__DIR__` 相对 include 视图；[tests/bootstrap.php](../../tests/bootstrap.php) 不加载 autoloader，路径错也会全绿；PSR-4 大小写与 [bin/build-plugin-zip.sh:156](../../bin/build-plugin-zip.sh#L156) 的必需文件断言。
- 收益只是「一条规则取代两条」加去掉回落分支与 legacy 清单这个隐形地雷；运行时行为零变化，不修任何现存缺陷。
- **不要顺带重排子命名空间**：`Backup` 类与 `Sakura\ImageOptimizer\Backup` 命名空间、`Stats` 类与 `src/Stats/` 现在就同名共存，重排等于强制改名这两个高频类。

时机：等一次本就要全量回归的改动（例如拆 1,372 行的 [Image_Optimizer_Module](../includes/class-image-optimizer-module.php)）顺手做，单独一次行为零变更提交。数据、改动面与验收清单见 [DECISIONS.md](../../DECISIONS.md) 的「`includes/` 不搬迁」条。

现在只守一条：CI 或 pre-commit 拒收 `includes/` 下的新增文件与新增类。

## 2. 启动顺序

`sakura-tools.php` 只做四件事：定义常量、注册 autoloader、挂钩生命周期、把 `Plugin` 叫起来。

```
plugins_loaded(20) → Plugin::boot()
  ├─ Credential_Cipher::migrate_legacy_option()   旧密钥迁移
  ├─ Options::migrate_legacy_profile()
  ├─ Upgrade_Guard::maybe_upgrade( 版本, Activation::run )   带锁，失败写 transient
  ├─ is_admin()||WP_CLI → Sync\Schema::maybe_install()
  ├─ build_modules() → 逐个 register_hooks( $hooks )
  ├─ admin → admin_init 上排 Scan_Worker / Action_Worker
  ├─ WP_CLI → 注册 sakura-sync / sakura-thumb
  ├─ 手工挂 sakura_imgopt_daily_backup_cleanup
  └─ $hooks->register()      一次性把队列交给 WordPress
```

关键点：**所有钩子先入队，最后统一 `register()`**。这带来两个便利——测试可以在不启动 WordPress 的情况下检查完整钩子面；组合根可以决定某次请求要不要装某个模块。

`Hook_Loader` 的行为要记住（`src/Support/Hook_Loader.php`）：

- `add_action( $hook, $callback, $priority = 10, $accepted_args = 1 )`，`add_filter` 同签名；
- `register()` 幂等；
- **注册之后再 `add_action` 会立即生效**，不再入队。有代码依赖这个行为（`register_frontend`），改 `Hook_Loader` 前先搜一遍。

## 3. 模块契约

```php
// src/Contracts/Module.php
interface Module {
    public function register_hooks( Hook_Loader $hooks ): void;
}
```

契约注释原文：

> Implementations must not add WordPress hooks in their constructors, so the composition root can decide which modules to load and tests can inspect the complete hook surface without booting WordPress.

所以：

- **构造函数只做赋值**，所有 `add_action` / `add_filter` 走 `register_hooks()`；
- 需要依赖就用构造函数注入（`Plugin::__construct( ?Hook_Loader $hooks = null )` 是范例，测试靠它注入假 loader）；
- 一个模块只负责一件事。渲染、设置、后台资源三样都在同一个模块里时，用不同的方法分开挂。

`src/Contracts/` 另有四个仓储接口：`Backup_Repository_Interface`、`File_System_Interface`、`Settings_Repository_Interface`、`Stats_Repository_Interface`。它们的意义是把文件系统与数据库从业务里摘出去，让测试能注入内存实现。新代码要碰这三类资源时，先看有没有现成接口。

## 4. 模块装配表

`Plugin::build_modules()` 的顺序是有讲究的，改顺序可能让 renderer 找不到：

| 顺序 | 装什么 | 条件 |
|---|---|---|
| 1 | 5 个仓储 + `Image_Processor` | always |
| 2 | `System_Settings_Module`、`Image_Optimizer_Module` | is_admin |
| 3 | `Thumbnail_Manager`、处理器 | always |
| 4 | `Media_Library_Module` | is_admin（只提供卡片位置，不注册钩子） |
| 5 | `Thumbnail_Optimizer_Module` | always |
| 6 | `Options`、`Storage_Adapter`、`Index_Repository`、`Scan_Service`、`Scan_Worker` | always |
| 7 | `Sync_Calibrator`、`Action_Worker`、`Alerting`、`Prometheus`、`Attachment_Indexer`、`Verify_Worker` | always |
| 8 | `S3_Storage_Module`、`Sync_Center_Module`、`Delete_Queue_Panel` | is_admin |
| 9 | `Admin\Menu` | is_admin，**必须最后** |
| 10 | `Delete_Worker`、`Upload_Observer`、`Storage`、`Nboke\UserFiles\Module` | always |

`Admin\Menu` 压轴的原因写在代码注释里：*The menu is registered last so every renderer exists*。菜单构建时要遍历 `Registry` 里已注册的 renderer，早装就会拿到空表。

类注释另有一句边界：*Admin-only modules are not loaded on front-end or REST requests.* 前台请求不装后台模块，别把前台要用的逻辑塞进 admin 分支。

## 5. 后台页面怎么路由

四层，从上往下：

```
Registry::modules()      声明有哪些模块、每个模块有哪些页签
      ↓
Admin\Menu             把模块变成 add_menu_page / add_submenu_page
      ↓
Registry::current()     从 ?page= 与 ?t= 解出当前 module/tab
      ↓
renderer( module, tab ) 取事先 register_renderer 注册的回调
```

### 模块表

| module | slug | caps | tabs |
|---|---|---|---|
| system | `sakura-tools` | `manage_options` | settings |
| image | `sakura-tools-image` | `manage_options` | rules, thumb, backup, stats |
| storage | `sakura-tools-storage` | `manage_options` | connection, sync, deletes, rewrite, cost |
| files | `sakura-tools-files` | `review` | settings, users, queue, log, zibll |

页签参数是 `t`，不是 `tab`。`Registry::url( $module, $tab )` 在「默认页签且模块有多个页签」时会省略 `t`。

### 三处容易踩的地方

1. **`Registry::current()` 对非本插件页面返回 `array( '', '' )`**。这是审计 A09 的修复——曾经它把所有非插件页都当成 system 页，导致 CSS/JS 串到别的后台页。任何「当前是不是我的页」的判断都必须走它或 `Registry::on()`。
2. **`Menu::render()` 有四道闸**：`current_user_can( $cap )` → `tab_gate()` 的 capable → enabled → renderer 存在。`!enabled` 时返回 403 + `noindex`，并渲染 `render_locked()`；那个方法的契约是「no form, no nonce, no business value」——只解释缺什么、怎么回去。
3. **旧 slug 要在 WP 校验 `?page=` 之前拦下**，所以 `redirect_legacy` 挂在 `init` 优先级 5 与 `admin_page_access_denied` 优先级 5 两处。

### 页签的门禁

页签可以带 `gate`：

```php
'users' => array(
    'label' => __( '用户容量', 'sakura-imgopt' ),
    'gate'  => array( 'caps' => 'execute' ),
),
```

或带条件回调：

```php
'gate' => array(
    'when' => static fn(): bool => Zibll_Bridge::instance()->available(),
    'note' => static fn(): string => Zibll_Bridge::instance()->note(),
    'code' => 'zibll',
    'caps' => 'manage',
),
```

`Registry::tab_gate()` 返回 `array{enabled,note,code,caps,capable}`；`tab_can()` 在 `manage_options` 下恒真，否则按 `review` / `execute` 走 `Nboke\UserFiles\Capabilities::can_review()/can_execute()`。

## 6. 生命周期四件事

### 激活（`Activation::run`）

默认 option → `s3_options` → 旧键迁移（`irmia_imgopt_*` → `sakura_imgopt_*`）→ 三处 `maybe_install()`（Sync、S3 上传指标、UserFiles）→ 排程 7 处（`sufm_tick` 单次 +30s、`Scan_Worker::schedule_maintenance()`、`Sync_Calibrator::schedule()`、`Delete_Worker::schedule()`、`Verify_Worker::schedule()`、`Alerting::schedule()`、每日备份清理）→ **最后才写版本号**。

版本号最后写的理由在注释里：前面的建表/排程任一步失败时，`Upgrade_Guard` 下次请求仍会重跑。**加新步骤时要保住这个顺序**。

### 升级（`Upgrade_Guard`）

`version_compare( 已装, 当前, '<' )` 判定；用 `add_option()` 抢锁（比 transient 原子），锁 300 秒过期可抢占；失败写 transient 并 `do_action( 'sakura_imgopt_upgrade_failed', $error )`。

### 停用（`Deactivation::run`）

清 8 个具名 cron + `wp_unschedule_hook` 兜底 + 按常量数组清 `Action_Worker::HOOK`、`Scan_Worker::CLEANUP_HOOK`/`DAILY_HOOK`、`Sync\Schema::BACKFILL_HOOK`/`BACKFILL_RECENT_HOOK`、`Sync_Calibrator::CALIBRATE_HOOK`/`KICK_HOOK`、`sakura_imgopt_sync_scan_tick`，最后撤 6 个能力。

注释：「停用只清定时任务；媒体 URL、选项与备份都保留，卸载时按开关处理。」**加新 cron 必须同步加到这里**，否则停用后它还在跑（审计 B12 就是这个问题）。

### 卸载（`uninstall.php` + `Uninstaller`）

`uninstall.php` 必须先 `require_once` 主文件再 `require_once` `src/Uninstaller.php`。原因写在注释里：WP 执行卸载时主文件从未加载、autoloader 没注册，不 require 会 `Nboke\UserFiles\Capabilities` fatal，站点半卸载。

流程：`cleanup_current_site()` → 判断 `sakura_imgopt_delete_data_on_uninstall`（默认关）→ `cleanup_persistent_data()`。

24 张自定义表，每个数据域一个 schema 类：

| 归属 | 表前缀 | 建表方法 | 版本 option |
|---|---|---|---|
| 同步索引 | `{prefix}sio_sync_*` | `Sync\Schema::maybe_install()` | `sakura_imgopt_sync_schema`（v1.9.0） |
| 用户文件空间 | `{prefix}sufm_*` | `UserFiles\Schema::maybe_install()` | `UserFiles\Schema::VERSION_OPTION` |
| S3 上传指标 | `{prefix}sio_s3_upload_events` | `S3\Upload_Metrics::maybe_install()` | — |
| S3 删除队列 | `{prefix}sio_s3_deletes` | `S3\Delete_Jobs` | — |
| 链接改写账本 | `{prefix}sio_url_rewrites` | `S3\Url_Rewrite_Repository::maybe_install()` | `sakura_imgopt_url_rewrite_schema`（v1） |

同步索引 6 张（index / scans / …），用户空间 15 张（media_operations、folders、files、file_tokens、usage、reservations、artifacts、delete_requests、delete_request_items、delete_batches、jobs、events、notifications、rate_limits、space_grants）。

option 命名统一 `sakura_imgopt_*`；UserFiles 用 `sufm_*`。表名一律走各 Schema 类的 `table()`，不手拼。

详细约定见 [04-数据与存储.md](04-数据与存储.md)。

## 8. 后台资源怎么加载

`Page_Assets::enqueue( $page )` 是唯一入口，`Assets::enqueue_page()` 只是它的薄包装（`Page_Assets::enqueue( Route::current_page() )`）。

样式顺序固定：`tokens.css` → `base.css` → `components.css` → `pages/{module}.css`（存在才加载）→ `pages/{page}.css`（存在才加载）。脚本顺序固定：`core.js` → `api.js` → `ui.js` → `pages/{page}.js`。

版本串用 `group_version()` 生成：`版本号.mtime.字节数`。所以**改完文件不用手动改版本号，浏览器也会重拉**。

配置通过 `wp_localize_script( 'sakura-admin-core', 'sakuraPage', $config )` 注入，含 `ajaxUrl`、`restUrl`、`nonce`、`data`（来自 `Page_Assets::set_data()`）、`strings`。

页面专属数据要在 `admin_enqueue_scripts` 里先 `set_data( $page, $config )` 再 `Assets::enqueue_page()`。

## 9. 前台入口

前台只有三处：

- **`fast-search.php`**：一个直接访问的独立文件，用 `SHORTINIT` 只加载 WordPress 的一小部分。完整引导要 ~150ms，而查询本身不到 1ms，所以它绕开 `admin-ajax.php`，自己校验短期 HMAC 令牌（绑定用户 + profile + 10 分钟有效期，只授只读对象元数据）。改分页/搜索契约时要和 AJAX 端点一起改，两边返回同样的结构。
- **`Nboke\UserFiles\Module::register_frontend()`**：挂在 `after_setup_theme` 上——主题函数（含子比的 URL helper）此时才存在，`plugins_loaded` 时还没有。它只在前台（或 AJAX）且 `Settings::entry_enabled()` 为真时才 `new Frontend\Entry` 并把钩子交给**同一个** `Hook_Loader`。这里依赖「注册后再 `add_action` 会立即生效」：loader 早已 register 过，晚加的钩子被直接转发给 WordPress。
- **`Nboke\UserFiles\Space_Panel::register()`**：在主文件 `plugins_loaded` 优先级 20 上，用 `class_exists` 守卫后调用。它挂 `wp_enqueue_scripts`、`rest_api_init`、`payment_order_success`（优先级 12），以及一个优先级 5 的资源过滤器（要早于主题为 AJAX 页签补资源的时机）。

前台还有媒体库与编辑器面板：REST 面永远注册（每条路由自己判权限），前台入口则受 `Settings::entry_enabled()` 开关控制——「主题暴露哪个用户中心」是主题问题，媒体库不是。

其余模块都在 admin 分支里，前台请求不会加载。
