# 04 数据与存储

这一页管三件事：**option 怎么存、表怎么建、数据怎么清**。改数据库或加 option 前必读。

> 装配关系见 [01-架构与装配.md](01-架构与装配.md)，新功能的整体流程见 [02-新增功能.md](02-新增功能.md)。

## 1. 三类存储

| 类型 | 用什么 | 谁负责 | 例子 |
|---|---|---|---|
| 设置 | `wp_options` | `Settings_Repository` / 各模块 | `sakura_imgopt_quality` |
| 自有数据 | 自定义表 | 三个 Schema 类 | `{prefix}sio_sync_index` |
| 派生/缓存 | option 或瞬态 | 各 worker | `sakura_imgopt_sync_metrics` |

**业务代码不直接调 `get_option()` 读写设置**——那是 `Settings_Repository` 的职责。它的类注释：

> this class owns the option names, defaults and typed reads so image/admin services do not call `get_option()` directly.

## 2. option 命名与归属

| 前缀 | 归属 | 例子 |
|---|---|---|
| `sakura_imgopt_` | 插件主体 | `sakura_imgopt_quality`、`sakura_imgopt_backup_enabled` |
| `sufm_` | 用户文件空间 | `sufm_schema_version`、`sufm_settings` |
| `s3_options` | 对象存储（沿用 S3 Uploads 的键，**故意不加前缀**） | `s3_options['bucket']` |

`s3_options` 不加前缀是刻意的兼容决定：S3 Uploads 插件用同一组键，加了前缀就无法共存或迁移。

历史键 `irmia_imgopt_*` 已在 `Activation::run()` 里迁移到 `sakura_imgopt_*`（新键存在则跳过）。**不要再用 irmia 前缀写新代码**。

### 设置项的四处登记

新增一个 option 要同时改四个地方，漏一个就会出现「默认值不生效」或「卸载后残留」：

1. `Settings_Repository::DEFAULTS`——默认值（键是完整 option 名）；
2. 一个带类型的读取方法（内部做范围钳制）；
3. `Activation::run()` 的默认 option 列表——`add_option()` 只在键不存在时写入；
4. `Uninstaller` 的清理清单——见 §5。

## 3. 设置保存：一张卡一个表单

后台一张可编辑卡 = 一个独立表单，只保存本卡的 option。表单由 `UI::card()` 的 `form` 参数生成：

```php
UI::card(
    array(
        'id'   => 'compress',
        'form' => array(
            'option_group' => 'sakura_imgopt_settings',
            'markers'      => 'fields',
        ),
        'save' => '保存设置',
    ),
    $body
);
```

### 为什么需要 Card_Form

`options.php` 会把**提交组里注册的所有 option** 一起保存。没有防护的话，保存「压缩」卡会把「缩略图」卡的 option 清空。`Card_Form` 的类注释：

> options.php saves every option registered for the submitted group. Without a guard, saving one card would blank the options owned by the other cards.

它给表单塞两个隐藏字段（`_sakura_card`、`_sakura_partial=1`），再用 `pre_update_option` 过滤器把「不属于本卡」的 option 保持原值。

### 三种 markers

| markers | 用于 | 额外参数 |
|---|---|---|
| `fields`（默认） | 多 option 表单 | — |
| `option_fields` | 单个数组型 option | `option => 'option_name'` |
| `none` | 自定义 saver（自己处理提交） | — |

`option_fields` 把标记写进 option 数组内部（`$option[_sakura_card]`），因为 `options.php` 只把 option 值传给 sanitize 回调，顶层隐藏字段到不了那里。

### 服务端守卫

`register_setting()` 之后必须调：

```php
Card_Form::guard_options( 'sakura_imgopt_basic', array(
    'layout' => array( Layout::GAPS_OPTION, Appearance::OPTION ),
) );
```

数组是「卡片 id => 该卡拥有的 option 列表」。

### 现有的 option group

| group | 谁注册 | 涵盖 |
|---|---|---|
| `sakura_imgopt_settings` | `Image_Optimizer_Module` | 压缩、尺寸、重命名等主设置 |
| `sakura_imgopt_backup_settings` | `Image_Optimizer_Module` | 备份策略 |
| `sakura_imgopt_oss_group` | `Thumbnail_Optimizer_Module` | 缩略图场景与尺寸 |
| `sakura_imgopt_basic` | `System_Settings_Module` | 布局间距、外观 |
| `sufm_settings_group` | `UserFiles\Admin\Page` | 文件空间基础设置 |
| `sufm_space_group` | `UserFiles\Admin\Space_Page` | 空间扩容与支付 |

新页签**优先复用已有 group**；确实新增时，记得同步 `guard_options` 的映射。

## 4. 自定义表

### 三套 schema

| 归属 | 表前缀 | 类 | 版本常量 |
|---|---|---|---|
| 同步索引 | `{prefix}sio_sync_` | `Sync\Schema` | `VERSION = '1.8.2'`，option `sakura_imgopt_sync_schema` |
| 用户文件空间 | `{prefix}sufm_` | `UserFiles\Schema` | `VERSION = '1.6.0'`，option `sufm_schema_version` |
| S3 上传指标 | `{prefix}sio_s3_upload_events` | `S3\Upload_Metrics` | 无独立版本，随主版本 |
| S3 删除队列 | `{prefix}sio_s3_deletes` | `S3\Delete_Jobs` | 同上 |

同步索引 6 张：`index`、`scans`、`counts`、`jobs`、`events`、`operations`。

用户空间 15 张：`media_operations`、`folders`、`files`、`file_tokens`、`usage`、`reservations`、`artifacts`、`delete_requests`、`delete_request_items`、`delete_batches`、`jobs`、`events`、`notifications`、`rate_limits`、`space_grants`。

### 建表规范

```php
public static function table( string $name ): string {
    global $wpdb;
    return $wpdb->prefix . 'sio_sync_' . $name;
}
```

- **表名一律走 `table()`**，不手拼。PHPCS 的 `PreparedSQL.InterpolatedNotPrepared` 已被关掉，正因为表名全部来自这里；
- 建表用 `dbDelta()`，SQL 写成一行一个 `CREATE TABLE`，字符集用 `$wpdb->get_charset_collate()`；
- `dbDelta()` 对格式敏感：`PRIMARY KEY  (id)` 是两个空格、小写、字段定义每行独占。

### 版本守卫

```php
public static function maybe_install(): void {
    if ( self::VERSION === (string) get_option( self::OPTION, '' ) ) {
        return;
    }
    self::install();
}
```

**只有全部语句成功才写版本号**。`Sync\Schema::install()` 在失败时直接 return 并 `do_action( 'sakura_imgopt_s3_schema_failed', $failed )`，注释写明理由：

> Never advertise a version that did not fully land: the next request would skip the migration and then read missing tables or columns.

### 迁移

版本比较用 `version_compare( $previous, '1.1.0', '<' )` 挂在 `install()` 尾部。约定：

- **大批量回填不放在请求里**：先做一批（如 20000 行），剩下的交给 `wp_schedule_single_event` 的 cron 钩子；
- 回填期间旧查询路径要保持正确（`Sync` 的 `recent_at` 回填就是这样：回填没完成时 repository 回退到旧谓词，只是慢一点）；
- 回填完成写一个「就绪」option（如 `sakura_imgopt_sync_recent_ready`），后续查询靠它切快路径。

### 升级顺序

`Activation::run()` 的版本号写在**最后**，注释解释：

> 前面的建表/排程任一步失败时，Upgrade_Guard 下次请求仍会重跑。

改这一段要保持顺序：默认 option → 建表 → 排程 → 写版本。

## 5. 卸载：删什么、留什么

`uninstall.php` 先 `require_once` 主文件与 `Uninstaller.php`（否则 autoloader 没注册会 fatal），再调 `Uninstaller::run()`。

### 无条件删除

- 6 张同步索引表 + `sio_s3_uploads`/`sio_s3_deletes`/`sio_s3_upload_events` 历史表；
- 所有 cron 事件（`wp_unschedule_hook` 逐个清，批量事件带 id 清不干净）；
- 6 个自定义能力（`Capabilities::revoke()`）——注释：能力不是用户数据。

同步索引无条件删的理由在注释里：

> It is dropped unconditionally: keeping a multi-hundred-megabyte orphan table after uninstall would surprise site owners, and a reinstall rebuilds it with one scan.

### 有条件删除

只有 `sakura_imgopt_delete_data_on_uninstall` 为 1 时，才执行 `cleanup_persistent_data()`：删除设置、`sufm_*` 表、云存储密钥、备份文件。

用户空间表默认**保留**：

> The user file space keeps its tables by default: the ledger explains every attachment it owns, so a reinstall can resume instead of orphaning rows.

否则只调 `delete_ephemeral_data()` 清瞬态与锁。

### 清理清单

新增 option / 表 / 目录时，按性质归入：

| 方法 | 放什么 |
|---|---|
| `monitoring_options()` | 监控类（上传指标、告警、Prometheus token） |
| `derived_options()` | 可重建的派生状态（扫描缓存、同步统计、缩略图统计） |
| `delete_ephemeral_data()` | 锁、瞬态、升级标记 |
| `cleanup_persistent_data()` | 真正的用户数据（设置、密钥、备份） |

**新增一张表必须同时改 `drop_sync_tables()` 或 `drop_sufm_tables()`**，否则卸载后留下孤儿表。

## 6. 文件存储

| 内容 | 位置 | 谁管 |
|---|---|---|
| 原图备份 | `uploads/` 下的备份目录 | `Backup_Repository`，cron `sakura_imgopt_daily_backup_cleanup` 清理 |
| 缩略图缓存 | `uploads/` 下缓存目录 | `Thumbnail\Cache`，可 flush |
| 用户文件 | 虚拟目录映射到 `uploads/` | `UserFiles\...`，配额在 `sufm_usage` |

- 文件操作走 `File_System_Interface`（`Filesystem\File_System_Repository` 是默认实现），不要在业务类里直接 `unlink()` / `rename()`；
- 备份目录要定期探测是否可被公网访问（`Backup_Exposure_Probe`），后台「备份还原」页有检测按钮。

## 7. 队列与租约

三套 worker 都是「队列表 + cron tick + 租约」的结构：

| worker | 表 | 钩子 |
|---|---|---|
| `Action_Worker` | `sio_sync_jobs` | `sakura_imgopt_sync_job_tick` |
| `Delete_Worker` | `sio_s3_deletes` | `sakura_imgopt_s3_delete_tick` |
| `Scan_Worker` | `sio_sync_scans` | `sakura_imgopt_sync_scan_tick` |

租约（lease）防并发：认领时写 `lease_until` 与 `claim_token`，处理完清空。新写 worker 要照抄这个模式，**不要用「先查再改」的非原子判断**。

幂等靠唯一键：`sio_sync_jobs.dedupe_key` 是 `UNIQUE KEY`，重复入队会被 `INSERT IGNORE` 吃掉。

## 8. 多站点

- 每站独立 option、独立表（`$wpdb->prefix` 含站点 id）；
- `Activation` / `Deactivation` 由 WP 逐站触发；
- `Uninstaller::run()` 在 `is_multisite()` 时遍历所有站点 `switch_to_blog()` 逐个清；
- 上传目录也按站点分。

写新逻辑时如果用了 `get_site_option()`，要想清楚是不是真的全网共享——现有代码全部用站点级 option。

## 9. 数据安全红线

- 表名、字段名可以拼；**值必须走 `$wpdb->prepare()`**；
- `IN (...)` 用 `implode( ',', array_fill( 0, count( $ids ), '%d' ) )` 生成占位符（PHPCS 数不清这类，会报 warning，属已知误报）；
- 密钥用 `Credential_Cipher` 加密后存 `s3_options`，不要明文落 option；
- REST 的 owner id 一律从会话取，类注释：*Every owner id comes from the session; a request body can never name one.*
