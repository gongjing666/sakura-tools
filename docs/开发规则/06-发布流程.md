# 06 发布流程

一次发布 = **改版本号 → 写 changelog → 本地三关 → 提交推送 → 打包/自动 Release → 部署验证**。

## 1. 版本号必须三处一致

| 位置 | 形式 |
|---|---|
| `sakura-tools.php` 头部 | `* Version:     1.27.5` |
| `sakura-tools.php` 常量 | `define( 'SAKURA_TOOLS_VERSION', '1.27.5' );` |
| `readme.txt` | `Stable tag: 1.27.5` |

**不一致会让 `release.yml` 直接失败**（它读着头版本号去比对 Stable tag，不等就 `exit 1`）。

版本号语义照常：`MAJOR.MINOR.PATCH`。修 bug 走 PATCH，新功能走 MINOR；破坏兼容（option 键改名、表结构不兼容、钩子语义变化）走 MAJOR，并在 changelog 里写明迁移路径。

## 2. 写 changelog

在 `readme.txt` 的 changelog 区顶部插入：

```
= 1.27.6 =

* 修复：……

= 1.27.5 =
```

约定（从现有条目看出来的）：

- 标题严格是 `= 版本号 =`，前后空行；
- 每条一句话，中文，以「新增 / 修复 / 调整 / 优化 / 移除」开头；
- **写清影响范围**：涉及哪些文件、是否改数据、是否改路由。现有条目里常见「不改数据、路由、option 键与钩子语义」这类收尾句，就是为升级决策服务的；
- `release.yml` 会用 awk 从这个标题抽到下一个 `= 数字` 之间作为 GitHub Release 的正文。**空条目会导致 Release 正文退化成一个标题**。

## 3. 本地三关

```bash
composer test          # PHPUnit，基线 470 tests / 2411 assertions
composer phpstan       # level 5，必须 [OK] No errors
composer lint:strict   # PHPCS，无 error
```

加上静态检查：

```bash
php -l sakura-tools.php
# 改了 JS 的：
node --check assets/ui/js/xxx.js
# CSS：花括号配平
git diff --check          # 行尾空白
```

判据见 [05-测试与质量.md](05-测试与质量.md)。CI 不跑 PHPCS，本地这关不能省。

后台有改动时还要按 [03-后台UI.md](03-后台UI.md) 第 11、12 节在浏览器走一遍。

## 4. 提交

提交信息用 Conventional Commits 前缀，现有历史是英文：

```
perf(ui): cut the admin's page-change cross-fade, feedback on click
refactor(ui): replace the drag layout engine with static card placement
release: 1.26.0
fix(s3): ...
```

- 一个提交只做一类事（重构与功能分开、格式与行为分开）；
- 版本发布提交用 `release: X.Y.Z`；
- **不要在一次提交里混入无关的格式化改动**——PHPCS 的格式类 sniff 已关闭，正是为了避免这种 diff。

推送到 `main`（历史主干就是 `main`）。

## 5. 打包

### 本地（验证用）

```bash
bin/build-plugin-zip.sh --version 1.27.5 --out dist
```

输出：

```
dist/sakura-tools-1.27.5.zip
dist/sakura-tools-1.27.5.zip.sha256
```

补建历史版本包：

```bash
bin/build-plugin-zip.sh --ref c8e6b4a --version 1.22.9 --out dist
```

脚本的行为要点：

- 用 `git archive` 从 ref 出包，**只含已跟踪文件**，未跟踪的本地文件不会泄漏；
- 出包后删掉开发路径：`.github/`、`bin/`、`docs/`、`tests/`、`stubs/`、`.phpunit.cache`、`.gitignore`、`composer.json/lock`、`phpcs.xml.dist`、`phpstan.neon`、`phpunit.xml.dist`、`DEVELOPMENT.md`、`DECISIONS.md`；
- 只保留 `vendor/s3/`，其余 `vendor/` 内容清空；
- 断言必需文件存在（`sakura-tools.php`、`uninstall.php`、`readme.txt`、`includes/class-image-processor.php`、`src/Plugin.php`、`vendor/s3/vendor-prefixed/autoload.php`）；
- 断言包里没有开发文件；
- 输出 `Files / Size / SHA256`。

**`dist/` 被 `.gitignore` 忽略**，不进版本库。

> 新增根目录下的 md 文件如果不想进发布包，要加进脚本的 `rm -f` 列表；`docs/` 下的内容自动被排除。

## 6. GitHub Release（自动）

`release.yml` 在 push `main` 且改动以下任一文件时触发：

- `sakura-tools.php`
- `readme.txt`
- `bin/build-plugin-zip.sh`
- `.github/workflows/release.yml`

也可以在 Actions 里手动 `workflow_dispatch`。

流程：

1. 从主文件 `sed` 出版本号，校验正则 `^[0-9]+\.[0-9]+\.[0-9]+([.-][0-9A-Za-z.-]+)?$`；
2. 校验 `readme.txt` 的 `Stable tag` 与之一致，不一致直接失败；
3. `gh release view v<版本>` 判断是否已存在，存在就跳过；
4. `bash bin/build-plugin-zip.sh --version X --out dist`；
5. 用 awk 抽 changelog 段落写 `release-notes.md`（空则回退一行标题）；
6. `gh release create v<版本> dist/*.zip dist/*.zip.sha256 --target $GITHUB_SHA --title v<版本> --notes-file release-notes.md`。

并发控制 `group=plugin-release`、`cancel-in-progress: false`、`timeout-minutes: 10`。

**要重建同一个版本**：先删掉对应的 Release 与 tag，再手动跑 workflow。

### 手打 tag 的情况

历史上 `v1.27.0` / `v1.27.1` / `v1.27.3` / `v1.27.4` / `v1.27.5` 是轻量 tag 指向提交。手工打 tag 时：

```bash
git tag v1.27.5
git push origin v1.27.5
```

注意**光打 tag 不会产出 Release 附件**——附件只由 workflow 生成。要么让 workflow 跑一次，要么用 `gh release create` 补。

## 7. 部署

生产的插件目录是一个 **git checkout**，所以升级用：

```bash
cd /www/wwwroot/www.nboke.com/wp-content/plugins/sakura-tools
git fetch origin
git merge --ff-only origin/main
chown -R www:www .
```

要点：

- `--ff-only` 保证不会产生合并提交；有本地改动先查 `git status`；
- **部署后属主会被 git 改成 root，必须 `chown -R www:www` 修回**，否则 WordPress 无法写文件；
- 验证：
  ```bash
  wp plugin list --allow-root | grep sakura
  git describe --tags --exact-match
  git status --porcelain     # 应为空
  ```

### 上线前必做的三件事

1. **备份**：`tar czf /www/backup/sakura-tools-<日期>.tar.gz <插件目录>`；
2. **浏览器实测**：目标版本的页面能打开、主内容渲染、console 干净；
3. **debug.log**：确认没有新增 fatal/warning。

## 8. 发布检查表

- [ ] 版本号三处一致
- [ ] `readme.txt` changelog 顶部有对应条目，且写清影响范围
- [ ] `composer test` 全绿
- [ ] `composer phpstan` 无错
- [ ] `composer lint:strict` 无 error
- [ ] 改动的 PHP `php -l` 通过、JS `node --check` 通过
- [ ] 后台改动已在 1440 与 390 看过
- [ ] 新增/修改的 cron 已进 `Deactivation::run()`
- [ ] 新增表/option 已进 `Uninstaller` 清理清单
- [ ] 文档已同步（规则文档、代码结构文档、changelog）
- [ ] `git push origin main` 后 workflow 跑通、Release 附件存在
- [ ] 生产部署后 `chown -R www:www`、`git status` 干净、浏览器验证通过

## 9. 回滚

- **代码**：`git checkout <上一个 tag>` 再 `git merge --ff-only` 回来，或直接 `git reset --hard v<上一个版本>`（仅当确认无本地改动）；
- **数据**：表结构向前兼容就无需回滚；不兼容时用备份 tar 还原目录 + 数据库备份还原；
- **对象存储**：`sio_sync_*` 表是可重建缓存，删了重扫即可，不要试图手工修补。

回滚后记得重新 `chown -R www:www`。
