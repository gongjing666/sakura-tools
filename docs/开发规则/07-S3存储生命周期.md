# 07 S3 存储生命周期

这一页规定一份存储配置从「填好」到「删除」的整条路径：什么时候允许换桶、第一次上传成功之后锁住什么、关掉总开关之后能做什么、删配置时连带清什么。**存储页面上的每个按钮，都必须能在这一页找到它属于哪一格。**

> 相邻篇：option 的读写、登记与卸载见 [04-数据与存储](04-数据与存储.md)；卡片、弹窗、令牌与 1440/390 验收见 [03-后台UI](03-后台UI.md)；新增一家存储厂商见 [02-新增功能](02-新增功能.md) §12；把对象从旧桶搬到新桶见 [08-OpenList搬桶手册](08-OpenList迁移通道.md)（插件不实现迁移通道，搬对象是插件原生上传或人工操作）。
> 本页引用的行号以 **`1.28.3`**（2026-11-18）为准，改代码后如与代码不符以代码为准并顺手修正本页。
> **状态：R1–R19 已全部实现并已在生产验证（1.28.3，2026-11-18）。** 逐条落地的 beta 版本见 §8 表；R19 的步骤 1–7 在 `1.28.2-beta-8`，步骤 8（Schema 1.9.0，索引按桶身份分区）在 `1.28.2-beta-9`，批次写入的占位符缺陷在 `1.28.2-beta-10` 修复，全部随 `1.28.3` 发布。 §1 与 §2 描述的是**施工前**（`1.28.1-beta-6`）的样子，保留下来是为了说明每条规则在补什么洞，不是现状；逐条落点见 §8，验收见 §9（标「待真机」的条目还要在开发者的浏览器与生产各走一遍）。

## §0 为什么需要这一页

存储配置不是「一张表单」，而是一个有状态的实体。过去三个版本各修了一次同一个形状的问题，根因都是状态没被显式建模：

| 版本 | 现象 | 真正的错 |
|---|---|---|
| 1.27.6 之前 | 改配置时偷偷多出一份 | 保存语义没有区分「改这份」和「换一份」 |
| 8119bf8 | 换服务商保存，覆盖掉原配置 | 「换目标」被当成「改这份」 |
| b819827 | 换桶后附件 URL 全部退回站点域名 | 「已上传到哪个桶」没有权威记录，只能靠指纹推断 |

三次的共同点：**没有一处代码能回答「这份配置现在处于什么状态、因此允许什么」**。每次修补都是在具体分支上加一个 if，下一个分支又漏。所以这一页先把状态和判定表定死，再谈实现。

## §2 十二个缺口

> 十二条都已按 §5 补上。缺口描述保留原样，因为它们解释了规则为什么长这样；逐条落点见 §8。

1. **默认值不是约束。** 「默认保留本地」只是表单初始值。用户随手一勾就变成「上传后删本地」，而删除本地与「以后想换桶」在数据上是互斥的——本地没了，新桶永远补不齐。默认值挡不住这个操作，只有锁定挡得住。
2. **没有绑定概念，换桶成本为零。** 换一份配置只需点一张卡片，没人问「新桶里有没有这些对象」。代价由三个月后的裂图承担。
3. **删除语义与开关状态脱钩。** 现在「能不能删」只看「是不是活动配置」，于是最该删的那种（关掉总开关后要换桶）偏偏删不掉，而不该留的（绑定中的配置）只要先切走就能删。
4. **删除确认只有一句话。** 它既没说云端对象不会被删，也没说哪些附件会因此永久失联，更没有要求操作者确认自己删的是哪一份。
5. **上传指标只增不减。** `sio_s3_upload_events` 全表 GROUP BY 出 totals，清理逻辑从来没写过。站点跑三年，这张表就是三年。
6. **上传行为不受生命周期约束。** 「不上传 WordPress 生成的缩略图」今天可以随手上下来回切，而它决定云端到底有没有子尺寸：绑定后切一次，同一站点的附件就分成「带尺寸」和「不带尺寸」两段，缩略图改写开到哪一段，哪一段的尺寸 URL 就是 404。它和「删除本地文件」一样属于「一次决定、长期生效」的开关，必须与绑定一起冻结（R11）。
7. **URL 出口没有被登记。** 插件只挂在 `wp_get_attachment_url` 上，`srcset` 的候选由 WordPress 用 `wp_upload_dir()['baseurl']` 自拼（`wp-includes/media.php:1501-1502`），正文里的 `<img>` 更是发布时固化的。换桶、删本地、不上传子尺寸的后果会从这些没登记的出口漏出去，而「现在没裂图」往往只是 `sizes` 为空把整段短路了（R12）。
8. **「在桶里」这件事只写了一半的账。** 上传成功会写一整套同步状态，但从桶里下载回来不会——下载路径只写对账索引与媒体库记录，附件 meta 停在 `pending`。于是同一个桶里的同一张图，上传进来的走 CDN，下载回来的走站点域名。索引里那条 `synced` 也救不了：指纹判定与索引核对全包在 `SYNCED === $status` 里，`pending` 的附件根本轮不到（R13）。
9. **下载回来的附件没有主人。** 上一条的孪生缺口在另一本账上：`Attachment_Adopter` 有意挂 `sufm_skip_attachment_adoption` 跳过采纳（钩子时机不对，记了也是记错人），但下载完成后没有人补——`sufm_files` 无行，媒体库按 `NOT EXISTS` 判成「未分配媒体」，该管理员的配额也从未增加过这 192994 字节。R13 修的是 URL，这条修的是归属与配额（R14）。
10. **URL 语法靠一次联网测试决定，而测试结果会过期。** 「自动」方式在 `1.28.2-beta-3` 之前要先点「立即测试」，插件 `HEAD` 一张桶里的样图，通不过就判「不处理」。这条路有三个问题：测试是手工触发的，跑完就把结论存成 option，之后存储配置怎么变它都不知道；样本图挑的是「已同步」的附件，刚换桶时那些附件还没落盘，取到的样本可能在新桶里根本不存在，于是「明明是好的配置却报 404」；最要紧的是它让**一张图片的可用性**决定**整站 URL 语法**——语法本来只需要知道「这家厂商支持哪种写法」，那是 `Provider_Registry` 里的一张静态表，不需要问桶（R15）。
11. **缩略图改写与存储状态脱钩。** 存储换桶、换商、换图片域名之后，缩略图改写（`sakura_imgopt_oss_thumb['enabled']`）照旧开着，继续用旧桶的命名样式与旧域名拼 URL。旧版唯一的兜底是删掉探测结果，让「自动」方式降级成 `none`——而这一步随探测一起被删掉之后，就彻底没有人管了（R16）。
12. **切桶之后，同步中心继续拿上一个桶的数字做事。** 索引是按 `profile_id` 分区的，切到新配置那一刻，页面上的「已同步 132 / 覆盖率 100%」全部属于旧桶；而这些按钮——「刷新差异」「重试失败」「批量删除」「行内删除」——都按这些数字去**新桶**执行。更要命的是「开始完整核对」这个按钮其实发的是增量扫描（`ajax_scan()` 自 v1.22.8 起调 `start()` 不传 mode），旧索引还在，增量只补新文件，永远对不出新桶的全貌。用户唯一的提示是左下角一句「已启用这份配置。」，等下一次刷新才可能看到别处的提醒，中间那几分钟可以做任何事（R18）。

## §3 状态机

存储配置只有四个状态。**任何操作都要先落到一个状态，再查它允许什么。**

| 状态 | 判定 | 这一态允许 | 这一态禁止 |
|---|---|---|---|
| **S0 空** | 没有可用配置 | 新增配置、填表、测试连接 | 启用 S3 存储（没有卡片可点，开关只能由卡片触发） |
| **S1 未绑定** | 活动配置完整，`binding` 为空 | 改任何字段、新增配置、切换配置、删除非活动配置 | — |
| **S2 已绑定** | `binding` 非空且 `enabled=true` | 改配置名称、改密钥、改图片地址前缀、新增配置、切换配置（**仅普通锁定**，高风险锁定拒绝，见 R5）、删除非活动配置 | 改五项身份（R4）、改上传行为（R11）、删除绑定配置、高风险锁定下切换配置 |
| **S3 已暂停** | `binding` 非空且 `enabled=false` | 同 S2（含「高风险锁定不能切换」），**外加删除绑定配置**（删除即解绑；若 `binding['no_local_saving']==='true'`，必须先删完其余配置，见 R10） | 改五项身份、改上传行为 |

迁移只有五条边：

| 从 | 事件 | 到 | 条件 |
|---|---|---|---|
| S0 | 保存一份完整配置 | S1 | `Options::is_configured()` 为真 |
| S1 | 第一次成功上传递交 | S2 | `mark_synced()` 回读确认为 `synced`（见 R3） |
| S2 | 再点一次正在使用的那张配置卡片 | S3 | `active_profile_id` 保留，卡片变浅 |
| S3 | 点任意一张配置卡片 | S2 | 配置仍完整（不完整时卡片本身 `disabled`） |
| S3 | 删除绑定配置 | S0 或 S1 | 删除即解绑（见 §6）。普通锁定可留下其余配置（→ S1）；高风险锁定必须清空后删（→ S0，见 R10） |

**S1 → S2 是单向的**：绑定之后没有「解绑但保留配置」的入口，因为那等于给「换个桶试试」开一个后门。要解绑只能走 S3 → 删配置。

**开关只有一个入口：配置卡片本身。** `enabled` 不再是「添加存储配置」卡里的一个复选框——点一张不是当前使用的卡片＝切换并启用，点当前正在使用的那张＝关闭（卡片变浅，`active_profile_id` 保留）。所以 S0 不可能「开着」：没有卡片，就没有可点的东西。这也意味着 S2 ↔ S3 的每一次切换都要经过一次明确的点击，而不是填表时顺手带过去。

**两种锁定形态只差「解绑时其余配置能不能留」**：同一时刻被绑定的只有一份配置，解绑就是把它删掉。普通锁定下，删完绑定配置后剩下的那几份直接回到 S1（它们从未被绑定过）；高风险锁定下，其余配置必须先删光，解绑后落到 S0——因为那些配置指向的桶里没有「本地副本已被删掉」的对象，切过去就是死链（R10）。

## §4 数据模型：`binding`

`s3_options` 新增一个 `binding` 键，不新建表。理由：它是配置的附属属性，必须与 `profiles` 同一个 option 里原子写入；拆表就会有两个真相。

```php
'binding' => array(
    'profile_id'      => 'prof_5233fa6ccfaa',
    'provider'        => 'dogecloud',
    'bucket'          => 'doss-v2-328e5d1039000fe8-1258813047',
    'endpoint'        => 'https://cos.ap-chengdu.myqcloud.com',
    'region'          => 'ap-chengdu',
    'upload_path'     => 'wp-content/uploads',
    'no_local_saving' => 'false',
    'no_thumb'        => 'false',
    'locked_at'       => 1794848642,
    'locked_by'       => 1,
),
```

| 字段 | 用途 |
|---|---|
| `profile_id` | 绑的是哪一行；切换与删除的判定靠它 |
| `provider` / `bucket` / `endpoint` / `region` / `upload_path` | 身份五项，逐段比对就知道「这次保存是不是在换桶」（`Options::IDENTITY_FIELDS`，`src/S3/Options.php:130`）。注意它比附件指纹宽一段，`region` 不进指纹，见 R4 |
| `no_local_saving` | 绑定那一刻的取值，之后以此为准，POST 不再作数 |
| `no_thumb` | 同上：绑定那一刻「是否上传缩略图」的取值，之后不再接受 POST（R11） |
| `locked_at` / `locked_by` | 界面文案与排障；`locked_by` 是当时登录用户 id |

**写入点只有一个**：`Synchronous_Uploader::finalize()`，在 `mark_synced()` 回读确认为 `synced` 之后（`src/S3/Synchronous_Uploader.php:342` 写状态、`:345-352` 回读）、删除本地文件之前（`:378-380`），调用 `Options::lock_binding()`（`:360-374`），且仅在 `binding` 为空时写入。`skipped` / `failed` / `held` 一律不写——「试过但没成」不构成绑定。

**读取入口**（都放 `src/S3/Options.php`，业务代码不直接读 option）：`binding(): ?array`（`:140`）、`is_bound(): bool`（`:162`）、`binding_allows( array $candidate ): bool`（`:174`）、`changed_identity_fields( array $candidate ): string[]`（`:195`，只用来在错误提示里点出改了哪几项）。写入与清除走静态方法 `Options::lock_binding()`（`:269`）与 `Options::clear_binding()`（`:309`）。

**解绑点只有一个**：删除绑定配置（`Profile_Manager::delete_profile()` 里调 `Options::clear_binding()`）。`Uninstaller` 无需单独处理——它整条删 `s3_options`，`binding` 随 option 一起消失。

**相邻的一个标记**：`s3_options['behaviour_locked']`（`'true'` / `'false'`）记「这个站点曾经完成过绑定」。它与 `binding` 同时置位，在配置表被清空时清除；默认 `'false'`，`defaults()`（`src/S3/Options.php:116-117`）与 `Activation` 的硬编码默认值（`src/Activation.php:63-64`）两处都写了。它不参与身份判定，只服务 R11——因为 `binding` 解绑时就被清空了，记不住这件事。

**`space` 不是身份字段**：它只是多吉系列厂商的控制台空间名，用于默认配置名（`Options::default_profile_name()`）与 `Bucket_Label::display()`；真正决定对象落在哪的是 `bucket`，`Client_Factory` 与 `Storage_Adapter` 都不读 `space`。所以 R4 不冻结它，改它不算换桶。

## §5 十九条规则

### R1 默认保留本地附件

表单默认不勾「上传成功后删除本地文件」。这条只是**默认值**，真正的约束是 R3 与 R4——默认值可以被覆盖，绑定不行。

绑定之后这个开关的取值决定了站点的**两种锁定形态**，后面的规则要用到：

| 形态 | `binding['no_local_saving']` | 本地副本 | 解绑时另外的配置 |
|---|---|---|---|
| **普通锁定** | `'false'` | 上传后保留 | 可以留在 S1，切换过去仍然能显示（本地有文件，URL 降级到站点域名） |
| **高风险锁定** | `'true'` | 上传成功后已删除 | 必须**全部删掉**才允许删绑定配置，见 R10 |

落点：`src/Activation.php:58`、`src/S3/Options.php:108`。两处默认值必须同时是 `'false'`。

### R2 勾选高风险选项必须先过一道弹窗

「上传成功后删除本地文件」是唯一一个**当下看不出来、三个月后才致命**的开关。勾选时必须弹窗，把后果说完整，且这次勾选要被服务端复核。

前端：`no_local_saving` 从 `false` 变成 `true` 时调 `admin.ui.confirm()`，取消则把复选框还原为未勾选；同意则同时打上隐藏域 `no_local_saving_ack=1`。

服务端：`save()` 与 `save_behaviour()` 都检查——若提交值由假变真而 `no_local_saving_ack` 不为 `1`，返回 `error=risk_ack`，不写库。判定集中在一个静态方法 `Settings_Saver::risk_ack_missing( string $old_value, string $new_value ): bool`（`src/S3/Settings_Saver.php:188`）：只有 `false → true` 才需要 ack，`true → true`（已勾着再保存）不需要，`true → false`（取消勾选）也不需要。

**弹窗只是礼貌，服务端才是守卫**：隐藏域初值是 `'0'`，只有确认过的这一次提交才置 `'1'`。手工构造或重放的 POST 不带 `1`，落库前会被拒。前端另有一道 submit 守卫——复选框勾着而 ack 仍是 `'0'` 时（浏览器前进/后退会恢复勾选状态，却没有 `change` 事件）拦下提交并重新弹窗。

文案定稿（四段式：后果 → 范围 → 不可逆 → 锁定）：

> 勾选后，新上传的图片及其缩略图只有在全部成功传到云端并回读校验通过后，才会删除服务器上的本地文件；任何一张失败都会保留整组本地文件。只影响本机新上传的附件，从同步中心手动上传历史附件时始终保留本地副本。本地文件删除后本插件无法恢复，只能从云端重新下载；如果云端对象后来被删除或被覆盖，这些附件将永久无法显示。首次成功上传后，本选项和这份存储配置会一起锁定，届时无法再更改。锁定之后如果想重新选择存储服务商或存储桶，唯一的办法是把已保存的存储配置**全部删除**（不能切换、不能改字段），再重新新增一份。

落点：`src/S3/S3_Storage_Page.php:678-690`（`no_local_saving_ack` 隐藏域，初值 `'0'`）、`:722` 与 `:731`（两个复选框）、`:226-234`（`$page_strings` 里的 `riskAckTitle` / `riskAckText` / `riskAckItems` / `riskAckAccept`）、`src/S3/Settings_Saver.php:298-306`（`save()`）与 `:480-491`（`save_behaviour()`）（服务端复核）、`assets/ui/js/pages/storage-connection.js:715-810`（`initRiskAck()`，含 change 与 submit 两道）。

### R3 第一次成功上传递交即绑定

绑定触发点是**提交成功**，不是「配置保存成功」，也不是「测试连接成功」。理由：配置可以随便试，测试连接只证明凭据能用，只有真的把一个对象钉进桶里，才证明这套配置和这个站点的目录结构是对得上的。

判定链：`mark_synced()` 写入后**回读** `Sync_Status::status()` 必须等于 `Sync_Status::SYNCED`（`src/S3/Synchronous_Uploader.php:345-352` 已经在回读），且 `binding` 为空，才写 `binding`。回读失败说明持久化没落地，此时不能锁——否则用户会遇到「锁住了但一份都没传上去」。

两个例外**不绑定**：`$manual`（同步中心手动上传历史附件）与 `$preserve_local`（保留本地副本的重试）。它们本来就保留本地副本、可以重跑，与「锁定」要给的保证正好相反。

落点：`src/S3/Synchronous_Uploader.php:342`（`mark_synced()`）、`:345-352`（回读）、`:360-374`（`Options::lock_binding()`，同时写 `behaviour_locked`）、`:378-380`（删本地）。

### R4 绑定后冻结身份五项

绑定之后，下面五项**任何一个被改动都视为换桶**，服务端直接拒绝（`error=locked`），不是「弹窗提醒后放行」：

| 冻结项 | 为什么 |
|---|---|
| `provider` | 换厂商必然换桶 |
| `bucket` | 换桶本体 |
| `endpoint` | 同一家换个地域也是换桶 |
| `region` | 参与签名，与 endpoint 一起决定对象落在哪 |
| `upload_path` | 改了它，已上传对象全部不在新路径下，URL 立刻死 |

**这五项比附件指纹宽一段，`region` 不在指纹里。** `Synchronous_Uploader::target_hash_for()`（`src/S3/Synchronous_Uploader.php:520-529`）算的是 `v2|provider|bucket|endpoint|upload_path`，**没有 `region`**——因为 URL 由前三段与路径决定，改 `region` 而 endpoint 不变时对象仍在同一处可读。`region` 只有两个真实落点：`src/S3/Client_Factory.php:113`（建客户端时的默认值）与 `src/S3/Delete_Jobs.php:66`（删除任务的比对）。

冻结仍然把它算进去（`Options::IDENTITY_FIELDS`，`src/S3/Options.php:133`）：改 `region` 意味着换了一个签名地域，对象可能落到另一端点，而「指纹没变」会让所有已同步附件误以为 URL 还有效。宁可多拦一段，也不让一次地域迁移静默变成死链。

所以准确的说法是：**冻结比指纹严，指纹比冻结松**。改五项里的任一 `→ error=locked`；改 `region` 之外的其余四项，指纹也一定变。

上传行为（`no_local_saving` 与 `no_thumb`）不在本表里，由 R11 管：它也在同一次成功上传后落锁，但解冻条件不同，而且是「忽略 POST」而不是「报错」。

**不冻结**（改了不影响桶身份）：配置名称、`key` / `secret`（轮换密钥）、`object_acl`、`upload_url_path`（CDN 域名，纯展示）。

实现要点：`save()` 在 `binding` 非空时调 `binding_allows( array $stored ): bool`（`src/S3/Options.php:174`）逐字段 trim 后严格比对，五项里任一不等即 `redirect( saved=0, error=locked, fields=改动的字段 )` 且不写库（`src/S3/Settings_Saver.php:354-373`）；其余字段按上面五个白名单放行。`fields` 只是给人看的提示，判定不看它。

守卫的三个前提缺一不可：`$will_write`（这次真的会写库，草稿不算）、`binding` 非空、`binding['profile_id']` 等于**正在保存的那一份**。改别的配置不受影响——它们从来没有绑定过。

### R5 绑定后仍可切换与新增，但开关只由配置卡片触发

绑定锁的是**桶的身份**与**上传行为**，不是「能不能用别的配置」。所以：

- **新增配置照常**：「添加存储配置」卡随时可以再存一份（换服务商时服务端仍会强制新建，见 `Settings_Saver::save_as_new_for_save()`）。保存一份新配置**不会**把它设成活动配置，也**不会**动 `enabled`——要启用必须去点那张卡片。
- **切换配置**：点另一张卡片＝切换并启用（R6）。绑定期切换不会丢绑定，`binding` 只在删除绑定配置时清除。但**普通锁定与高风险锁定分两种**：普通锁定（`binding['no_local_saving']==='false'`）照常切换——本地副本还在，URL 会降级到站点域名，切过去仍然能显示；高风险锁定（`==='true'`）**拒绝切换**，返回 `error=locked`，因为那些附件的本地副本已经删了，别的桶里没有这些对象，切过去就是死链（R10）。点回绑定自己那张卡片（关闭再打开）不算切换，放行。
- **开关只有卡片一个入口**：「添加存储配置」卡里没有「启用 S3 存储」复选框（1.28.1-beta-7 起移除）。点当前正在使用的卡片＝关闭 S3（卡片变浅，`active_profile_id` 保留）；点别的卡片＝切换并开启。这样「没有配置却开着 S3」在结构上不可能出现。
- **保存连接设置不再有副作用**：`save()` 的 `enabled` 取自库里已有值，活动配置沿用 `active_profile_id`，顶层镜像字段只在被保存的那份就是活动配置时才改写。存一份草稿不会把整站媒体地址挪到没人选的桶上。

**误解要提前挡掉**：绑定后仍然可以新增和切换，所以「已锁定」徽章不能挂在别的配置卡上——它只会挂在身份五项与上传行为那里（R4 / R11 的界面表现）。真正的「换桶」不是切换，而是**改掉当前这份配置的身份字段**，那条路被 R4 封死。

落点：`src/S3/Profile_Manager.php:35` / `:49` / `:62`（`switch_profile()` / `enable_profile()` / `disable()` 共用 `activate()` `:87`）、同文件 `:282-292` 的 `Profile_Manager::switch_refused_by_binding( ?array $binding, string $target_id ): bool`（判定的唯一出处，`activate()` 在 `:117-135` 调它，失败返回 `'locked'`）、`includes/class-s3-storage-module.php`（`wp_ajax_sakura_s3_toggle_profile` 与 `toggle_error_message()` 的 `locked` 文案）、`src/S3/S3_Storage_Page.php`（`state_payload()` `:957`、配置卡按钮 `:292`）、`assets/ui/js/pages/storage-connection.js`（`initProfileToggle()` 与 `applyState()`）。

### R6 关闭总开关＝暂停，不是解绑

`enabled=false`（再点一次当前配置卡片）时绑定仍然有效：配置还在、对象还在、只是 `Upload_URL::restore()` 把图片域名换回站点域名。此时**允许删除绑定配置**（R7），删了才解绑。这样「换桶」的唯一路径是显式的三步，而不是点错一张卡片。

关闭 S3 也是**唯一能走到解绑的入口**——高风险锁定下它同时是「删其余配置」这一步的前置条件（R10）。

### R7 删除判定表

| 配置 | `enabled` | 绑定 | 能否删除 | 结果 |
|---|---|---|---|---|
| 非活动 | 任意 | 不可能是绑定态 | ✅ | 通用确认 → 删除 |
| 活动 | `true` | 无 | ❌ | `error=delete_active`：「当前使用中的配置不能删除。如需更换存储桶，请先点这张卡片关闭 S3 存储。」 |
| 活动 | `true` | 有 | ❌ | `error=delete_bound`：同上，且说明会失去绑定 |
| 活动 | `false` | 有 | 视情况 | **普通锁定**（`binding['no_local_saving']==='false'`）：高风险确认 → 删除并解绑。**高风险锁定**（`==='true'`）：若还有别的配置则拒绝，`error=pending_profiles`，见 R10 |
| 活动 | `false` | 无 | ✅ | 通用确认 → 删除 |

**高风险确认**（「活动 + 已绑定 + 关闭」且放行时）必须包含三件事：

1. 说明解绑后果：删除后这份配置、它的核对记录、计数、删除队列与归档都会消失，站点回到未配置状态，图片地址会还原为站点域名。
2. 说明云端不受影响：**桶里的对象不会跟着删除**，需要自行到控制台处理。
3. 若 `binding['no_local_saving'] === 'true'`，单独列出「这 N 个附件将永久无法显示」（N = 该配置下 `seen_remote=1` 且本地文件已不存在的附件数），并要求**手打配置名称**才能提交。

落点：判定在 `src/S3/Profile_Manager.php:191-247`（`delete_profile()`，先算 `$is_bound_profile` / `$is_active` / `$is_live` 再查表）；界面上的同一套判定在 `src/S3/S3_Storage_Page.php:877-889`（`delete_refusal()`，只负责 `disabled` 与 `title`，**不负责拒绝**）；弹窗文案在 `:907-949`（`delete_confirm()`）；表单属性在 `:325-360`；编排与错误映射在 `includes/class-s3-storage-module.php:195-227`；错误码表在 `src/S3/S3_Storage_Page.php:1096-1103`。

**界面与服务端必须各判一次**：按钮 `disabled` 只是提前告知，真正的拒绝在 `Profile_Manager::delete_profile()` 里，伪造 POST 一样返回同一错误码。两处判定的输入相同（是否绑定 / 是否活动 / `enabled` / `binding['no_local_saving']` / 配置条数），改一处就要改另一处。

### R8 删除配置的连带清理

删除一份配置时必须按顺序做完，任何一步漏掉都会留下孤儿：

| # | 动作 | 漏掉的后果 |
|---|---|---|
| 1 | `unset( $profiles[ $id ] )` | — |
| 2 | `Index_Repository::purge_index( $id, $bucket )`（清 `jobs` / `scans` / `events` 三张表；`index` / `counts` 只在没有别的配置行指向同一桶时才清，见 R19.7） | 同步中心残留幽灵行 |
| 3 | `DELETE FROM sio_s3_deletes WHERE profile_id = ?` | 删除任务找不到 adapter，每天退避重试到 `dead`，日志刷屏 |
| 4 | `unset( $retired_targets[ $id ] )` | 归档配置越积越多，且指向已不存在的 profile |
| 5 | 若删的是绑定配置：`unset( binding )` | 站点永久卡在「已绑定但配置没了」 |
| 6 | 若删的是活动配置：`active_profile_id` 置空、顶层凭据清空、`Upload_URL::restore()` | 顶层 `provider`/`bucket` 指向已删配置，URL 过滤器读不到目标 |

**明确不清**（这三样是刻意的）：

- **云端对象**：插件不替用户删桶。删本地配置不等于删云端数据。
- **附件 post meta**（`_sakura_imgopt_s3_target` / `_sakura_imgopt_s3_objects` / `_sakura_imgopt_s3_synced_at`）：指纹按「厂商|桶|endpoint|路径」算，不认配置行 id（`Synchronous_Uploader::target_hash_for()` `src/S3/Synchronous_Uploader.php:496-505`，旧形态见 `:519-545`）。删掉配置后若用同样参数重建一份，指纹完全一致，已同步附件**不用重传**就能恢复正确 URL。这是保留它们唯一的理由。
- **上传指标行**：走 R9 的保留期，不随配置删除。

`operations` 表不按 profile 分区（它是资源级互斥表），所以不在第 2 步范围内。

**删除只做上面 6 步**：`includes/class-s3-storage-module.php` 的 `delete_profile()` 先算好桶身份（`Bucket_Identity::from_profile()`，**必须在删行之前算**，删完就解析不出来了），再 `Index_Repository::purge_index( $id, $bucket )`（第 2 步），再 `Delete_Jobs::forget_profile()`（第 3 步）；第 1/4/5/6 步都在 `Profile_Manager::delete_profile()` 的同一次 `update_option` 里原子完成。

### R9 上传指标的保留期

`sio_s3_upload_events` 记录每次上传的结果，`profile_id` 只用于建索引，**全仓库没有任何地方按配置查它**——`snapshot()` 是全局 GROUP BY。所以它不会成为「删除配置后的孤儿数据」，问题是它从来不删。

- `Upload_Metrics::prune()`（`src/S3/Upload_Metrics.php:335`）：把 `day` 早于 `KEEP_DAYS` 的行按 `result` 聚合进冻结基线 `sakura_imgopt_s3_upload_metrics`（`legacy()` 已是「冻结基线 + 明细表」模式，`:322-356`），再删行。
- 冻结基线的 `totals` 只增不减，所以「历史总数」永远单调递增，而 `days` 只保留最近 14 天。**顺序不能反**：先把过期行折进基线，再 `DELETE`。反了就会让页面上传总数凭空变小。
- 用 `add_option( Upload_Metrics::PRUNE_LOCK )` 抢锁（`src/S3/Upload_Metrics.php:52` 常量、`:57` 的 300 秒 TTL）：两个请求同时跑到这里时只有一个删行，另一个直接返回 0，避免同一批行被折进基线两次。
- 挂进既有每日 cron `sakura_imgopt_sync_cleanup`：`src/Sync/Scan_Worker.php:181` 现在是 `index->cleanup()` 之后紧跟 `( new Upload_Metrics() )->prune();`。
- 该 cron 已登记在 `src/Deactivation.php`，不需要新增排程；`src/Uninstaller.php:134` 已把 `sakura_imgopt_s3_upload_prune` 加进清理清单。

### R10 高风险锁定：解绑只能「全部删除后重来」

`binding['no_local_saving'] === 'true'` 时，附件在本地的副本已经被删过（R3/R4 的 `should_cleanup()`，`src/S3/Synchronous_Uploader.php:377-387`）。这条规则把「换桶」从「麻烦」升级为「必须推倒重来」：**锁定之后想重新选择存储服务商或存储桶，唯一的办法是把已保存的存储配置全部删除**（不能切换、不能改字段），再重新新增一份。

**唯一允许的路径**：

```text
高风险锁定（S2，no_local_saving=true）
  └─ 再点当前卡片（关闭 S3）                → S3 已暂停
       └─ 依次删除其余所有配置              → 每次都要通用确认（它们不是活动配置）
            └─ 最后删除绑定配置             → 放行条件：profiles 只剩它一份 + binding.no_local_saving='true'
                 └─ 配置表为空              → S0，没有任何配置可切换
                      └─ 新增配置 B、填完、开 S3、第一次上传成功 → S2（绑定 B）
```

判定用三条事实：**要删的是不是绑定配置**、**`binding['no_local_saving']` 的值**、**`profiles` 里还剩几条**。逐格如下：

| 想删的配置 | 是否绑定配置 | `no_local_saving` | 还有别的配置吗 | 结果 |
|---|---|---|---|---|
| 绑定配置 | 是 | `'true'` | 有 | ❌ `error=pending_profiles`：「高风险锁定下不能保留其它配置。请先删除其余 N 份配置（它们指向的桶里没有这些附件），再删除当前配置。」 |
| 绑定配置 | 是 | `'true'` | 无 | ✅ 高风险确认（R7 三项 + 手打配置名）→ 删除并解绑 |
| 绑定配置 | 是 | `'false'` | 任意 | ✅ 按 R7（普通锁定，不限制其它配置） |
| 其它配置 | 否 | — | 任意 | ✅ 通用确认即可（删它们不动 `binding`） |

> 表里「其它配置」在正常情况下都**不是**绑定那份（`binding['profile_id']` 指向的配置唯一）。若历史数据出现 `active_profile_id` 与 `binding['profile_id']` 不一致的畸形状态，先按 R7 的「活动配置」行判定，不要套用本表。

**为什么必须清空**：`no_local_saving='true'` 期间上传的附件，本地文件已经删了，对象只在绑定那个桶里。别的配置指向的桶里没有这些对象，切过去 URL 会走 CDN 却取不到文件（死链），退到站点域名也照样 404（本地同样没有）。所以解绑之前那几份配置留着没有意义，只会让人误以为「还能切过去看一眼」。

**顺序是固定的，反了就卡住**：绑定配置一定是最新一次切换的目标，所以「其余配置」按定义都**不是**活动配置；而 R7 第 1 行允许删除「非活动 + 任意开关状态」的配置，因此这一步**不需要先把当前配置切走，也不需要再动开关**。真正会卡住的只有一种操作顺序——先点绑定配置的删除按钮：它会被 `pending_profiles` 拒掉，提示先删其余的。

**弹窗文案要比普通锁定重**，普通锁定的三条之外再加两条：

1. 明确「这是最后一次机会」：删除后站点回到未配置状态，**已删除本地副本的 N 个附件将永久无法显示**，除非用同样的服务商与桶名重新建一份配置（附件 post meta 仍在，R8「明确不清」）。
2. 明确「不是切换」：这里没有「切到另一份配置继续用」的选项，因为其余配置已经按规则先删掉了。

**界面**：删除按钮的 `title` 与确认框文案要把顺序写死——「高风险锁定：请先点当前配置卡片关闭 S3 存储，删除其余全部配置，再删除当前配置」。绑定配置的删除按钮在「还有别的配置」时 `disabled` 并给出这个 `title`，而不是点下去才报错。

落点：`src/S3/Profile_Manager.php:191-247`（`pending_profiles` 判定，与 `binding` 一起读）、`src/S3/S3_Storage_Page.php:877-889`（`delete_refusal()` 返回 `pending_profiles`，按钮 `disabled` + `title` 文案在 `:325-346`）、`:907-949`（`delete_confirm()` 的五条 items）、`:1096-1103`（错误码表）、`includes/class-s3-storage-module.php:195-227`（错误映射）。

### R11 绑定后「上传行为」整卡冻结

R4 冻结的是**桶的身份**（决定对象落在哪儿）；这一条冻结的是**上传行为**（决定本地副本留不留、子尺寸传不传）。两者在同一次成功上传后一起落锁，但**解冻条件不同**——身份跟 `binding` 走，行为跟「配置表是否为空」走。

冻结的两项：

| 冻结项 | 为什么 |
|---|---|
| `no_local_saving` | 见 R1/R2。绑定后本地副本可能已经删过一批，改它只会让「以后上传的保留、以前删掉的不再回来」，用户会误以为风险解除 |
| `no_thumb` | 决定要不要把 `$metadata['sizes']` 里的子尺寸一起上传（`src/S3/Synchronous_Uploader.php:141`）。绑定后来回切一次，云端就会在时间轴上分成「带尺寸」与「不带尺寸」两段，而缩略图改写开启时缺尺寸就是 404（`src/Thumbnail/Settings.php:973` 已把这两者的冲突列为警告） |

**不冻结**：`upload_concurrency`（云端传输并发数，`src/S3/S3_Storage_Page.php:618-629`）。它只决定传得多快，不决定传哪些、也不影响本地副本；冻结它等于让绑定后的站点永远不能调优，收益为负。若今后要求连它一起冻，把它加进上表即可，其余设计不变。

**冻结与解冻**

- 冻结：第一次成功上传递交（R3），与写 `binding` 同一处、同一时刻。
- 解冻：`profiles` 为空——插件里一份存储配置都不剩。

为什么解冻条件要比身份冻结更严：普通锁定解绑之后配置表里可能还剩 N 份（§6），那一刻 `binding` 已经清空，若按 `binding` 判断就会立刻解冻；用户改完 `no_local_saving` 再让另一份配置完成一次上传，风险就在没人拦的情况下被重新打开。所以行为冻结一旦落下，**只有把配置表清空才解除**。这条终点正好与 R10 高风险锁定要求的 S0 重合，两条规则不冲突；普通锁定下则多一个中间态——配置还在、行为仍冻结。

**需要一个新标记**：`binding` 在解绑时会被清空（R8 第 5 步），记不住「这个站点曾经绑定过」。所以在 `s3_options` 里加 `behaviour_locked`（`'true'` / `'false'`）：

| 字段 | 置 `'true'` | 置 `'false'` |
|---|---|---|
| `behaviour_locked` | 与 `binding` 同一处（R3 的写入点） | 删除配置后 `profiles` 变为空时；`Uninstaller` 随 option 一起消失 |

判定式：`'true' === behaviour_locked && array() !== profiles`。后半句是防御——配置表空了就必须解冻，哪怕标记因手工改库而残留。

**服务端真值**（前端 `disabled` 只是视觉，R4 那条坑在这里同样成立：字段被禁用后浏览器不提交，`isset()` 会读成 `false`）：

- 有 `binding`：两项一律取 `binding['no_local_saving']` / `binding['no_thumb']` 快照，忽略 POST。
- 无 `binding` 但 `behaviour_locked='true'`：取当前 option 里已存的值，忽略 POST。
- 两个入口都要走这条取值：`save()` 的 `src/S3/Settings_Saver.php:298-306` 与 `save_behaviour()` 的 `:480-491`。两处都已经改成先问 `$this->options->behaviour_frozen()`，为真时用 `behaviour_snapshot()` 覆盖两项，否则才读 POST。漏掉任一个，冻结就形同虚设。
- 取值本身有唯一出处：`Options::behaviour_frozen(): bool`（`src/S3/Options.php:228`）与 `Options::behaviour_snapshot(): array{no_thumb,no_local_saving}`（`:241`）。界面、保存、上传三处读的都是它们，不各自判断。`Synchronous_Uploader::finalize()` 删本地前也读快照（`src/S3/Synchronous_Uploader.php:376-379`），否则手工改库就能删掉绑定说好要保留的本地文件。

**界面**

- 「上传行为」卡（`src/S3/S3_Storage_Page.php:633-744`，`anchor='sakura-s3-behaviour'`）里两个复选框 `disabled`，字段上方加一条状态行（`data-sakura-role="behaviour-lock"`，`:720`），文案取 §7 的四段。
- `check_field()` 扩了第 7 个参数 `bool $disabled = false`（`src/S3/S3_Storage_Page.php:824`），输出 `class="check check--stacked is-locked"` 与 `disabled` 属性；没有扩 `id` / `data-*`——需要挂 JS 钩子的场景改用 `Field` 的 `type=custom`（`src/Admin/UI/Field.php:90-100` 原样输出回调返回值，回调自负转义）。样式在 `assets/ui/pages/storage.css:220`（`.behaviour-lock`）与 `:229`（`.is-locked`），复选框的置灰在 `assets/ui/components.css:493` / `:498` / `:502`。
- 「保存设置」按钮保留可用：并发数不冻结，点保存仍会存下并发数，其余两项被服务端忽略。整卡置灰会让用户以为连速度都不能调。

**冻结只封这两个开关，不封任何操作**：

- 切换存储配置（多配置下的换桶路径，§6）不受影响；
- 同步中心的一切动作不受影响：完整核对、增量扫描、单条/批量上传、下载、删除；
- 改配置名称、轮换密钥、改图片地址前缀不受影响（R4 的不冻结清单）；
- 删除配置不受影响（R7/R10 判定表照旧）。

一句话：冻结改的是「上传时删不删本地、传不传子尺寸」，不是「谁能操作」。

落点：`src/S3/S3_Storage_Page.php:633-744`（整卡）、`:676-694`（状态行）、`:696-713`（两个复选框传 `$behaviour_frozen` 作 `disabled`）、`:715-730`（并发数照常可改）、`:824`（`check_field()` 第 7 参）、`:957-1050`（`state_payload()` 里的 `behaviourFrozen`）、`src/S3/Settings_Saver.php:298-306` 与 `:480-491`（真值来源）、`src/S3/Synchronous_Uploader.php:360-379`（同时写 `binding` 与 `behaviour_locked`，并按快照决定删不删本地）、`src/S3/Profile_Manager.php:191-247`（配置表空时由 `Options::clear_binding()` 置 `'false'`）、`src/S3/Options.php:217` / `:228` / `:241`（读取入口）。

### R12 每个 URL 出口都要说出它经过哪条过滤路径

R4 管「桶的身份」，R11 管「上传行为」，这一条管**读出口**：同一个附件 URL 有好几条出站路径，插件只挂在其中两条上，其余由 WordPress 自己拼。不把这张表登记清楚，「换桶 / 删本地 / 不上传子尺寸」的后果就会从没登记的出口漏出去。

| 出口 | 谁生成 | 过插件的 URL 过滤器 |
|---|---|---|
| `wp_get_attachment_url()` | `Storage::revert_unsynced_url()`（`src/S3/Storage.php:145`，优先级 25）、`normalize_root_url()`（同文件 `:167`，优先级 30） | 是 |
| `wp_get_attachment_image_src()` 的主图 `src` | 走 `image_downsize()` → `wp_get_attachment_url()`（`wp-includes/media.php:226`） | 是 |
| 子尺寸的单独 URL | `image_get_intermediate_size()` 补 `url` 时同样调 `wp_get_attachment_url()`（`wp-includes/media.php:867-869`） | 是 |
| **`srcset` 的候选** | `wp_calculate_image_srcset()` 用 `wp_get_upload_dir()['baseurl']` 自拼（`wp-includes/media.php:1501-1502`、`:1592`） | **否** |
| 正文里写死的 `<img src>` / `<img srcset>` | `post_content` 在发布时固化 | **否**（见 §10） |
| REST / sitemap / 主题自行拼的图片 URL | 由调用方决定，插件无从插手 | **否** |

规则本身只有两句：

1. **新增任何「跟随 S3 状态改域名」的出口，必须走 `wp_get_attachment_url()`**，或复制它的两段判定（`should_keep_local()` 加 `confirmed_in_active_bucket()`）。不许在插件里按 `upload_url_path` 自行拼 URL——那等于绕过状态判定。
2. **不经过附件 API 的出口，必须在这张表里有名字。** 有名字＝已知旁路，出问题时知道去哪儿查；没名字＝下次换桶时才会被发现。

**为什么 `srcset` 是这张表里最危险的一行**

候选的基址来自 `wp_get_upload_dir()['baseurl']`，而那个值由 `upload_url_path` 决定（`wp-includes/functions.php:2480`）。生产站的 `upload_url_path` 是 `https://bf.nboke.com/wp-content/uploads`，所以**候选天然指向 CDN，附件过滤器返回什么都不影响它**。

2026-11-17 在生产站实测（附件 316，只读；子尺寸是内存里注入的假条目，没有落库、没有动文件）：

| 注入 | `wp_get_attachment_image_src()` | `wp_calculate_image_srcset()` |
|---|---|---|
| 无 | `https://bf.nboke.com/.../20261117-081227-GJdsJ.webp` | 两个候选都在 `bf.nboke.com` |
| 把附件 URL 过滤器改成返回 `https://www.nboke.com/...` | 主图与子尺寸 URL 都变成 `www.nboke.com` | **两个候选仍在 `bf.nboke.com`** |

同一张图、同一时刻，`src` 与子尺寸都降到本地了，`srcset` 一个字没变。这就是旁路。

**它现在为什么不报错**

三道提前退出把它挡住了。生产 132 张图的 `sizes` 全为空（`sakura_imgopt_disabled_sizes` 七项全禁），第一道就返回：

- `sizes` 为空 → `return false`（`wp-includes/media.php:1462`）。
- 候选不足 2 个 → `return false`（同文件 `:1635`）。注入一个与主图**长宽比不同**的子尺寸会走到这里：看起来「没事」，其实是候选被 `wp_image_matches_ratio` 丢掉了（`:1589`）。要复现必须注入同长宽比的子尺寸。
- `src_matched` 不成立 → `return false`（`:1570`）：`src` 里必须含「子目录／子尺寸文件名」这一段的同目录同基名。

所以「生产现在没裂图」不等于「这条旁路不存在」。它成立的前提是有人给这个站点加了子尺寸（换主题、改 `sakura_imgopt_disabled_sizes`、换插件版本），从那一刻起老附件开始输出指向 CDN 的候选。

**与 R11 的交界**

`no_thumb='true'` 时子尺寸**只留在本地、永远不上传，也不会被本地清理删掉**：它们不进 `manifest()`（`src/S3/Synchronous_Uploader.php:141` 只在 `no_thumb` 不为 `'true'` 时才收集 `$metadata['sizes']`），而 `cleanup_local()`（同文件 `:395`）只删传进来的 `$manifest`。但 `_wp_attachment_metadata['sizes']` 里仍然记着它们，于是 `srcset` 会为一组**云端根本不存在**的文件生成候选 → 404。`src/Thumbnail/Settings.php:973` 已经把这条冲突列为 `no_thumb` 警告，那是目前唯一的防线。

**已实现的处理方式**

WordPress 给了整组候选的过滤器：`$sources = apply_filters( 'wp_calculate_image_srcset', $sources, $size_array, $image_src, $image_meta, $attachment_id )`（`wp-includes/media.php:1632`）。插件挂在它上面（`src/S3/Storage.php:174`，优先级 20、5 个参数），做法是**丢弃候选，不换域名**（理由见 §10「`srcset` 候选改走本地域名」）：

1. `no_thumb='true'` → 直接返回 `array()`。子尺寸永不上传，候选必然是 404（见上面「与 R11 的交界」）。
2. 这个附件没有 `_sakura_imgopt_s3_objects` 记录 → 原样返回，沿用 WordPress 自己的规则，不替它做决定。
3. `should_keep_local( $status, $has, $match )` 为假（即插件**信任**桶里有这组对象）→ 原样返回。桶是唯一真相时不该由插件来掩盖 404。
4. 否则（插件不信任桶）逐个候选过 `key_candidates()`，能对上 `desired_keys()` 的候选**全部丢弃**——它们是一组没被验证过的声明。

丢光候选时 WordPress 在 `wp-includes/media.php:1635` 返回 `false`，页面退化成普通 `src` 属性，而 `src` 已经走过 `wp_get_attachment_url` 那两个过滤器。这是可接受的降级：**宁可少一组响应式候选，也不输出一组可能 404 的地址**。

落点：`src/S3/Storage.php:174`（注册）、`:725-767`（`filter_srcset()`）、`:790-818`（`drop_missing_candidates()`，比对用既有的 `:935` `key_candidates()`）、`tests/S3LifecycleTest.php`（R12 的九个用例：`no_thumb` 全丢、已确认保留、`failed` 丢自有候选、换桶无索引证据丢、索引确认则保留、别人的文件不丢、无记录保留、`attachment_id=0` 原样、Feature 关闭时零查询）。

### R13 下载回来的附件必须当场回写同步状态

R3 规定「第一次成功上传递交即绑定」，这一条规定它的孪生兄弟：**从桶里读回来的对象，同样是「这个附件在活动桶里」的证据**，必须当场写成同一套 meta。漏掉它，附件会停在 `pending`，URL 出口就把一张确实在桶里的图降级成站点域名。

**三个动作叠起来造成的黑洞**：

1. 「同步中心 → 下载到媒体库」只做三件事：下文件（`Storage_Adapter::download_file()`）、写对账索引（`Index_Repository::record_downloaded()`，`src/Sync/Index_Repository.php:624`）、建媒体库记录（`Attachment_Adopter::adopt()`，`src/Sync/Attachment_Adopter.php:135-191`）。
2. `adopt()` 内部走 `wp_insert_attachment()`，触发 `add_attachment`，被 `Storage::queue_attachment()`（`src/S3/Storage.php:150` 注册、`:191` 执行）标成 `pending`。
3. 同一个 `adopt()` 又挂了 `sakura_imgopt_s3_skip_finalize`（`src/Sync/Attachment_Adopter.php:157`），于是 `Synchronous_Uploader::finalize()` 在 `src/S3/Synchronous_Uploader.php:196-200` 直接返回 `skipped`——不上传，也不 `mark_synced()`。

结果：附件 `_sakura_imgopt_s3_status` 永远停在 `pending`，`_sakura_imgopt_s3_target` 与 `_sakura_imgopt_s3_objects` 全空。URL 侧于是这样判：`revert_unsynced_url()` 只在 `SYNCED === $status && $has` 时才算指纹（`src/S3/Storage.php:692-695`），`pending` 走进 `should_keep_local( 'pending', true, null )`，在 `:964-972` 落到最后一行 `return true` → `map_cdn_to_local()` 把 CDN 基址换成本地 → 页面显示主域名。

**规则**：

1. **凡是「确认对象就在活动桶里」的动作，都要写 `synced` 那一套 meta**，与上传路径完全一致：`_sakura_imgopt_s3_status`、`_sakura_imgopt_s3_target`（`Synchronous_Uploader::target_hash_for( 活动配置 )`）、`_sakura_imgopt_s3_objects`、`_sakura_imgopt_s3_object_versions`、`_sakura_imgopt_s3_synced_at`。
2. **写 meta 只有一个出处**：`Action_Worker::write_back()`（`src/Sync/Action_Worker.php:209-243`）。行内路径与后台队列路径共用它，不许各写一套——两套必然分叉，分叉的表现就是同一个动作在媒体库里留下两种状态。
3. **不许无条件标 `synced`**：`write_back()` 只在「`desired_keys()` 全都已在 `objects` 里」（`:226-228` 的差集判空）时才 `mark_synced()`。只恢复了一个子尺寸的附件仍应停在 `pending`，否则桶里缺主文件也会被宣称同步。
4. **`download` 与 `upload` 同等对待**：`write_back()` 的准入从 `'upload' === $action` 放宽为 `upload|download`（`src/Sync/Action_Worker.php:218-223`）。`delete` 走 `mark_object_removed()` 的分支不变。

**落点**：`src/S3/Sync_Actions.php:70-107`（`download()` 成功分支：先 `record_downloaded()` 写索引，再 `adopt()`，用 adopt 的返回值当 `attachment_id`，拿不到时回落 `Storage_Adapter::attachment_id_for_key()`）、`src/S3/Sync_Actions.php:123-143`（`mark_downloaded()` 把 `write_back()` 包一层）、`src/Sync/Action_Worker.php:218-223`（准入放宽）。批量下载（`src/S3/Sync_Center_Module.php:1291-1335` 的 `download_keys()`）与后台队列（`src/Sync/Action_Worker.php:147`）都调同一个 `Sync_Actions::download()`，因此只改一处、两条路一起修好。

**未覆盖（明确记下）**：「同步中心 → 核对媒体库」的 `adopt_missing()`（`src/S3/Sync_Center_Module.php:1185`）同样只 adopt、不回写。它证明的是「本地有这个文件」，不是「刚刚从桶里读回了它」，所以不能照抄 `download` 的结论；是否要按索引行自己的 `status` 在那里补写，等真实站点出现「核对完媒体库、URL 却掉了」再定。

**为什么不能指望「下次扫描自己好」**：扫描（`Scan_Service` → `Index_Repository::reconcile()`）只写对账索引，附件 meta 没有「从索引反向同步」的通道；`confirmed_in_active_bucket()` 会顺手 `retarget()` 纠正指纹（`src/S3/Storage.php:856-859`），但它的调用点全都包在 `SYNCED === $status` 里——`pending` 的附件永远轮不到。所以这条必须在下载当场写，事后补不回来。

生产现场（2026-11-17，同一配置、同一个桶）：上传进来的那张 `status=synced` + 缤纷云指纹 → URL 是 `bf.nboke.com`；下载回来的那张 `status=pending` + 无指纹 → URL 是 `www.nboke.com`。这就是这条规则存在的理由。

### R14 下载回来的附件还要补上用户文件空间那本账

R13 管附件 meta，这一条管**另一本完全独立的账**：附件归谁、占多少字节。两本账都没有人替下载路径写的时候，同一张图会同时表现成「URL 掉了」与「媒体库里没主」。R13 只修好了前者。

**为什么 `Attachment_Adopter` 跳过账本是对的**：它在 `:152-154` 挂 `sufm_skip_attachment_adoption`（注释原话：文件从桶里恢复回来的是文章附件，不是文件空间上传，别记进用户配额账本）。抑制本身没错——`add_attachment` 触发的那一刻 `post_author` 还没写、文件还在落盘，那时候采纳会记成零字节或记错人。**错的是抑制之后没有任何人补**：下载是一次明确的管理员动作，文件就在本机、作者就在 `post_author` 里，此时补账本的每个前提都成立。

**规则**：

1. **凡是「把对象落成本地附件」的动作，都要当场补账本**，与媒体库上传路径口径一致：建 `sufm_files` 行（`source=media`、`charged_bytes` 按磁盘真实占用、`manifest_version` 与 artifacts 由 `Sync_Service` 写）、再把 `charged_bytes` 记进 `sufm_usage.used_bytes`。
2. **补账本只有一个出处**：`Media_Adoption::adopt()`（`src/UserFiles/Services/Media_Adoption.php:77-105`）。媒体库删除守卫与下载路径共用它，不许各写一套——两套必然分叉，分叉的表现就是同一张图在两个页面上占的字节数不同。
3. **必须幂等**：入口第一件事是 `Files::get_by_attachment()`，**有行就直接返回 `charged_bytes`、不再计费**。下载可以被重复触发（重试、批量、队列），无幂等就是重复扣配额。
4. **没有作者就不进账本**：`post_author` 为 0、或该用户已不存在，`Sync_Service::adopt()` 会返回 `false`，此时不写行也不扣费。宁可留在「未分配媒体」等人来「指定归属」，也不要挂到一个已经不存在的用户身上。
5. **计入配额是期望行为，不是副作用**：从桶里下回来的图占的是本站磁盘，理应占该管理员的配额。以当前 WordPress 数据库为准——哪份文件属于谁，库里写得清清楚楚，下载只是把当初遗留在云端的资源收回来（用户 2026-11-18 的裁定）。

**落点**：`src/UserFiles/Services/Media_Adoption.php:77-105`（`adopt()`）、`src/S3/Sync_Actions.php:144`（`mark_downloaded()` 末尾调 `charge_owner()`）、`:164-172`（`charge_owner()`，用 `class_exists` 守卫，保持 S3 模块对 UserFiles 的单向可选依赖）、`src/UserFiles/Media/Media_Hooks.php:999-1016`（`adopt_unmanaged()` 改为复用同一服务）。三条下载路径（单条、批量 `download_keys()`、后台队列）都汇聚在 `mark_downloaded()`，因此只改一处。

**为什么不能靠 `adopt_owner_backlog()` 兜底**：它确实会在该用户「下次上传任意文件」时把这类附件补进来（`src/UserFiles/Media/Media_Hooks.php:899` 触发、`:1028-1054` 的 `LEFT JOIN`），但那是**下一次上传**才发生的事，中间这段时间媒体库一直显示「未分配媒体」、配额也一直是少的。下载当场补，才不用等一个可能永远不来的时机。

生产现场（2026-11-17，附件 321 = `20261117-081224-EJ2zY.webp`）：下载回来之后 `sufm_files` 无行、媒体库列表显示「未分配媒体 / 来源：WordPress 原库 / 所有者：—」，而管理员 sakura 名下的磁盘合计比 `sufm_usage.used_bytes` 正好多 192994 字节——就是它。这就是这条规则存在的理由。

### R15 「自动」方式是静态能力推断，不是联网测试

缩略图改写要拼出一种 URL 语法（命名样式 / 宽高参数 / 不处理）。决定用哪一种的，是**这家厂商支持哪种写法**——这是 `Provider_Registry` 里的一张静态表，不是桶的运行状态。R15 规定：`provider_mode='auto'` 时只查这张表，不发任何网络请求。

**规则**：

1. **auto 只做集合判定**：`Provider_Registry::supports( $provider, 'style' )` 与 `supports( $provider, 'params' )`（`src/Thumbnail/Provider_Registry.php:53-57`）。表里没有这家厂商 → 两个都返回 false，自然落到 `none`。
2. **降级顺序固定**：命名样式（厂商支持 style **且** `style_map` 非空）→ 宽高参数（厂商支持 params **或** 配了自定义模板）→ `none`。前一步不成立才看下一步，不许跳级。
3. **插件里不再有任何联网的语法测试**：`src/Thumbnail/Probe.php`、`src/Thumbnail/Provider_Status.php`、页面上的「连接测试」卡、`admin_post_sakura_thumb_probe`、`wp sakura-thumb probe` 命令、`tests/ThumbnailProbeInvalidationTest.php` 全部删除（`1.28.2-beta-4`）。要判断配置能不能用，用存储页的「测试连接」（那是另一件事，走 `Connection_Tester`）。
4. **升级要清掉旧结论**：`register_settings()` 开头一次性 `delete_option( 'sakura_imgopt_thumb_probe' )`（`includes/class-thumbnail-optimizer-module.php:260-264`）。留着它就是留一个没人读、但会被人误以为还在生效的旧账。
5. **配置里显式选过的值不许被 auto 覆盖**：`none` / `style` / `params` / `native` 四个显式值原样生效，`style` 与 `params` 在厂商不支持时降级成 `none`（显式选择不猜）。只有 `auto` 走上面第 2 条的推断。

**落点**：`src/Thumbnail/Settings.php:865-905`（`resolve_mode()`，三参签名 `( array $opt, string $provider, string $host )`）、`:849-851`（`effective_mode()` 直接转调它，不再读探测结果）、`:914-935`（`conflicts()` 去掉 `$probe` 参数，内部同样调三参 `resolve_mode()`）、`src/Thumbnail/Provider_Registry.php:36-45`（`NATIVE` 表，目前只有 `bitiful` 与 `dogecloud`，两者都是 `array( 'style', 'params' )`）、`src/Thumbnail/CLI.php:22-40`（`status` 不再打印探测结论）、`src/Admin/Layout.php:118-130`（布局里没有 `probe` 卡）。

**为什么测试不是「更保险」**：它测的是「桶里那张样图现在还 HTTP 200 吗」，而不是「这家厂商支持哪种语法」。样本图挑的是已同步附件（`Probe::sample()` 优先 `SYNCED`），刚换桶时那批附件还没落盘，取到的样本在新桶里不存在 → HEAD 拿到 404 → 明明配置正确却报「无法访问」。生产 2026-11-17 就是这样：切到缤纷云之后点「立即测试」提示 404，用户以为是连接坏了，几分钟后再点又 ok。更根本的是**结论会过期**：测试通过后把 `mode` 存进 option，之后换桶、换商、换域名它都不知道，也没有任何东西会让它失效。

生产现场（2026-11-18）：活动配置是 `dogecloud` / `doge.nboke.com`，`style_map` 四项都填了。旧代码下 `effective_mode()` 返回 `none`（改写开关是开的，但什么都不做）；新代码返回 `style`。这是 R15 带来的**唯一行为变化**：从「静默不生效」变成「按厂商能力真的改写」。

### R16 切换存储目标必须关掉缩略图改写总开关

缩略图改写的输出，一半由存储配置决定：命名样式属于某一家厂商，图片域名来自 `upload_url_path`，自定义模板里也可能写死了桶域名。存储目标一换，改写继续开着就是在**按旧桶的样子拼新桶的 URL**——轻则全部回落（因为域名不匹配，改写被跳过），重则拼出一批指向旧桶的地址。所以 R16 规定：存储目标变化时，把缩略图改写的总开关关掉，由用户到缩略图页自己重新决定。

**规则**：

1. **判定只看会改变输出目标的字段**：`provider` / `bucket` / `space` / `region` / `endpoint` / `upload_path` / `upload_url_path` / `active_profile_id`（`storage_target_changed()`，`includes/class-thumbnail-optimizer-module.php:340-348`）。轮换 `key` / `secret`、改 `object_acl`、调 `upload_concurrency` **不算**——它们不改变 URL 长什么样，静默关掉开关只会让用户莫名其妙。
2. **只关 `enabled`，不动其它字段**：`style_map`、`sizes`、`scopes`、`dpr` 是用户的劳动成果，换桶之后照样有效；清空整份 option 等于让他重做一遍。写回走 `get_option` → 改一个键 → `update_option`，不经表单、不复位其它键。
3. **顺带作废旧域名**：`Settings::reset()` 把主题缓存里存着的完整 URL（`post_thumbnail_url_{size}` 一类）一起清掉。只关开关不清缓存，页面上仍会显示一段时间旧域名。
4. **已经关着就不啰嗦**：`enabled` 本来就是空值时只做第 3 步，不写 option、不置提示（否则每次保存无关设置都弹一次）。
5. **提示走弹窗，不走 `admin_notices`**：切换当场由 `S3_Storage_Page::switch_modal_html()` 随 AJAX 返回体一起下发、前端 `openSwitchModal()` 直接打开（`assets/ui/js/pages/storage-connection.js`，R18）；下次进「缩略图优化」页时 `render_page()` 读一次 `sakura_imgopt_thumb_switch_notice` 就删（`includes/class-thumbnail-optimizer-module.php:388-401`），命中则页面用 `UI::modal()` 打开一条紧凑对话框（`includes/views/thumb-settings.php`，id `sakura-thumb-switch-modal`），并显示当前图片域名供核对。**不再用顶部红色 admin notice**：那条 notice 只在保存/切桶之后的下一次后台请求里出现，位置在页面最上方、离被改的控件很远，用户已经从「左下角 toast 说成功」直接跳到「顶部红字说出事了」（2026-11-18 用户反馈）。

**落点**：`includes/class-thumbnail-optimizer-module.php:311-332`（`on_s3_options_changed()`，挂 `update_option_s3_options`，`:58` 注册）、`:340-348`（`storage_target_changed()`）、`:356-374`（`render_conflict_notice()` 的 transient 分支）、`src/Uninstaller.php:330`（transient 清理清单）。切换配置的写入点在 `src/S3/Profile_Manager.php:159`（`update_option( Options::OPTION, $raw, false )`），保存配置在 `src/S3/Settings_Saver.php`，两条路都会触发这个钩子，所以只挂一处即可覆盖全部换目标的方式。

**为什么在存储侧做、不在缩略图页做**：缩略图页根本不知道「存储被换了」，它的渲染只读当前值；没有任何一次请求会「路过」缩略图页。挂 `update_option_s3_options` 是唯一能在换目标那一刻执行的地方。

**为什么不是「自动改写成新桶的样式」**：新桶支持什么、用户想要哪种写法、尺寸映射怎么对应，都是用户的决定；插件替他猜，猜错的表现就是他看不到图却不知道为什么。关掉开关 + 说清楚「请到缩略图优化重新设置」，比一个安静的错判更好。
### R17 有效期短于任务的凭据必须按需续期

有的厂商不发长期密钥：多吉云的 S3 兼容访问要先用永久 Access Key 换一份**两小时有效**的临时凭据（`POST https://api.dogecloud.com/auth/tmp_token.json`，`ttl` 上限 7200 秒，`scopes` 必填），换出来的 `sessionToken` 还要作为安全令牌一起签名。官方文档明确建议缓存复用，接口另有每日调用上限（80000 次/天）；永久 S3 密钥只对存储量或日流量超过 10TB 的客户开放，这条路当前走不通。

问题不在「怎么取」，而在「取一次能撑多久」。客户端对象在 `Client_Factory::$clients`（`src/S3/Client_Factory.php:44` 的静态表、`:79-81` 的命中即复用）与 `Object_Store` 的构造闭包里被整个任务复用——`Storage_Adapter::store()`（`src/S3/Storage_Adapter.php:451-475`）把 client 包进 `static function () use ( $client )`，一次 WP-CLI 批量迁移、一次「扫描 → 上传」都能跑过两小时。第一个小时取到的凭据，第二个小时就过期：所有请求一起 `403 ExpiredToken`，而这批错误过去还会被翻成「签名或临时凭据无效，请检查 Access Key/Secret」——用户改密钥改到天亮也修不好。

**规则**：

1. **凭据以 `callable` 交给 SDK，不在 `make()` 里取一次写死。** `ClientResolver::_apply_credentials()`（`vendor/s3/vendor-prefixed/aws/aws-sdk-php/src/ClientResolver.php:677`）见到 callable 就原样放行、不包 `CredentialProvider`；`Middleware::signer()`（同目录 `Middleware.php:186-190`）于是**每签一次名**调一次它。续期点因此落在签名路径上：用到才检查，不用就不请求，不需要任何计时器。落点 `src/S3/Client_Factory.php:110-131`。
2. **提前量 30 分钟，不是「过期才换」。** `S3_Doge_Cloud::REFRESH_MARGIN = 1800`（`includes/class-s3-doge-cloud.php:26`），判定在 `response()`（`:280`，`:287` 的 `$remaining > self::REFRESH_MARGIN`）。两小时的凭据拖到最后一刻才续，剩下那段窄窗口正好卡在一次批量任务的中途；提前半小时等于把「凭据会不会在任务里失效」挪出关键路径。
3. **两条硬约束，改的时候别丢。** callable **必须返回 Promise**（`Create::promiseFor()` / `Create::rejectionFor()`）——签名中间件拿到就 `.then()`，返回数组会直接 fatal；`Credentials` **必须带 `$expires`**——不传时 SDK 视为永久凭据、永不刷新，而 `CredentialProvider::memoize()` 的 `REFRESH_WINDOW`（`CredentialProvider.php:63`）写死 60 秒、对没有过期时间的凭据还走 `$isConstant = true` 分支，所以**不能改用 memoize() 代替自己的提前量**。`src/S3/Client_Factory.php:104-107` 的注释就是这两条（落点 `:111-131`，`$expires` 在 `:128`）。
4. **续期失败要退避，旧凭据未过期就静默降级。** `RETRY_BACKOFF = 60`（`:37`）与 `arm_backoff()`（`:353`）；`response()` 打接口之前先查退避标记（`:291`），命中且旧凭据还在有效期内就直接返回旧的、不报错（`:293-296`）；真去请求而失败时，只要 `$remaining > 0` 就写一条日志后照旧返回旧凭据（`:306-314`）。**没有这一步，一次接口抖动会被每次签名放大成几百次调用**，两小时窗口足够把每日额度打满。
5. **有用户在等结论的入口必须显式预检。** 惰性刷新把「取凭据」从 `make()` 里移走了，于是「密钥填错了」不会在保存或点「测试连接」时暴露，而要等第一次真实请求才报——那时错误已经是 `S3Exception`，`Connection_Probe` 问不出「Endpoint 通不通、桶在不在」。所以四处用户可感知的入口在 `make()` 之后补一次 `Client_Factory::preflight()`（`src/S3/Client_Factory.php:175`）：`src/S3/Connection_Tester.php:41`、`src/S3/Sync_Center_Module.php:718`、`includes/class-s3-storage-module.php:352`（连接测试）与 `:424`（配置卡探测）。凭据失败单独用 `S3_Credential_Error`（`src/S3/S3_Credential_Error.php`）表达，`Connection_Probe::diagnose()` 优先识别它（`src/S3/Connection_Probe.php:96`），不会被误报成「Endpoint 没有响应」；`Error_Mapper` 把 `ExpiredToken` / `InvalidToken` 从 `sakura_s3_auth_failed` 拆成 `sakura_s3_token_expired`（`src/S3/Error_Mapper.php:37`、`:124-126`），`SignatureDoesNotMatch` 仍是前者。

**为什么用 `wp_remote_post` 而不是 `wp_safe_remote_post`**：多吉云的接口是硬编码的厂商地址，不来自任何用户输入，`wp_safe_remote_*` 的 SSRF 校验在这里换不来安全，却会让整条凭据链在域名解析异常时整体失效。2026-11-18 的事故就是这条路：本机 Clash/mihomo 开 TUN 后 fake-IP 把 `api.dogecloud.com` 解析到 `198.18.0.55`，WordPress 的 `wp_http_validate_url()`（`wp-includes/http.php`，把 `198.18.0.0/15` 标成 benchmarking 网段）在**发包之前**就把请求拒成 `WP_Error`「URL 无效」——签名、密钥、配额全对，却一个字节都没发出去，桶里没有对象，页面只显示「多吉云接口没有返回可解析的响应，请稍后重试。」。因此：`request_credentials()`（`includes/class-s3-doge-cloud.php:156`）用 `wp_remote_post()`（`:177`）；`WP_Error` 的原文存进 `$last_transport_error`，由 `fetch()`（`:324`）拼成「多吉云接口请求失败：%s」写进 `last_error()`，用户才看得到真正原因；只有响应体真的解析不出来时才回落到原来那句「没有返回可解析的响应」。宿主机侧另有双保险：把 `api.dogecloud.com`、`*.myqcloud.com` 加进 mihomo 的 `fake-ip-filter`。

**为什么不是 wp-cron**：cron 只在有 HTTP 请求进来时才被派发，一次 WP-CLI 长任务从头到尾没有 `wp_cron()`，跑到第 90 分钟时没有任何东西会替你换 token；就算派发了，cron 也只能保证「大约在某刻执行」，而真正需要有效凭据的是**签名那一刻**。按需检查与「什么时候用」天然对齐，是唯一不依赖外部调度器的时机。

**为什么不在 `make()` 里重取再换 client**：client 被 `Client_Factory::$clients` 静态缓存，还被 `Object_Store` 的构造闭包捕获；换 client 等于重灌整条链，而 AWS SDK 本来就支持「每次签名现取凭据」，用它比绕开它便宜。

**为什么不再写 JSON 文件**：旧实现把 token 落在 `wp-content/.sakura-s3-cache/dogecloud-token.json`，明文 token 在 Web 根内；现在缓存走 transient（有对象缓存时在 Redis 里），`cleanup_legacy_cache()`（`:59`）只负责删掉遗留文件。

### R18 切桶后同步中心封存，跑完一次完整核对才解锁

同步中心的每一个数字都是**针对某一个桶**算出来的：`nb_sio_sync_index` 的行按 `profile_id` 分区，覆盖率、差异数、体积分布都是从这些行汇总来的。切到另一个桶之后，页面上那套「132 个已同步 / 100% 覆盖」说的是上一个桶，而现在的读写目标换成了另一个地址——数字看着完好，实际一个字节都没在新桶里核对过。更糟的是这些按钮仍然可点：批量删除会把旧索引里的 key 发到新桶去删，批量下载会去新桶取根本不在那里的对象，「刷新差异」会在旧索引上重算出一份看起来正常、实则全错的账。

用户 2026-11-18 从多吉云切到缤纷云时现场就是这样：切换后只有左下角一个 toast 说成功，同步中心照常显示 132 个已同步，没有任何东西提示「这些数字不是这个桶的」。所以 R18 规定：**存储目标一变，同步中心就封存**，唯一的出口是跑一次完整核对。

**规则**：

1. **封存状态落在 `s3_options` 里，不落 transient。** 键名 `reconcile_pending`，值 `array( 'profile_id' => 新配置 id, 'at' => 置位时间戳, 'bucket' => 新桶名, 'from' => 旧配置名 )`，默认 `array()`（`src/S3/Options.php:120`）。放 option 而不是 transient 的理由：这是一条**必须被处理掉**的状态，不是一条提示——transient 会自己过期，过期之后页面就「自动恢复正常」了，而索引并没有重建。读取走 `Options::reconcile_pending()`（`:271`），空数组归一成 `null`，缺键时补 `profile_id`/`at`/`from`/`bucket` 四个默认值（老站升级上来没有这个键，不能因此报错）。
2. **置位必须与「改指向」写在同一次 `update_option` 里。** `Profile_Manager::activate()`（`src/S3/Profile_Manager.php:180-190`）在写库之前算 `$moved = self::target_moved( $previous_target, $raw )`，为真就把 `reconcile_pending` 塞进同一个 `$raw`，随后 `:190` 一次写入。**不许**先写库再补一次 `update_option`：两条写之间有一次后台请求的窗口，那一刻页面看到的是「新桶 + 旧数字」，正是要避免的状态。
3. **判据是「读写目标变了」，不是「配置 id 变了」。** `target_moved()`（`:311-319`）比对 `provider` / `bucket` / `space` / `region` / `endpoint` / `upload_path` 六个字段，trim 后逐一对比。刻意**不算** `upload_url_path` 与 `active_profile_id`：前者只是展示用的图片域名（换 CDN 域名不影响对象在哪），后者是核对行的分区键，两者变化都不代表桶换了。点名切回当前已启用的那张卡（`activate()` 走同一份配置）六个字段全等 → 不置位。
4. **只有 `full` 与 `resume` 完成才解锁，`incremental` 不解锁。** `Scan_Service::finalize()`（`src/Sync/Scan_Service.php:855`）在 `finish_scan()` 与第二次 `summary()` 之后调 `Options::clear_reconcile_pending( $profile )`，条件是 `in_array( (string) $scan->mode, array( 'full', 'resume' ), true )`。`resume` 要算：`Index_Repository::resume_scan()`（`src/Sync/Index_Repository.php:211`）会把 `mode` 改写成 `'resume'`，但那一趟仍然两端全量走一遍，若只认 `full`，「核对中断 → 继续核对跑完」永远解不开闸。`incremental` 不算：它用 `sakura_imgopt_sync_full_at` 作截止时间，只统计上次全量之后的文件（`Scan_Service.php:419-420`），证明不了新桶里有什么。
5. **解锁只认闸门自己的那个 profile。** `clear_reconcile_pending()`（`src/S3/Options.php:296-313`）读出现有 `reconcile_pending`，`$owner` 非空且与传入的 `$profile_id` 不同就直接返回——A 桶置的闸不能被 B 桶的核对解掉。空 owner 或空入参则放行，避免历史上手写过残缺值时永远锁死。
6. **页面分两层：硬冻结与核对闸。** 视图顶部（`includes/views/s3-sync-center.php:88-96`）：`$frozen = $is_configured && ! $storage_enabled`（R6 的「已停用」，行为不变）；`$reconcile_gated = ! $frozen && $is_configured && $storage_enabled && array() !== $reconcile_gate`（R18 新增）；`$locked = $frozen || $reconcile_gated` 供「两个原因都该禁」的控件用。**这两层不合并**：停用是「服务商那边现在不能碰」，闸门是「这个桶还没核对过」，文案和出口都不一样。
7. **闸门期只放行本地动作与「开始完整核对」，其余全禁。** 闸门要拦的是「拿旧桶的数字去动新桶」，所以用 `$locked` 禁用：刷新差异（`s3-sync-center.php:588`）、继续核对（`:590`、`:686`）、重试失败（`:591`）、批量上传/下载/删除（`:796-798`）、所有行内上传/下载/删除（`:876-886`）。**用 `$frozen` 而不是 `$locked` 的是两类**：一类是出口与出口相邻的操作——「开始完整核对」（`:587`、`:681`）与「重新核对（本地 + 云端）」（`:739`）；另一类是**不碰索引行的本地动作**——启用/停用同步记录（`:337`、`:655`）、测试连接（`:656`）、忽略规则保存（`:495`）、补建媒体库记录（`:754`，服务端也放行 `adopt`）。判断标准只有一条：**这个动作会不会按索引里的旧数字去向桶里写或删**。「立即校准」的整块（`:350-360`）在闸门期直接不渲染（`if ( $calibrate_stale && ! $locked )`）——它提示的「30 天未校准」本身就是旧桶的结论，与闸门提示叠在一起只会给两个出口。停用 S3 时（`$frozen`）才全部禁。
8. **服务端也要拦，不能只靠按钮。** 留着一个切桶前的旧标签页，按钮还是可点的。`Sync_Center_Module::guard_reconcile_gate()`（`src/S3/Sync_Center_Module.php:422-433`）在闸门升起时 `wp_send_json_error( …, 409 )`，`code` 为 `sio_reconcile_required`；同步中心里三处：`ajax_resume()`（`:530`）、`ajax_refresh()`（`:563`）、`ajax_action()`（`:806`，`'adopt'` 之外全部拦）。`adopt`（补建媒体库记录）放行：它只碰本地媒体库，不读也不写桶。`ajax_scan()` 不拦——它是出口。**存储模块里还有一处必须单独拦**：`S3_Storage_Module::retry_failed()`（`includes/class-s3-storage-module.php:501-513`，`wp_ajax_sakura_s3_retry`）在同一个 `code` 下返回 409 —— 失败清单属于旧桶，闸门期重试会把对象推进没人扫过的桶、或从那桶里重删；按钮虽然已禁用，切桶前打开的旧标签页仍持有有效 nonce。
9. **闸门期升起的核对必须是完整核对。** `ajax_scan()`（`:447`）原本调 `$this->scanner->start()`，而 `Scan_Service::start( string $profile_id = '', string $mode = 'incremental' )`（`:131`）的默认值是 `incremental`——按钮写着「开始完整核对」，实际跑的是增量。这条老缺陷从 `55cb935`（v1.22.8 首次导入）起就在，R18 之前不影响结果（增量也走全量 remote，只是本地侧靠 `mark_dirs_scanned()` 回填），但它让「跑完核对就解锁」在语义上不成立：**叫全量的按钮必须真的跑全量**。现在显式传 `'full'`。
10. **保存配置表单不许把这个键弄丢。** `Settings_Saver::save()` 是**从零重建** option 数组（`src/S3/Settings_Saver.php:276-292`），任何新键不加进 `keep_reserved_keys()`（`:168-180`）就会在用户保存一次连接设置后消失——闸门会在没跑过核对的情况下自己解开。所以该方法的 `$defaults` 映射里必须有 `'reconcile_pending' => array()`。
11. **切换当场给弹窗，不指望用户自己发现。** 卡片切换成功后，`includes/class-s3-storage-module.php:177-181` 在 AJAX 返回体里带上 `switchModal`（`S3_Storage_Page::switch_modal_html()`，`src/S3/S3_Storage_Page.php:1058-1091` 生成的 `UI::modal_html()` 片段）与 `switched=true`；前端 `openSwitchModal()`（`assets/ui/js/pages/storage-connection.js:587`）把它挂进 `.sakura-admin` 根节点后 `admin.ui.openModal()` 打开，命中时不再弹左下角那条无信息量的 toast（`:646`）。弹窗列两条：缩略图改写已关（R16）、同步中心的数字是上一个桶的、点「开始完整核对」恢复（R18）；上传行为处于冻结态时再补一条（R11）。
12. **文案说清「数字属于上一个桶」，不要只说「请核对」。** 页面顶部的闸门提示（`s3-sync-center.php:321-330`）带上旧配置名与新桶名：「存储目标已从「多吉云」切换到当前配置（桶 bf-xxx），下方的数字还是上一个桶的……」。同一个「冻结」在 R6 与 R18 下含义不同，文案必须让人分得出自己遇到的是哪一种。

**落点**：`src/S3/Options.php:120`（defaults）、`:262-283`（`reconcile_pending()`）、`:296-313`（`clear_reconcile_pending()`）；`src/S3/Profile_Manager.php:180-190`（置位与写库同一次）、`:311-319`（`target_moved()`）、`:199-206`（返回体带 `moved` / `from`）；`src/S3/Settings_Saver.php:173`（`keep_reserved_keys()` 透传）；`src/Sync/Scan_Service.php:855`（解锁）；`src/S3/Sync_Center_Module.php:358-359`（提取变量）、`:414-417`（`reconcile_gate_active()`）、`:422-433`（`guard_reconcile_gate()`）、`:447`（`start( '', 'full' )`）；`includes/views/s3-sync-center.php:88-96`（三层状态）、`:315`（`data-reconcile-gated`）、`:321-330`（闸门提示）、`:585`/`:737`（出口按钮只认 `$frozen`）；`assets/ui/js/pages/storage-sync.js:345-372`（`isReconcileGated()` / `isLocked()` / `isBlocked()`）、`:600`、`:759`、`:960`；`assets/ui/js/pages/storage-connection.js:587-616`（`openSwitchModal()`）、`:646`；`src/S3/S3_Storage_Page.php:1058-1091`（`switch_modal_html()`）；`includes/class-s3-storage-module.php:177-181`（切桶返回体带 `switchModal`）、`:501-513`（`retry_failed()` 闸门拦截）；`assets/ui/components.css:1550-1599`（弹窗里的 `.dialog__list` 与 `.switch-host`）。

**为什么封存而不是清空统计**：把数字清零看起来更「干净」，但它把「这个桶从没核对过」与「这个桶确实什么都没有」变成同一种画面。保留旧数字 + 一条明说「这些数字不是这个桶的」的提示，用户才知道自己面对的是「还没有数据」而不是「数据已经归零」。清空还会丢一份可对照的历史：迁移刚做完时，旧桶的覆盖率正是判断「搬全了没有」的参照。

**为什么不在切换时自动跑一次核对**：切桶这个动作来自一次 AJAX 点击，跑一次完整核对要遍历整桶（`Scan_Service::PAGE = 1000`，分页拉列表，几十秒到几分钟）。把它塞进那个请求只会让卡片一直转圈，失败时还分不清「切换失败」还是「核对失败」。核对本来就该由用户在自己方便的时候点，闸门只负责保证「在它跑完之前不许动」。

**为什么闸门不放行「刷新差异」**：`refresh()` 只是在现有索引上重算汇总（`Scan_Service.php:185`），不列举云端；在闸门期重算出来的仍是一份关于旧桶的账，却会因为「用户手动点过、页面刷新了」而显得可信。放行它等于给闸门开一个看起来无害的旁路。

### R19 桶身份只有一处定义，三档字段不许混用

> 这一条是「规范先行」的产物：R1–R18 各自需要一个「这是不是同一个桶」的判断，于是同一个问题在代码里长出了五套答案，字段各不相同，已经互相打脸（见下表）。R19 不新增功能，它规定**这一件事只能有一个定义**，之后所有判定都从它取。

#### R19.1 现状：五套「桶身份」，字段各不相同

| 用处 | 位置 | 参与字段 | 混用后果（已实测） |
|---|---|---|---|
| 附件指纹 v2（现行） | `src/S3/Synchronous_Uploader.php:520` | provider / bucket / endpoint / upload_path | — |
| 附件指纹 legacy（仍被接受） | `src/S3/Synchronous_Uploader.php:543` | **profile_id** / provider / bucket / endpoint / upload_path | 任何配置行的旧哈希永不过期 |
| 删除队列指纹 | `src/S3/Delete_Jobs.php:61` | provider / bucket / endpoint / **region** | 与上传指纹永不可互比（文档已声明，但没说明「为什么两个都叫 target_hash」） |
| R18 切桶判定 | `src/S3/Profile_Manager.php:311` | provider / bucket / **space** / region / endpoint / upload_path | 只改 `space`（纯展示字段）会误判为换桶，无谓封存同步中心 |
| R4 绑定冻结判定 | `src/S3/Options.php:133` | provider / bucket / endpoint / **region** / upload_path | 只改 `region` 会 `error=locked`，但指纹不变（对象地址没动） |

生产实测（2026-11-18，132 个附件）：`prof_5233fa6ccfaa`（多吉云）与 `prof_9463a17e7884`（缤纷云）各有 132 条 `synced` 索引行，`seen_local=132 / seen_remote=132 / remote_size>0=132`。**真正记录「文件在哪个桶」的数据一直存在且正确**，五套身份只是围着它的五种问法。

#### R19.2 规则：字段分三档，取哪档由判定的目的决定

**A 档 · 寻址字段**（决定「对象在哪个地址」，参与指纹）

```text
provider | bucket | endpoint | upload_path
```

只有这四个字段变了，才算「另一个桶」。指纹（`target_hash_for()`）只认这一档，`hash = sha256( 'v2|' + 四段 )` 的既有算法**保持不变**——改算法会让所有已存指纹作废（post meta、`sio_sync_jobs`、`sio_s3_deletes` 三处）。

**B 档 · 可用性字段**（不影响对象地址，改了仍然连不上/连得上另一处）

```text
region | key | secret | object_acl
```

- `region` 参与签名与 SDK 路由（`src/S3/Client_Factory.php:137`），改错连不上，但对象 URL 不变 → **不参与指纹**，参与 R4 的「连得上吗」（`IDENTITY_FIELDS`）。
- `key` / `secret` 轮换本就允许，从不冻结。
- `object_acl` 只对新上传的对象生效，不回改旧对象。

**C 档 · 展示字段**（纯 UI，任何判定都不许读）

```text
space | upload_url_path | 配置名 name
```

- `space` 是**多吉云控制台里的「存储空间名称」**，真正的桶是 `s3Bucket`（`src/S3/Bucket_Label.php` 类注释明说：`nboke` 与 `doss-v2-328e5d1039000fe8-1258813047` 毫无相似之处）。`space` 在世面上只有三个读者：`Bucket_Label::display()`、`S3_Storage_Page.php:301`、`includes/views/s3-sync-center.php:134`，**全部是渲染**。所以它不参与任何「桶是否变了」的判定。
- `upload_url_path` 是 CDN 域名，换域名不影响对象在哪（R16 已单独处理缩略图开关，不走桶判定）。

#### R19.3 `space` 必须从 R18 的判定里移除（本轮唯一的判定改动）

`Profile_Manager::target_moved()` 去掉 `space`。理由：改 `space` 不移动任何对象，把同步中心封存起来要求用户重跑全量核对，是让用户为一次纯展示改动付出几分钟的扫描。

**保留 region 在 `target_moved()` 里**：改 region 意味着同一个桶换了一条入口，签名与可用性都变，此时封存提示「核对一下」是合理且低成本的。它与 A 档的区别只在于「指纹不会因此失效」，而 R18 的闸门本来就不读指纹。

#### R19.4 一个确认入口：`Bucket_Confirmation`

「这个对象在这个桶里吗」今天有三个答案来源，分散在三处：

| 来源 | 位置 | 谁在用 |
|---|---|---|
| 指纹比对（纯 post meta） | `Synchronous_Uploader::target_matches()` `:578` | 上传跳过 `Synchronous_Uploader.php:226`、队列失效 `Action_Worker.php:102` / `:238` |
| 手指纹 **或** 索引 | `Storage::confirmed_in_active_bucket()` `:844` | URL 走向 `revert_unsynced_url()`、`filter_srcset()` |
| 索引（逐 key 一条 SQL） | `Storage::index_confirms()` `:875` | 上一条的第二级 |

**R19.4.1** 新增 `src/S3/Bucket_Identity.php`：唯一字段定义 + 三档常量 + `hash_for( array $fields ): string`。`Synchronous_Uploader::target_hash_for()` / `target_hashes_for()` 改为委托它，输出保持逐字节不变。

**R19.4.2** 新增 `src/S3/Bucket_Confirmation.php`：唯一确认入口，三个方法 `confirms( int $attachment_id ): bool`、`confirms_key( string $key ): bool`、`confirms_many( array $keys ): array`。内部顺序固定为「指纹 → 索引（批量）→ 否定」，**三处消费者全部改调它**：上传跳过、队列失效、URL 走向。

**R19.4.3** `confirms_many()` 必须批量查询。今天是 `index_has_key()` → `Index_Repository::find()`（`src/Sync/Index_Repository.php:1621`）一个 key 一条 SQL；生产 132 个附件每个 1 个 key 是 20 ms，一旦有 6 个子尺寸就是 792 次 SQL。新增 `Index_Repository::find_many( string $profile_id, array $keys ): array` 用一次 `WHERE profile_id=%s AND object_key_hash IN (UNHEX(…),…)`。

**R19.4.4** 确认结果按 `(桶身份, key)` 进 `wp_cache` 对象缓存（组 `sakura_imgopt_bucket`，TTL 1 小时），**上传成功、删除成功、扫描完成三处主动失效当前桶的分区**。`Storage::$index_confirmed`（`:97`）保留，它只是单请求内存加速。

#### R19.5 渲染路径不许写库

现状：`Storage::confirmed_in_active_bucket()` 在确认命中后调 `Sync_Status::retarget()`（`src/S3/Storage.php:858`），而它挂在 `wp_get_attachment_url`（`:145`）与 `wp_calculate_image_srcset`（`:174`）上。**每浏览一次文章就 `update_post_meta` 一批指纹**——用户观察到的「指纹分布随浏览变化 126/6 → 129/3 → 132/0」就是这一行造成的。

**规则**：写指纹的动作只有两个出处，都在后台：

1. 上传成功 → `Synchronous_Uploader::finalize()` → `mark_synced()`（已有）。
2. **完整核对完成 → `Scan_Service::finalize()` 里的回填**（新增）：对本次扫描中 `status=synced`、且索引确认、且指纹 ≠ 当前桶身份的附件，批量 `retarget()`。这是唯一一处「把已有知识固化成指纹」的批量写入。

渲染路径从此只读：命中索引就放行 URL，但**不再回写**。

#### R19.6 上传跳过与队列失效必须认索引

`Synchronous_Uploader.php:226` 与 `Action_Worker.php:102` / `:238` 目前只调 `target_matches()`（纯指纹），**完全不知道索引的存在**。后果是灾备场景里最伤的一种：

```text
切到备用桶（对象早已预置好）→ 指纹不匹配
  → 点「全量同步」或队列里还有旧任务
  → Uploader 只认指纹 → 判「未确认」→ 132 个对象全部重传
```

**规则**：两处都改调 `Bucket_Confirmation::confirms()`。「这个对象在这个桶里吗」只有一个答案来源，指纹是它的快路径，索引是它的兜底。

> 注意与 `Action_Worker` 的动机区分：队列行上的 `target_hash` 是为了「排队后设置变了就别往新桶写」（H-01），那条判断**必须继续用纯指纹比对**——它问的是「我排队时瞄的是不是现在这个桶」，不是「对象在不在」。R19.6 只改「要不要重传」，不改「能不能执行」。

#### R19.7 灾备：确认知识必须跨配置行

`sync_index` 的唯一键是 `(profile_id, object_key_hash)`（`src/Sync/Schema.php:105`），查询按 `active_profile_id()`。于是「同一桶换一份配置行」「新建一份指向备用桶的配置」都会掉进同一个坑：**指纹能继承，索引不能** → 对象明明在，判「未确认」→ URL 全量降级。

两步走（都已在 `1.28.2-beta-9` 落地，随 `1.28.3` 发布）：

- **过渡（beta-8，无 schema 变更）**：`find_many()` 的 profile 条件从单值改成「所有指向同一桶身份的配置行」集合。生产 4 份配置，集合最多 4 个，配合批量查询开销可忽略。
- **正式（Schema 1.9.0，beta-9）**：`sio_sync_index` 与 `sio_sync_counts` 各增 `target_hash char(64)`，索引唯一键改 `(target_hash, object_key_hash)`、计数表主键改 `(target_hash, status)`，`profile_id` 降级为「最后一次确认它的配置行」（`upsert` 的 `ON DUPLICATE KEY UPDATE` 每次把它刷成最新写入者）。**桶是分区键，配置行只是标签。** 过渡版的「同桶行集合」因此收拢成单值：`find_many()` 的参数从 profile id 列表改成桶身份列表，`Bucket_Confirmation::profiles()` 换成 `buckets()`，返回 `array( $identity )`。

**迁移（`Schema::prepare_bucket_partition()`，在 dbDelta 之前跑）**：

1. 版本 `>= 1.9.0`，或 `SHOW INDEX` 里已经出现 `target_object` → 直接返回（幂等）。
2. 逐个 `ALTER TABLE ... DROP INDEX` 老键：`profile_object`、`status_keyset`、`profile_kind`、`profile_dir`、`profile_key`、`profile_recent`。**dbDelta 只 ADD 不 DROP**，库里多出来的旧索引必须自己删，否则唯一键会同时存在两份约束。
3. `ADD COLUMN target_hash char(64) NOT NULL DEFAULT '' AFTER id`（列还不存在时）。
4. 回填：`SELECT DISTINCT profile_id`，逐行 `Bucket_Identity::from_profile( Options::profile( $id ), $options )->hash()` 后 `UPDATE ... SET target_hash`。**找不到配置行的 profile_id 保留 `''`，不猜桶**——宁可让这些行落进「无主」分区，也不能把它们算到当前活动桶头上。
5. 去重：两份配置行可能指向同一个桶，同一对象于是有两行。`DELETE dup ... INNER JOIN keep ON keep.object_key_hash=dup.object_key_hash AND keep.target_hash=dup.target_hash AND keep.id < dup.id`，留最早那行（第一次扫描写的）。
6. `DROP TABLE IF EXISTS {counts}`——**改主键不能靠 dbDelta**（`ADD PRIMARY KEY` 会报 Multiple primary key defined），计数表本来就是派生数据，dbDelta 之后按 `GROUP BY target_hash,status` 重建。

**清除语义随之改变**（`Index_Repository::purge_index()`）：`jobs` / `scans` / `events` 三张表仍按 `profile_id` 清，`index` / `counts` 只在「这个桶没有别的配置行指向它」时才清（`bucket_shared()`）。两个调用方都要先捕获桶身份再动手：`Settings_Saver::save()` 用**改之前那行**算 `previous_bucket` 传进去，`S3_Storage_Module::delete_profile()` 在 `delete_profile()` 之前算好——删完行就再也解析不出桶了。

#### R19.8 指纹升级为「带出处的确认记录」

`mark_synced()` 写裸字符串（`src/S3/Sync_Status.php:69`），`retarget()` 改写不留痕（`:95`），这正是「标签与事实不符」的根源。改成：

```text
_sakura_imgopt_s3_target          ← 保持字符串，旧代码继续比对（不动）
_sakura_imgopt_s3_target_meta = {
  hash, confirmed_at, confirmed_by: "upload"|"scan", profile_id

```

`synced_at` 保持不刷新（`retarget()` 现在刻意如此：没重传就不该假装刚同步），`confirmed_at` 诚实记录「什么时候确认它在这个桶里」。有了 `target_meta` 之后，legacy 分支（`target_hashes_for()` 按 profile_id 拼哈希）可以一次性批量回填后收掉。

**只有两个写入者**：`mark_synced()`（`confirmed_by: upload`，第三个参数传活动配置行，`Synchronous_Uploader::finalize()` 与 `Action_Worker::write_back()` 各一处）与 `retarget()`（`confirmed_by: scan`，`Scan_Service::backfill_fingerprints()` 一处）。记录由私有方法 `write_target_info()` 生成，因此不可能与 `TARGET_META` 不一致；`mark_synced()` 收到空指纹、以及 `clear()`，都会把记录一并删掉。`confirmation()` 在没有记录时返回 `array()`——空哈希就是「没有」的判据，调用方不必区分「没写过」与「写坏了」。

#### R19.9 R7/R10 的「删除后有多少附件变死链」必须走同一入口

`S3_Storage_Page::lost_local_for()`（`:848`）算的是 v2 指纹，`Sync_Status::lost_local_count()` 用 `hash_equals()` 精确比对。而全仓其他地方接受 legacy 形式。**凡是 legacy 形式存下来的指纹，在这个破坏性确认框里都会被漏掉 → 弹窗报 0，实际有风险。**

改成同一入口：`lost_local_count( Options $options, int $limit = 500 )` 不再收指纹字符串，改为收那个桶的配置快照，逐行用 `Synchronous_Uploader::target_matches()` 判定——全仓接受哪些形式，这个计数就接受哪些形式，新增形式时不会再漏一处。`lost_local_for()` 相应改成 `lost_local_count( new Options( $profile ) )`。

## §6 换桶的唯一路径

普通锁定（`binding['no_local_saving']==='false'`）下，路径是三步：

```text
S2 已绑定（普通锁定：本地副本还在）
  └─ 再点当前卡片（关闭 S3）        → S3 已暂停（图片回站点域名）
       └─ 删除绑定配置             → S0/S1（解绑）
            └─ 新增配置 B 并填完     → S1
                 └─ 点 B 的卡片，第一次上传成功 → S2（绑定 B）
```

高风险锁定（`binding['no_local_saving']==='true'`）下，路径是四步，**中间多一道「删光其余配置」**：

```text
S2 已绑定（高风险锁定：本地副本已删）
  └─ 再点当前卡片（关闭 S3）        → S3 已暂停
       └─ 删除其余全部配置          → 只剩绑定配置
            └─ 删除绑定配置         → S0（配置表为空）
                 └─ 新增配置 B 并填完 → S1 → 点 B 的卡片，第一次上传成功 → S2（绑定 B）
```

两者的区别只在「解绑那一刻配置表里还剩几份」：普通锁定允许剩下 N 份（本地文件还在，切过去仍能显示）；高风险锁定必须剩 0 份，理由见 R10。**想重新选择存储服务商或存储桶，只有这一条路**——改当前配置的身份字段被 R4 拦、删绑定配置被 R7/R10 拦，能动的只有「关闭 S3」和「删配置」。注意「新增一份别的配置再点它」并不是换桶：切换只换用哪份配置，不会迁移任何对象，新桶里没有那些文件（对象要先搬过去，见下文）。

没有第二条路。特别地：**插件自己不做「换桶向导」（预检 → 复制/重传 → 再切）**。跨厂商没有服务端复制能力（`copy_source` 只能表达一个桶 + 一个键，无法携带第二个 endpoint 与第二套凭据），插件内部也没有任何 `CopyObject` 调用点；要服务的就是一个不存在的入口。

**搬对象是插件之外的动作**：本地还留着对象副本（`no_local_saving='false'`，本站就是这种）时走**插件原生上传**——按本节路径换完配置，再用 `wp sakura-s3 migrate` 把本地文件传进新桶；本地已经没有副本时，先用同步中心的「下载到媒体库」（R13/R14）把文件取回本地，再走同一条路。**OpenList 只作人工搬桶工具**（建两个挂载、复制对象、删挂载，见 [08](08-OpenList迁移通道.md) §7），插件不调用它、也不存它的凭据；它不校验内容，直搬过去的目标桶还会污染同步索引（08 §7.1 的警告），只在「本地没有副本且不想下载回来」时才用。顺序不变：**对象先进新桶，再删旧配置、新增配置、开 S3、跑完整核对**；搬对象要在关闭 S3 之后（源桶不再增长）、删除旧配置之前（源桶还读得到）完成。

目标桶怎么建（公有读、`upload_path` 不变、关版本控制…）、目标已有部分对象怎么迁（`merge` / `skip_existing` / `overwrite` 的真实语义）、三条路线的代价与收尾顺序，见 08 §7.2–§7.6。

> **高风险锁定下的迁移要多绕一步。** R10 要求删绑定配置时配置表里只剩它，所以「搬完对象、切到目标配置」这条路走不通——目标配置本身也是「其余的配置」，得先删掉它才能删源配置。真实顺序是：**搬完 → 删光全部配置（含目标配置）→ 重新新增目标配置 → 开 S3 → 跑完整核对**。重新新增同参数配置不会丢东西：桶里对象还在，附件 post meta 里的指纹按「厂商|桶|endpoint|路径」算（`src/S3/Synchronous_Uploader.php:496-505`），同参数重建后指纹一致，URL 立刻走新桶域名，**不需要再传一遍**。

**R11 的冻结与这条路径互不干扰**：冻结的是上传行为（`no_thumb` / `no_local_saving`），上面每一步都不读它——关 S3、删配置、新增配置、点卡片启用、跑完整核对照常可做。唯一的区别是换桶之后那两个开关仍然不能改，它们本来就是绑定时定下的。

## §7 上线策略：不回溯

升级到本规范后，`binding` 为空。**已有的 130 个已同步附件不会触发锁定**——它们只是历史，不构成「现在这套配置被验证过」。

锁定从**新版本第一次成功上传递交**开始。理由：老站的历史状态无法反推（不知道当初有没有勾过「删除本地文件」），回溯锁定会把一批配置焊死在一个可能已经缺本地文件的桶上，那比不锁更糟。

代价是升级后有窗口期可以自由换桶。为此在「上传行为」卡下方加一行状态条：

- 未绑定：「这份配置还没有成功上传过。完成第一次上传后，服务商、存储桶、服务地址与『上传成功后删除本地文件』将被锁定。」
- 已绑定（普通锁定）：「2026-11-17 10:12 起已锁定。如需更换存储桶，请先点当前配置卡片关闭 S3 存储，再删除它。」
- 已绑定（高风险锁定，`binding['no_local_saving']='true'`）：「2026-11-17 10:12 起已锁定，且已开启『上传成功后删除本地文件』。如需更换存储服务商或存储桶，只能先点当前配置卡片关闭 S3 存储，删除其余全部存储配置，再删除当前配置，然后重新新增——本地副本已不在，没有别的路可走。」
- 上传行为（上面前三条都适用）：「不上传 WordPress 生成的缩略图」与「上传成功后删除本地文件」已随绑定一起固定，只有把存储配置全部删除之后才能重新选择。

## §9 验收清单

服务端：

- **V1** S1 状态勾选高风险但无 `ack` → `error=risk_ack`，`s3_options` 未变。
- **V2** S1 状态带 `ack` 勾选 → 保存成功，`no_local_saving='true'`。
- **V3** 绑定后提交改动 `bucket` 的 POST → `error=locked`，库未变（伪造 POST 也要拦住）。
- **V4** 绑定后带着 `save_as_new=1` **改绑定那份的身份五项** → 新建一份配置（新 `profile_id`），绑定那份原样不动，`binding` 不变。
  > 这一条原先写「`save_as_new=1` → `error=locked`」，与 R5「新增配置照常」矛盾。R4 的守卫只拦「正在保存的那一份就是绑定那份」，另存为新配置产生的是另一个 id，绑定那一行根本没被改，所以放行是对的（`src/S3/Settings_Saver.php:354-373` 的 `$binding['profile_id'] === $profile_id` 条件）。要真正改掉绑定那份的身份，唯一的动作是直接编辑它——那条路仍然返回 `error=locked`（V3）。
- **V5** 绑定后 `switch_profile()` 切到另一份配置：**普通锁定（`binding['no_local_saving']='false'`）→ 成功**，`binding` 不变、配置卡换人；**高风险锁定（`='true'`）→ `'locked'`**，库未变。切回绑定自己那张卡片（关闭再打开）两种形态都必须放行。
  > 这一条原先只写「→ `'locked'`」，与 R5「切换配置照常」矛盾。2026-11-17 定为：**普通锁定允许切换、高风险锁定拒绝**——因为高风险锁定下本地副本已删，切过去就是死链（R10 的理由），而普通锁定下 URL 会降级到站点域名，切过去仍然能显示。代码在 `Profile_Manager::switch_refused_by_binding()`。
  > 已验证：`tests/S3LifecycleTest.php` 与 `tests/ProfileManagerTest.php` 的切换用例。
- **V6** S2 删除绑定配置 → `error=delete_bound`。
- **V7** S3 删除绑定配置 → 成功，`binding` 清空，`profiles` 少一条，`purge_index` 生效。
- **V8** 删除后 `sio_s3_deletes` 该 `profile_id` 行数 = 0，`retired_targets` 无该键。

## §10 明确不做

| 不做 | 原因 |
|---|---|
| 插件内的桶到桶直传 / 换桶向导 | 跨厂商无服务端复制；同厂商的 `copy()` 也只在 SDK 里存在，插件没有调用点。换桶仍是 §6 这一条路径；本地有副本时搬对象用插件原生上传（`wp sakura-s3 migrate`），OpenList 只作人工工具（[08](08-OpenList迁移通道.md) §11） |
| 插件内迁移通道 / 迁移卡 | 见 §6 与 [08](08-OpenList迁移通道.md) §11：唯一的**内容**校验入口 `Verify_Service` 只处理「本地还有副本」的行（`src/Sync/Verify_Service.php:218-220`），而真正需要搬桶的恰恰是本地没副本的场景；OpenList 预填目标桶又会让索引把对象判成已同步（对账只比大小，`src/Sync/Index_Repository.php:999-1007`），之后 `wp sakura-s3 migrate` 永不重传、Content-Type 与 ACL 错误无人修。这类工具市面已有更专业的实现 |
| 旧桶孤儿清点 | 需要另一套「列出桶内全部对象并与索引比对」的能力，超出生命周期范围 |
| 改写文章正文里写死的旧域名 | `post_content` 里的 `<img>` 是发布时固化的，与附件 URL 过滤器无关，属于另一个课题 |
| 尺寸级 URL 降级 | `wp_get_attachment_url` 只返回一个基础 URL，做不了「主图走 CDN、缺的尺寸走本地」。**注意这条不是 `srcset` 旁路的理由**：旁路已由 R12 挂上 `wp_calculate_image_srcset`（`src/S3/Storage.php:174`）处理——处理方式是丢弃候选，不是降级到本地 |
| `srcset` 候选改走本地域名 | 候选换成另一个域名会让「本浏览器看到的地址」与「云端实际托管的位置」长期不一致，换桶时又全部失效；正确做法是逐个候选确认对象是否在活动桶，不在就丢弃（R12） |
| 解绑但保留配置 | 等于给换桶开后门，与 R3 的设计意图相反 |
| 「核对媒体库」（`adopt_missing()`）顺手把附件标成 `synced` | 它证明的是「本地有这个文件」，不是「刚刚从桶里读回了它」。本地有文件却不在桶里的附件，标了 `synced` 就是反向的假账（R13 只管下载路径）。真要补，得先按索引行自己的 `status` 逐行判，那是另一条规则 |
| 高风险锁定下「先在原地换商再试」 | 见 R10：`no_local_saving='true'` 时改身份被 R4 拦，唯一出路是删光全部配置重来；给一条「这次例外」的通道等于把锁定作废 |
| 把 `no_local_saving` 从 `true` 改回 `false` | 本地文件已经删了，改回 `false` 只是让**之后**新上传的附件保留本地，对已删的那批毫无帮助，反而会让人以为「风险解除」 |
| 让下载回来的附件留在「未分配媒体」 | 下载是管理员明确动作，文件就落在本机、作者就在 `post_author` 里，没有任何理由让它游离在账本外。用户 2026-11-18 明确：下载回来的图计入该管理员的配额是期望行为（R14）。仍留在「未分配媒体」的只有一种：作者为空或已不存在 |
| 去掉 `Attachment_Adopter` 的 `sufm_skip_attachment_adoption` 过滤器 | 那个抑制是对的：`add_attachment` 触发时 `post_author` 还没写、文件还在落盘，那时候采纳会记成零字节或记错人。正确的做法是下载完成后显式补一次（R14），而不是让钩子在错误的时机抢着记 |
| 给「核对媒体库」（`adopt_missing()`）也补账本 | 它采纳的是**本地已有但从未入账**的文件，与「刚从桶里读回来」不是同一件事；那批文件的归属仍应走「指定归属」或 `adopt_owner_backlog()`，让管理员显式决定。R14 只管下载路径 |
| 恢复联网能力探测（`Probe`） | 它测的是「桶里那张样图现在还能不能取到」，而 `auto` 要回答的是「这家厂商支持哪种 URL 语法」——后者是 `Provider_Registry` 里的一张静态表，与桶的运行状态无关。真要确认连通性，用存储连接页的「测试连接」（`Connection_Tester`）。探测还有两个结构性毛病：样图优先挑已同步附件，刚换桶时那张图可能还没在新桶里，于是配置正确却报 404；结论一旦写进 option 就再也不会自己失效（R15） |
| 换桶后自动把 `style_map` 改写成新厂商的样式名 | 新桶支持什么、尺寸怎么映射、用命名样式还是宽高参数，都是用户的决定。插件替他猜，猜错的表现是图片不显示且页面上一片安静——比关掉开关让他重新设置更糟（R16） |
| 换桶后保留缩略图开关并「静默回落」到不处理 | 静默回落等于开关在、实际什么都没做，用户会以为改写生效了。宁可关掉并明说「请重新设置」，这至少是一个他能看见、能处理的状态（R16） |
| 冻结期间提供「临时的例外修改」 | 一次例外等于没有冻结：改完的取值无法与已上传的对象对齐，也没有审计点能证明「只改过这一次」 |
| 换桶后给一条「跳过核对直接解锁」的出口 | 闸门要防的正是「拿旧桶的数字去操作新桶」。跳过核对等于让批量删除按旧索引的 key 去新桶里删、让刷新差异把旧账重算成一份看起来可信的账。唯一的出口就是那个真跑一遍的按钮（R18） |
| 闸门期把同步中心的数字清零 | 清零会让「这个桶从没核对过」和「这个桶确实什么都没有」变成同一幅画面；保留旧数字并明说「这些数字不是这个桶的」，用户才知道自己面对的是「还没有数据」。而且旧桶的覆盖率正是迁移刚做完时判断「搬全了没有」的参照（R18） |
| 切桶时同步触发一次自动核对 | 核对要遍历整桶（分页拉列表，几十秒到几分钟），塞进切桶那个 AJAX 只会让卡片一直转圈，失败时还分不清「切换失败」还是「核对失败」。切桶是用户的决定，核对该由他挑时间点（R18） |
