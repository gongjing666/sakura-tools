# 07 S3 存储生命周期

这一页规定一份存储配置从「填好」到「删除」的整条路径：什么时候允许换桶、第一次上传成功之后锁住什么、关掉总开关之后能做什么、删配置时连带清什么。**存储页面上的每个按钮，都必须能在这一页找到它属于哪一格。**

> 相邻篇：option 的读写、登记与卸载见 [04-数据与存储](04-数据与存储.md)；卡片、弹窗、令牌与 1440/390 验收见 [03-后台UI](03-后台UI.md)；新增一家存储厂商见 [02-新增功能](02-新增功能.md) §12；把对象从旧桶搬到新桶见 [08-OpenList迁移通道](08-OpenList迁移通道.md)。
> 本页引用的行号以 **1.28.2**（2026-11-17 发布）为准，改代码后如与代码不符以代码为准并顺手修正本页。
> **状态：规范已定，代码部分实现。** §1 描述的是施工前（1.28.1-beta-6）的真实现状，保留下来是为了说明每条规则在补什么洞；落地按 §8 的实施清单推进，尚未实现的条目仍在 §9 的验收清单里待验。
> **已落地（1.28.2）**：R5 整节——连接卡的「启用 S3 存储」复选框已移除，`enabled` 只由点配置卡片写入（`Profile_Manager::enable_profile()` / `disable()`，详见 [DECISIONS.md](../../DECISIONS.md) 的 1.28.1-beta-7 条）；R5 的「保存不挪活动配置」由 `Settings_Saver::keep_live_mirror()` 承担。R1–R4、R6–R11 仍待实施。

## §0 为什么需要这一页

存储配置不是「一张表单」，而是一个有状态的实体。过去三个版本各修了一次同一个形状的问题，根因都是状态没被显式建模：

| 版本 | 现象 | 真正的错 |
|---|---|---|
| 1.27.6 之前 | 改配置时偷偷多出一份 | 保存语义没有区分「改这份」和「换一份」 |
| 8119bf8 | 换服务商保存，覆盖掉原配置 | 「换目标」被当成「改这份」 |
| b819827 | 换桶后附件 URL 全部退回站点域名 | 「已上传到哪个桶」没有权威记录，只能靠指纹推断 |

三次的共同点：**没有一处代码能回答「这份配置现在处于什么状态、因此允许什么」**。每次修补都是在具体分支上加一个 if，下一个分支又漏。所以这一页先把状态和判定表定死，再谈实现。

## §2 六个缺口

1. **默认值不是约束。** 「默认保留本地」只是表单初始值。用户随手一勾就变成「上传后删本地」，而删除本地与「以后想换桶」在数据上是互斥的——本地没了，新桶永远补不齐。默认值挡不住这个操作，只有锁定挡得住。
2. **没有绑定概念，换桶成本为零。** 换一份配置只需点一张卡片，没人问「新桶里有没有这些对象」。代价由三个月后的裂图承担。
3. **删除语义与开关状态脱钩。** 现在「能不能删」只看「是不是活动配置」，于是最该删的那种（关掉总开关后要换桶）偏偏删不掉，而不该留的（绑定中的配置）只要先切走就能删。
4. **删除确认只有一句话。** 它既没说云端对象不会被删，也没说哪些附件会因此永久失联，更没有要求操作者确认自己删的是哪一份。
5. **上传指标只增不减。** `sio_s3_upload_events` 全表 GROUP BY 出 totals，清理逻辑从来没写过。站点跑三年，这张表就是三年。
6. **上传行为不受生命周期约束。** 「不上传 WordPress 生成的缩略图」今天可以随手上下来回切，而它决定云端到底有没有子尺寸：绑定后切一次，同一站点的附件就分成「带尺寸」和「不带尺寸」两段，缩略图改写开到哪一段，哪一段的尺寸 URL 就是 404。它和「删除本地文件」一样属于「一次决定、长期生效」的开关，必须与绑定一起冻结（R11）。

## §3 状态机

存储配置只有四个状态。**任何操作都要先落到一个状态，再查它允许什么。**

| 状态 | 判定 | 这一态允许 | 这一态禁止 |
|---|---|---|---|
| **S0 空** | 没有可用配置 | 新增配置、填表、测试连接 | 启用 S3 存储（没有卡片可点，开关只能由卡片触发） |
| **S1 未绑定** | 活动配置完整，`binding` 为空 | 改任何字段、新增配置、切换配置、删除非活动配置 | — |
| **S2 已绑定** | `binding` 非空且 `enabled=true` | 改配置名称、改密钥、改图片地址前缀、新增配置、切换配置、删除非活动配置 | 改五项身份（R4）、改上传行为（R11）、删除绑定配置 |
| **S3 已暂停** | `binding` 非空且 `enabled=false` | 同 S2，**外加删除绑定配置**（删除即解绑；若 `binding['no_local_saving']==='true'`，必须先删完其余配置，见 R10） | 改五项身份、改上传行为 |

迁移只有五条边：

| 从 | 事件 | 到 | 条件 |
|---|---|---|---|
| S0 | 保存一份完整配置 | S1 | `Options::is_configured()` 为真 |
| S1 | 第一次成功上传递交 | S2 | `mark_synced()` 回读确认为 `synced`（见 R3） |
| S2 | 再点一次正在使用的那张配置卡片 | S3 | `active_profile_id` 保留，卡片变浅 |
| S3 | 点任意一张配置卡片 | S2 | 配置仍完整（不完整时卡片本身 `disabled`） |
| S3 | 删除绑定配置 | S0 或 S1 | 删除即解绑（见 §6）。普通锁定可留下其余配置（→ S1）；高风险锁定必须清空后删（→ S0，见 R10） |

**S1 → S2 是单向的**：绑定之后没有「解绑但保留配置」的入口，因为那等于给「换个桶试试」开一个后门。要解绑只能走 S3 → 删配置。

**开关只有一个入口：配置卡片本身。** `enabled` 不再是「添加存储配置」卡里的一个复选框——点一张不是当前使用的卡片＝切换并启用，点当前正在使用的那张＝关闭（卡片变浅，`active_profile_id` 保留）。所以 S0 不可能「开着」：没有卡片，就没有可点的东西。这也意味着 S2 ↔ S3 的每一次切换都要经过一次明确的点击，而不是填表时顺手带过去。

**两种锁定形态只差「解绑时其余配置能不能留」**：同一时刻被绑定的只有一份配置，解绑就是把它删掉。普通锁定下，删完绑定配置后剩下的那几份直接回到 S1（它们从未被绑定过）；高风险锁定下，其余配置必须先删光，解绑后落到 S0——因为那些配置指向的桶里没有「本地副本已被删掉」的对象，切过去就是死链（R10）。

## §4 数据模型：`binding`

`s3_options` 新增一个 `binding` 键，不新建表。理由：它是配置的附属属性，必须与 `profiles` 同一个 option 里原子写入；拆表就会有两个真相。

```php
'binding' => array(
    'profile_id'      => 'prof_5233fa6ccfaa',
    'provider'        => 'dogecloud',
    'bucket'          => 'doss-v2-328e5d1039000fe8-1258813047',
    'endpoint'        => 'https://cos.ap-chengdu.myqcloud.com',
    'region'          => 'ap-chengdu',
    'upload_path'     => 'wp-content/uploads',
    'no_local_saving' => 'false',
    'no_thumb'        => 'false',
    'locked_at'       => 1794848642,
    'locked_by'       => 1,
),
```

| 字段 | 用途 |
|---|---|
| `profile_id` | 绑的是哪一行；切换与删除的判定靠它 |
| `provider` / `bucket` / `endpoint` / `region` / `upload_path` | 身份指纹的五段，逐段比对就知道「这次保存是不是在换桶」 |
| `no_local_saving` | 绑定那一刻的取值，之后以此为准，POST 不再作数 |
| `no_thumb` | 同上：绑定那一刻「是否上传缩略图」的取值，之后不再接受 POST（R11） |
| `locked_at` / `locked_by` | 界面文案与排障；`locked_by` 是当时登录用户 id |

**写入点只有一个**：`Synchronous_Uploader::finalize()`，在 `mark_synced()` 回读确认为 `synced` 之后（当前 `src/S3/Synchronous_Uploader.php:342` 写状态、`:346-350` 回读）、删除本地文件之前（:355），且仅在 `binding` 为空时写入。`skipped` / `failed` / `held` 一律不写——「试过但没成」不构成绑定。

**读取入口**（都放 `src/S3/Options.php`，业务代码不直接读 option）：`binding(): ?array`、`is_bound(): bool`、`binding_allows( array $candidate ): bool`。

**解绑点只有一个**：删除绑定配置。`Uninstaller` 无需单独处理——它整条删 `s3_options`，但要在 `docs` 的卸载清单里注明 `binding` 随 option 一起消失。

**相邻的一个标记**：`s3_options['behaviour_locked']`（`'true'` / `'false'`）记「这个站点曾经完成过绑定」。它与 `binding` 同时置位，在配置表被清空时清除；默认 `'false'`，要同时加进 `defaults()` 与 `Activation` 的硬编码默认值。它不参与身份判定，只服务 R11——因为 `binding` 解绑时就被清空了，记不住这件事。

## §5 十一条规则

### R1 默认保留本地附件

表单默认不勾「上传成功后删除本地文件」。这条只是**默认值**，真正的约束是 R3 与 R4——默认值可以被覆盖，绑定不行。

绑定之后这个开关的取值决定了站点的**两种锁定形态**，后面的规则要用到：

| 形态 | `binding['no_local_saving']` | 本地副本 | 解绑时另外的配置 |
|---|---|---|---|
| **普通锁定** | `'false'` | 上传后保留 | 可以留在 S1，切换过去仍然能显示（本地有文件，URL 降级到站点域名） |
| **高风险锁定** | `'true'` | 上传成功后已删除 | 必须**全部删掉**才允许删绑定配置，见 R10 |

落点：`src/Activation.php:58`、`src/S3/Options.php:97-115`。两处默认值必须同时是 `'false'`。

### R2 勾选高风险选项必须先过一道弹窗

「上传成功后删除本地文件」是唯一一个**当下看不出来、三个月后才致命**的开关。勾选时必须弹窗，把后果说完整，且这次勾选要被服务端复核。

前端：`no_local_saving` 从 `false` 变成 `true` 时调 `admin.ui.confirm()`，取消则把复选框还原为未勾选；同意则同时打上隐藏域 `no_local_saving_ack=1`。

服务端：`save()` 与 `save_behaviour()` 都检查——若提交值由假变真而 `no_local_saving_ack` 不为 `1`，返回 `error=risk_ack`，不写库。

文案定稿（四段式：后果 → 范围 → 不可逆 → 锁定）：

> 勾选后，新上传的图片及其缩略图只有在全部成功传到云端并回读校验通过后，才会删除服务器上的本地文件；任何一张失败都会保留整组本地文件。只影响本机新上传的附件，从同步中心手动上传历史附件时始终保留本地副本。本地文件删除后本插件无法恢复，只能从云端重新下载；如果云端对象后来被删除或被覆盖，这些附件将永久无法显示。首次成功上传后，本选项和这份存储配置会一起锁定，届时无法再更改。锁定之后如果想重新选择存储服务商或存储桶，唯一的办法是把已保存的存储配置**全部删除**（不能切换、不能改字段），再重新新增一份。

落点：`src/S3/S3_Storage_Page.php:605-612`（现文案在此替换）、`src/S3/Settings_Saver.php:395-410`（服务端复核）、`assets/ui/js/pages/storage-connection.js`（新增 `initRiskAck()`）。

### R3 第一次成功上传递交即绑定

绑定触发点是**提交成功**，不是「配置保存成功」，也不是「测试连接成功」。理由：配置可以随便试，测试连接只证明凭据能用，只有真的把一个对象钉进桶里，才证明这套配置和这个站点的目录结构是对得上的。

判定链：`mark_synced()` 写入后**回读** `Sync_Status::status()` 必须等于 `Sync_Status::SYNCED`（现有代码 :346-350 已经在回读），且 `binding` 为空，才写 `binding`。回读失败说明持久化没落地，此时不能锁——否则用户会遇到「锁住了但一份都没传上去」。

落点：`src/S3/Synchronous_Uploader.php:342-355`。

### R4 绑定后冻结身份五项

绑定之后，下面五项**任何一个被改动都视为换桶**，服务端直接拒绝（`error=locked`），不是「弹窗提醒后放行」：

| 冻结项 | 为什么 |
|---|---|
| `provider` | 换厂商必然换桶 |
| `bucket` | 换桶本体 |
| `endpoint` | 同一家换个地域也是换桶 |
| `region` | 参与签名，与 endpoint 一起决定对象落在哪 |
| `upload_path` | 改了它，已上传对象全部不在新路径下，URL 立刻死 |

这五项正是目标指纹的五段（`Synchronous_Uploader::target_hash_for()` `src/S3/Synchronous_Uploader.php:496-505`：`v2|provider|bucket|endpoint|upload_path`，旧形态在 `:519-545`），所以「冻结身份」与「指纹不变」是同一件事。

上传行为（`no_local_saving` 与 `no_thumb`）不在本表里，由 R11 管：它也在同一次成功上传后落锁，但解冻条件不同，而且是「忽略 POST」而不是「报错」。

**不冻结**（改了不影响桶身份）：配置名称、`key` / `secret`（轮换密钥）、`object_acl`、`upload_url_path`（CDN 域名，纯展示）。

实现要点：`save()` 在 `binding` 非空时逐字段比对 POST 与 `binding`，五项里任一段不等即返回 `error=locked` 且不写库；其余字段按上面四个白名单放行。

### R5 绑定后仍可切换与新增，但开关只由配置卡片触发

绑定锁的是**桶的身份**与**上传行为**，不是「能不能用别的配置」。所以：

- **新增配置照常**：「添加存储配置」卡随时可以再存一份（换服务商时服务端仍会强制新建，见 `Settings_Saver::save_as_new_for_save()`）。保存一份新配置**不会**把它设成活动配置，也**不会**动 `enabled`——要启用必须去点那张卡片。
- **切换配置照常**：点另一张卡片＝切换并启用（R6）。绑定期切换不会丢绑定，`binding` 只在删除绑定配置时清除。
- **开关只有卡片一个入口**：「添加存储配置」卡里没有「启用 S3 存储」复选框（1.28.1-beta-7 起移除）。点当前正在使用的卡片＝关闭 S3（卡片变浅，`active_profile_id` 保留）；点别的卡片＝切换并开启。这样「没有配置却开着 S3」在结构上不可能出现。
- **保存连接设置不再有副作用**：`save()` 的 `enabled` 取自库里已有值，活动配置沿用 `active_profile_id`，顶层镜像字段只在被保存的那份就是活动配置时才改写。存一份草稿不会把整站媒体地址挪到没人选的桶上。

**误解要提前挡掉**：绑定后仍然可以新增和切换，所以「已锁定」徽章不能挂在别的配置卡上——它只会挂在身份五项与上传行为那里（R4 / R11 的界面表现）。真正的「换桶」不是切换，而是**改掉当前这份配置的身份字段**，那条路被 R4 封死。

落点：`src/S3/Profile_Manager.php:35` / `:49` / `:62-78`（`switch_profile()` / `enable_profile()` / `disable()` 共用 `activate()` `:87-156`）、`includes/class-s3-storage-module.php`（`wp_ajax_sakura_s3_toggle_profile`）、`src/S3/S3_Storage_Page.php`（`state_payload()`、配置卡按钮）、`assets/ui/js/pages/storage-connection.js`（`initProfileToggle()`）。

### R6 关闭总开关＝暂停，不是解绑

`enabled=false`（再点一次当前配置卡片）时绑定仍然有效：配置还在、对象还在、只是 `Upload_URL::restore()` 把图片域名换回站点域名。此时**允许删除绑定配置**（R7），删了才解绑。这样「换桶」的唯一路径是显式的三步，而不是点错一张卡片。

关闭 S3 也是**唯一能走到解绑的入口**——高风险锁定下它同时是「删其余配置」这一步的前置条件（R10）。

### R7 删除判定表

| 配置 | `enabled` | 绑定 | 能否删除 | 结果 |
|---|---|---|---|---|
| 非活动 | 任意 | 不可能是绑定态 | ✅ | 通用确认 → 删除 |
| 活动 | `true` | 无 | ❌ | `error=delete_active`：「当前使用中的配置不能删除。如需更换存储桶，请先点这张卡片关闭 S3 存储。」 |
| 活动 | `true` | 有 | ❌ | `error=delete_bound`：同上，且说明会失去绑定 |
| 活动 | `false` | 有 | 视情况 | **普通锁定**（`binding['no_local_saving']==='false'`）：高风险确认 → 删除并解绑。**高风险锁定**（`==='true'`）：若还有别的配置则拒绝，`error=pending_profiles`，见 R10 |
| 活动 | `false` | 无 | ✅ | 通用确认 → 删除 |

**高风险确认**（「活动 + 已绑定 + 关闭」且放行时）必须包含三件事：

1. 说明解绑后果：删除后这份配置、它的核对记录、计数、删除队列与归档都会消失，站点回到未配置状态，图片地址会还原为站点域名。
2. 说明云端不受影响：**桶里的对象不会跟着删除**，需要自行到控制台处理。
3. 若 `binding['no_local_saving'] === 'true'`，单独列出「这 N 个附件将永久无法显示」（N = 该配置下 `seen_remote=1` 且本地文件已不存在的附件数），并要求**手打配置名称**才能提交。

落点：`src/S3/Profile_Manager.php:164-187`（判定）、`includes/class-s3-storage-module.php:189-215`（编排与错误映射）、`src/S3/S3_Storage_Page.php:274-283`（表单属性）、`src/S3/S3_Storage_Page.php:808-819`（错误码表）。

### R8 删除配置的连带清理

删除一份配置时必须按顺序做完，任何一步漏掉都会留下孤儿：

| # | 动作 | 漏掉的后果 |
|---|---|---|
| 1 | `unset( $profiles[ $id ] )` | — |
| 2 | `Index_Repository::purge_index( $id )`（清 `index` / `counts` / `jobs` / `scans` / `events` 五张表） | 同步中心残留幽灵行 |
| 3 | `DELETE FROM sio_s3_deletes WHERE profile_id = ?` | 删除任务找不到 adapter，每天退避重试到 `dead`，日志刷屏 |
| 4 | `unset( $retired_targets[ $id ] )` | 归档配置越积越多，且指向已不存在的 profile |
| 5 | 若删的是绑定配置：`unset( binding )` | 站点永久卡在「已绑定但配置没了」 |
| 6 | 若删的是活动配置：`active_profile_id` 置空、顶层凭据清空、`Upload_URL::restore()` | 顶层 `provider`/`bucket` 指向已删配置，URL 过滤器读不到目标 |
| 7 | 删除该配置在 OpenList 上的常驻镜像挂载（`/sakura-tools/<profile_id>`，见 [08](08-OpenList迁移通道.md) §4.6） | 留下孤儿挂载：持有已作废的凭据、占着该 `mount_path` 的 UNIQUE 位置 |

**明确不清**（这三样是刻意的）：

- **云端对象**：插件不替用户删桶。删本地配置不等于删云端数据。
- **附件 post meta**（`_sakura_imgopt_s3_target` / `_sakura_imgopt_s3_objects` / `_sakura_imgopt_s3_synced_at`）：指纹按「厂商|桶|endpoint|路径」算，不认配置行 id（`Synchronous_Uploader::target_hash_for()` `src/S3/Synchronous_Uploader.php:496-505`，旧形态见 `:519-545`）。删掉配置后若用同样参数重建一份，指纹完全一致，已同步附件**不用重传**就能恢复正确 URL。这是保留它们唯一的理由。
- **上传指标行**：走 R9 的保留期，不随配置删除。

`operations` 表不按 profile 分区（它是资源级互斥表），所以不在第 2 步范围内。

第 7 步是**唯一允许失败**的一步：OpenList 是外部服务，它连不上时删除配置必须照常成功。失败的处理是记进 `sakura_imgopt_openlist` 的 `state`，下次对账（`actual - desired`）自动清掉孤儿挂载——**绝不能因为删挂载失败就回滚配置删除**。

### R9 上传指标的保留期

`sio_s3_upload_events` 记录每次上传的结果，`profile_id` 只用于建索引，**全仓库没有任何地方按配置查它**——`snapshot()` 是全局 GROUP BY。所以它不会成为「删除配置后的孤儿数据」，问题是它从来不删。

- 新增 `Upload_Metrics::prune()`：把 `created_at` 早于 `KEEP_DAYS` 的行按 `result` 聚合进冻结基线 `sakura_imgopt_s3_upload_metrics`（`legacy()` 已是「冻结基线 + 明细表」模式，`src/S3/Upload_Metrics.php:322-356`），再删行。
- 冻结基线的 `totals` 只增不减，所以「历史总数」永远单调递增，而 `days` 只保留最近 14 天。
- 挂进既有每日 cron `sakura_imgopt_sync_cleanup`：`src/Sync/Scan_Worker.php:175-178` 目前只调 `$this->index->cleanup()`，加一行 `Upload_Metrics::prune()`。
- 该 cron 已登记在 `src/Deactivation.php`，不需要新增排程。

### R10 高风险锁定：解绑只能「全部删除后重来」

`binding['no_local_saving'] === 'true'` 时，附件在本地的副本已经被删过（R3/R4 的 `should_cleanup()`，`src/S3/Synchronous_Uploader.php:377-387`）。这条规则把「换桶」从「麻烦」升级为「必须推倒重来」：**锁定之后想重新选择存储服务商或存储桶，唯一的办法是把已保存的存储配置全部删除**（不能切换、不能改字段），再重新新增一份。

**唯一允许的路径**：

```text
高风险锁定（S2，no_local_saving=true）
  └─ 再点当前卡片（关闭 S3）                → S3 已暂停
       └─ 依次删除其余所有配置              → 每次都要通用确认（它们不是活动配置）
            └─ 最后删除绑定配置             → 放行条件：profiles 只剩它一份 + binding.no_local_saving='true'
                 └─ 配置表为空              → S0，没有任何配置可切换
                      └─ 新增配置 B、填完、开 S3、第一次上传成功 → S2（绑定 B）
```

判定用三条事实：**要删的是不是绑定配置**、**`binding['no_local_saving']` 的值**、**`profiles` 里还剩几条**。逐格如下：

| 想删的配置 | 是否绑定配置 | `no_local_saving` | 还有别的配置吗 | 结果 |
|---|---|---|---|---|
| 绑定配置 | 是 | `'true'` | 有 | ❌ `error=pending_profiles`：「高风险锁定下不能保留其它配置。请先删除其余 N 份配置（它们指向的桶里没有这些附件），再删除当前配置。」 |
| 绑定配置 | 是 | `'true'` | 无 | ✅ 高风险确认（R7 三项 + 手打配置名）→ 删除并解绑 |
| 绑定配置 | 是 | `'false'` | 任意 | ✅ 按 R7（普通锁定，不限制其它配置） |
| 其它配置 | 否 | — | 任意 | ✅ 通用确认即可（删它们不动 `binding`） |

> 表里「其它配置」在正常情况下都**不是**绑定那份（`binding['profile_id']` 指向的配置唯一）。若历史数据出现 `active_profile_id` 与 `binding['profile_id']` 不一致的畸形状态，先按 R7 的「活动配置」行判定，不要套用本表。

**为什么必须清空**：`no_local_saving='true'` 期间上传的附件，本地文件已经删了，对象只在绑定那个桶里。别的配置指向的桶里没有这些对象，切过去 URL 会走 CDN 却取不到文件（死链），退到站点域名也照样 404（本地同样没有）。所以解绑之前那几份配置留着没有意义，只会让人误以为「还能切过去看一眼」。

**顺序是固定的，反了就卡住**：绑定配置一定是最新一次切换的目标，所以「其余配置」按定义都**不是**活动配置；而 R7 第 1 行允许删除「非活动 + 任意开关状态」的配置，因此这一步**不需要先把当前配置切走，也不需要再动开关**。真正会卡住的只有一种操作顺序——先点绑定配置的删除按钮：它会被 `pending_profiles` 拒掉，提示先删其余的。

**弹窗文案要比普通锁定重**，普通锁定的三条之外再加两条：

1. 明确「这是最后一次机会」：删除后站点回到未配置状态，**已删除本地副本的 N 个附件将永久无法显示**，除非用同样的服务商与桶名重新建一份配置（附件 post meta 仍在，R8「明确不清」）。
2. 明确「不是切换」：这里没有「切到另一份配置继续用」的选项，因为其余配置已经按规则先删掉了。

**界面**：迁移卡的文案要把顺序写死——「高风险锁定：请先点当前配置卡片关闭 S3 存储，删除其余全部配置，再删除当前配置」。绑定配置的删除按钮在「还有别的配置」时 `disabled` 并给出这个 `title`，而不是点下去才报错。

落点：`src/S3/Profile_Manager.php:164-187`（新增 `pending_profiles` 判定，与 `binding` 一起读）、`src/S3/S3_Storage_Page.php:274-283`（按钮 `disabled` 与文案）、`:808-819`（错误码表）、`includes/class-s3-storage-module.php:189-215`（错误映射）。

### R11 绑定后「上传行为」整卡冻结

R4 冻结的是**桶的身份**（决定对象落在哪儿）；这一条冻结的是**上传行为**（决定本地副本留不留、子尺寸传不传）。两者在同一次成功上传后一起落锁，但**解冻条件不同**——身份跟 `binding` 走，行为跟「配置表是否为空」走。

冻结的两项：

| 冻结项 | 为什么 |
|---|---|
| `no_local_saving` | 见 R1/R2。绑定后本地副本可能已经删过一批，改它只会让「以后上传的保留、以前删掉的不再回来」，用户会误以为风险解除 |
| `no_thumb` | 决定要不要把 `$metadata['sizes']` 里的子尺寸一起上传（`src/S3/Synchronous_Uploader.php:141`）。绑定后来回切一次，云端就会在时间轴上分成「带尺寸」与「不带尺寸」两段，而缩略图改写开启时缺尺寸就是 404（`src/Thumbnail/Settings.php:973` 已把这两者的冲突列为警告） |

**不冻结**：`upload_concurrency`（云端传输并发数，`src/S3/S3_Storage_Page.php:618-629`）。它只决定传得多快，不决定传哪些、也不影响本地副本；冻结它等于让绑定后的站点永远不能调优，收益为负。若今后要求连它一起冻，把它加进上表即可，其余设计不变。

**冻结与解冻**

- 冻结：第一次成功上传递交（R3），与写 `binding` 同一处、同一时刻。
- 解冻：`profiles` 为空——插件里一份存储配置都不剩。

为什么解冻条件要比身份冻结更严：普通锁定解绑之后配置表里可能还剩 N 份（§6），那一刻 `binding` 已经清空，若按 `binding` 判断就会立刻解冻；用户改完 `no_local_saving` 再让另一份配置完成一次上传，风险就在没人拦的情况下被重新打开。所以行为冻结一旦落下，**只有把配置表清空才解除**。这条终点正好与 R10 高风险锁定要求的 S0 重合，两条规则不冲突；普通锁定下则多一个中间态——配置还在、行为仍冻结。

**需要一个新标记**：`binding` 在解绑时会被清空（R8 第 5 步），记不住「这个站点曾经绑定过」。所以在 `s3_options` 里加 `behaviour_locked`（`'true'` / `'false'`）：

| 字段 | 置 `'true'` | 置 `'false'` |
|---|---|---|
| `behaviour_locked` | 与 `binding` 同一处（R3 的写入点） | 删除配置后 `profiles` 变为空时；`Uninstaller` 随 option 一起消失 |

判定式：`'true' === behaviour_locked && array() !== profiles`。后半句是防御——配置表空了就必须解冻，哪怕标记因手工改库而残留。

**服务端真值**（前端 `disabled` 只是视觉，R4 那条坑在这里同样成立：字段被禁用后浏览器不提交，`isset()` 会读成 `false`）：

- 有 `binding`：两项一律取 `binding['no_local_saving']` / `binding['no_thumb']` 快照，忽略 POST。
- 无 `binding` 但 `behaviour_locked='true'`：取当前 option 里已存的值，忽略 POST。
- 两个入口都要走这条取值：`save()` 的 `:245-246`（连接卡分支里的 `$connection_only` 三元）与 `save_behaviour()` 的 `:399-400`。漏掉任一个，冻结就形同虚设。

**界面**

- 「上传行为」卡（`src/S3/S3_Storage_Page.php:568-640`，`anchor='sakura-s3-behaviour'`）里两个复选框 `disabled`，卡头加一条状态行：**已锁定。这一组选项在第一次上传成功后固定，只有把存储配置全部删除（先点当前卡片关闭 S3，再删除所有配置）之后才能重新选择。**
- `check_field()`（`:697-708`）不支持 `id` / `disabled` / `data-*`，要扩签名；也可以改走 `Field` 的 `type=custom`（`src/Admin/UI/Field.php:91-100` 原样输出回调返回值，回调自己负责转义）。
- 「保存设置」按钮保留可用：并发数不冻结，点保存仍会存下并发数，其余两项被服务端忽略。整卡置灰会让用户以为连速度都不能调。

**冻结只封这两个开关，不封任何操作**：

- 切换存储配置（多配置下的换桶路径，§6）不受影响；
- 同步中心的一切动作不受影响：完整核对、增量扫描、单条/批量上传、下载、删除、迁移（[08](08-OpenList迁移通道.md)）；
- 改配置名称、轮换密钥、改图片地址前缀不受影响（R4 的不冻结清单）；
- 删除配置不受影响（R7/R10 判定表照旧）。

一句话：冻结改的是「上传时删不删本地、传不传子尺寸」，不是「谁能操作」。

落点：`src/S3/S3_Storage_Page.php:568-640`（状态行）与 `:597-612`（两个复选框 `disabled`）、`src/S3/Settings_Saver.php:245-246` 与 `:399-400`（真值来源）、`src/S3/Synchronous_Uploader.php:342-355`（同时写 `binding` 与 `behaviour_locked`）、`src/S3/Profile_Manager.php:164-187`（配置表空时置 `'false'`）、`src/S3/Options.php`（`behaviour_locked()` / `behaviour_frozen()` 读取入口）。

## §6 换桶的唯一路径

普通锁定（`binding['no_local_saving']==='false'`）下，路径是三步：

```text
S2 已绑定（普通锁定：本地副本还在）
  └─ 再点当前卡片（关闭 S3）        → S3 已暂停（图片回站点域名）
       └─ 删除绑定配置             → S0/S1（解绑）
            └─ 新增配置 B 并填完     → S1
                 └─ 点 B 的卡片，第一次上传成功 → S2（绑定 B）
```

高风险锁定（`binding['no_local_saving']==='true'`）下，路径是四步，**中间多一道「删光其余配置」**：

```text
S2 已绑定（高风险锁定：本地副本已删）
  └─ 再点当前卡片（关闭 S3）        → S3 已暂停
       └─ 删除其余全部配置          → 只剩绑定配置
            └─ 删除绑定配置         → S0（配置表为空）
                 └─ 新增配置 B 并填完 → S1 → 点 B 的卡片，第一次上传成功 → S2（绑定 B）
```

两者的区别只在「解绑那一刻配置表里还剩几份」：普通锁定允许剩下 N 份（本地文件还在，切过去仍能显示）；高风险锁定必须剩 0 份，理由见 R10。**想重新选择存储服务商或存储桶，只有这一条路**——改当前配置的身份字段被 R4 拦、删绑定配置被 R7/R10 拦，能动的只有「关闭 S3」和「删配置」。注意「新增一份别的配置再点它」并不是换桶：切换只换用哪份配置，不会迁移任何对象，新桶里没有那些文件（§6 的迁移窗口才是把对象搬过去的地方）。

没有第二条路。特别地：**插件自己不做「换桶向导」（预检 → 复制/重传 → 再切）**。跨厂商没有服务端复制能力（`copy_source` 只能表达一个桶 + 一个键，无法携带第二个 endpoint 与第二套凭据），插件内部也没有任何 `CopyObject` 调用点；要服务的就是一个不存在的入口。

**迁移由 [08-OpenList迁移通道](08-OpenList迁移通道.md) 承担**：本机的 OpenList 在服务端同时挂载源桶与目标桶，流式复制，插件只发一次 `/api/fs/copy` 再轮询结果。每份完整配置在 OpenList 上都有一份**常驻镜像挂载**（`/sakura-tools/<profile_id>`），随配置增删改同步，所以迁移不需要现场建挂载。它不改这条路径的顺序——正确用法是在**关闭 S3 之后、删除旧配置之前**把对象搬进新桶（暂停态是唯一能操作桶的窗口），搬完再删配置、新增配置、开 S3、跑完整核对。**迁移入口只对「已保存的完整配置 ≥ 2」开放**：只有一份配置时删掉它没有任何可切换的目标，站点会退化成 S0。

> **高风险锁定下的迁移要多绕一步。** R10 要求删绑定配置时配置表里只剩它，所以「搬完对象、切到目标配置」这条路走不通——目标配置本身也是「其余的配置」，得先删掉它才能删源配置。真实顺序是：**搬完 → 删光全部配置（含目标配置）→ 重新新增目标配置 → 开 S3 → 跑完整核对**。重新新增同参数配置不会丢东西：桶里对象还在，附件 post meta 里的指纹按「厂商|桶|endpoint|路径」算（`src/S3/Synchronous_Uploader.php:496-505`），同参数重建后指纹一致，URL 立刻走新桶域名，**不需要再传一遍**。

**R11 的冻结与这条路径互不干扰**：冻结的是上传行为（`no_thumb` / `no_local_saving`），上面每一步都不读它——关 S3、删配置、新增配置、点卡片启用、跑完整核对照常可做。唯一的区别是换桶之后那两个开关仍然不能改，它们本来就是绑定时定下的。

## §7 上线策略：不回溯

升级到本规范后，`binding` 为空。**已有的 130 个已同步附件不会触发锁定**——它们只是历史，不构成「现在这套配置被验证过」。

锁定从**新版本第一次成功上传递交**开始。理由：老站的历史状态无法反推（不知道当初有没有勾过「删除本地文件」），回溯锁定会把一批配置焊死在一个可能已经缺本地文件的桶上，那比不锁更糟。

代价是升级后有窗口期可以自由换桶。为此在「上传行为」卡下方加一行状态条：

- 未绑定：「这份配置还没有成功上传过。完成第一次上传后，服务商、存储桶、服务地址与『上传成功后删除本地文件』将被锁定。」
- 已绑定（普通锁定）：「2026-11-17 10:12 起已锁定。如需更换存储桶，请先点当前配置卡片关闭 S3 存储，再删除它。」
- 已绑定（高风险锁定，`binding['no_local_saving']='true'`）：「2026-11-17 10:12 起已锁定，且已开启『上传成功后删除本地文件』。如需更换存储服务商或存储桶，只能先点当前配置卡片关闭 S3 存储，删除其余全部存储配置，再删除当前配置，然后重新新增——本地副本已不在，没有别的路可走。」
- 上传行为（上面前三条都适用）：「不上传 WordPress 生成的缩略图」与「上传成功后删除本地文件」已随绑定一起固定，只有把存储配置全部删除之后才能重新选择。

## §10 明确不做

| 不做 | 原因 |
|---|---|
| 插件内的桶到桶直传 / 迁移向导 | 跨厂商无服务端复制；同厂商的 `copy()` 也只在 SDK 里存在，插件没有调用点。迁移改由外部的 OpenList 通道承担，见 [08](08-OpenList迁移通道.md) |
| 单配置站点开放迁移入口 | 见 §6：迁移的收尾是「删源配置 → 切目标配置」，只有一份配置时没有目标可切 |
| 旧桶孤儿清点 | 需要另一套「列出桶内全部对象并与索引比对」的能力，超出生命周期范围 |
| 改写文章正文里写死的旧域名 | `post_content` 里的 `<img>` 是发布时固化的，与附件 URL 过滤器无关，属于另一个课题 |
| 尺寸级 URL 降级 | `wp_get_attachment_url` 只返回一个基础 URL，做不了「主图走 CDN、缺的尺寸走本地」 |
| 解绑但保留配置 | 等于给换桶开后门，与 R3 的设计意图相反 |
| 高风险锁定下「先在原地换商再试」 | 见 R10：`no_local_saving='true'` 时改身份被 R4 拦，唯一出路是删光全部配置重来；给一条「这次例外」的通道等于把锁定作废 |
| 把 `no_local_saving` 从 `true` 改回 `false` | 本地文件已经删了，改回 `false` 只是让**之后**新上传的附件保留本地，对已删的那批毫无帮助，反而会让人以为「风险解除」 |
| 冻结期间提供「临时的例外修改」 | 一次例外等于没有冻结：改完的取值无法与已上传的对象对齐，也没有审计点能证明「只改过这一次」 |
