## §0 为什么需要这一页

四个症状都指向同一处结构问题：

1. **管理员删不掉前台用户上传的附件。** 媒体库批量删除提示「已删除 0 个文件，2 个未能删除（可能是用户中心上传的文件）」。
2. **插件自己的删除入口各删各的。** 同步中心「删除远端」只删桶对象，本地文件、附件、台账、容量一动不动；审核队列删得比较完整，但必须先有用户提交申请。
3. **同一件事两套结算。** 官方入口走 `finalize_deleted_attachment()`，审核队列走 `complete_purge()`，靠进程内布尔标记避免双扣。
4. **删不干净会复活。** 只删远端后，URL 在 1 小时内仍指 CDN（对象已无 → 404），缓存过期后降级回站点域名 → 本地文件还在 → 内容重新可访问（URL 出口见 07 的 R12 与 `Storage::should_keep_local()`）。

根因：**「谁能删」和「删了怎么记账」被塞进同一个钩子，而记账又依赖进程内状态。** 于是要么拦（拦得过头，连管理员也删不掉），要么漏（漏了就永远不平：文件没了、容量不退、没有审计）。

这一页把两件事拆开：**拦截保留、判据改造**（不按文件来源放行，按操作者能力放行——管理员直接删，其余人只能申请）；**结算收敛成一个函数**（谁删的都在这里记账）。

**两个拦截点的问题不在「拦」，而在「判据」：**

- `guard_delete()`（`:557`）与 `guard_rest_delete()`（`:668`）是插件否决 WordPress 官方删除的两处入口（媒体列表只判真值，返回 `WP_Error` 会被当成功，注释在 `:598-601`）。
- 放行条件写死成「文件来源是 `source=media`」（`:590`），于是**是不是管理员根本没参与判断**：管理员删前台用户传的图被拒，而作者删自己的图是否能过，取决于来源而不是角色。
- 产品规则要的是「**管理员能删一切，管理员以下只能发起申请**」。按操作者能力表达才准确：`sufm_admin_delete_files`（`src/UserFiles/Capabilities.php:43`，`admin_caps()` 只授给 administrator）在 → 放行；不在 → 拒绝并引导申请。
- 容量真正的守卫是**唯一结算点**，不是拒绝删除；所以闸门可以留，判据必须换。

**结算的裂缝：**

- `finalize_deleted_attachment()` 依赖 `$direct_deletes[$post_id]`（`:110` 声明、`:596` 置位、`:623` 判断）。这是**进程内**状态：任何没经过 `guard_delete()` 的删除（脚本、其他插件、CLI、未来的新入口）都会让台账停在 `active` —— 文件没了、容量不退、没有审计。
- 审核队列通过 `sufm_allow_attachment_delete`（`Executor.php:758-762`）绕过同一个闸门，因此不置位，由 `complete_purge()` 自己结算。两套并存，靠「谁也别碰谁」维持正确。

## §2 规则

**D1 删除准入按能力判定，不按文件来源。** 保留 `pre_delete_attachment`（`src/UserFiles/Media/Media_Hooks.php:557`）与 `rest_pre_dispatch`（`:668`）两处闸门，放行条件改为：台账 `active` + `current_user_can( Capabilities::DELETE_FILES )` + `current_user_can( 'delete_post', $post_id )`。满足 → 直接删（并结算）；不满足 → 拒绝，提示「请提交删除申请」。**闸门只做准入，不做记账**；记账交给 D3 的唯一结算点。`$direct_deletes`（`:110`）随之删除。

**D2 只有两个观察点，位置固定：**

- `delete_attachment`（`src/S3/Storage.php:156`，已有）：远端对象入队删除。必须留在这里，因为 WordPress 在这个钩子之后才删 postmeta（见 §3.1），只有这时还能读到 `_sakura_imgopt_s3_objects`（`Sync_Status::OBJECTS_META`，`src/S3/Sync_Status.php:27`）。
- `deleted_post`：台账结算。新增观察者，取代 `finalize_deleted_attachment()` 里的 `$direct_deletes` 判断。

**D3 结算只有一个函数、只有一处扣减。** `Deletion::settle( int $file_id, string $via, int $actor_id, string $reason )`：事务内用条件更新 `lifecycle → purged` 决出胜者，胜者删 `artifacts` 行、`Quota::adjust_used( -charged_bytes )`（`src/UserFiles/Services/Quota.php:484`）、写审计；输家直接返回。**这是全插件唯一扣容量的地方。**

**D4 台账状态机加一态：** `active → deleting → purged`。`deleting` 由内核抢占时写入（`Files::claim_deleting()`），表示「有人在删」。前台列表只查 `lifecycle='active'`，所以 `deleting` 立刻从用户视野消失。

**D5 插件主动删除只有一个内核：** `Deletion::delete( array $targets, Deletion_Context $ctx )`，目标可以是 `attachment_id`、`file_id` 或对象 key。审核队列、同步中心、后台按钮、CLI 全部经它。

**D6 删除必然连带本地附件。** `FULL` 模式下 `wp_delete_attachment( $id, true )` 是必经步骤，不允许「只删对象」。只有**解析不到附件的对象**（仅云端行、孤儿对象、换桶残留）才允许 `REMOTE_ONLY` —— 这时本来就没有本地副本，语义自洽。

**D7 同步中心的删除升级。** 能解析到附件（`Storage_Adapter::attachment_id_for_key()`，`src/S3/Storage_Adapter.php:228`）且台账 `active` 的 key 走 `FULL`；否则保持仅删远端。按钮与确认文案必须说清这一区别。

**D8 审核队列并入内核，但保留自己的安全边界。** `purge_file()` 的租约、快照校验、连续授权、`claim_item_for_delete()`、`recover_deleting()` 全部保留（它们回答「这张申请单执行到哪一步」）；删附件与结算改调内核。两层互斥互不干扰：申请单行锁管单据，`files` 行条件更新管容量。

**D9 删除顺序固定（FULL）：** ① 抢占台账（`deleting`）② 删附件与本地文件（`wp_delete_attachment`）③ 远端对象（异步队列，或交互式同步删 + 校验）④ 结算（观察者或内核，谁先到谁赢）⑤ 索引与缓存（`Sync\Attachment_Indexer` 挂 `delete_attachment` 自动完成）。

**先本地后远端**：本地没了，URL 就没有可渲染的对象，不可能触发降级复活；反之会留下「桶里没了、本地还在」的窗口，正是 §0 症状 4。

**D10 审计一条一行。** 每次结算写 `nb_sufm_events`：`action='delete'`、`result='purged'|'missing'|'partial'`、`safe_detail` 记 `via` 与 `reason`（`wordpress|plugin|cli|sync` × `operator|request|moderation|cleanup`），`actor_id` 记当前用户、`owner_id` 记文件所有者、`subject_id` 记附件 ID。事件里不写路径与对象键（`Events` 的既有约定）。

**D11 在途申请与外部删除冲突时以事实为准。** 台账已被外部删除（`purged`）时，审核队列的该项标 `done / already`；附件已不存在但台账未结算的，先结算再关单。不允许「一直失败」。

**D12 不变量：** 对每个 owner，`nb_sufm_usage.used_bytes` 必须等于 `SUM(charged_bytes) FROM nb_sufm_files WHERE lifecycle='active' AND owner_id=...`。任何删除之后都必须成立；现成的 `/admin/reconcile` 就是校验器。

## §3 结算协议

### 3.1 必须记住的 WordPress 顺序

`wp_delete_attachment()` 的实际执行顺序（生产站 `wp-includes/post.php`）：

```
:6875  do_action( 'delete_attachment' )      ← 远端删除观察者在这里（postmeta 还活着）
:6881  delete_metadata '_thumbnail_id'
:6894  delete_metadata_by_mid（逐条删 postmeta）
:6898  do_action( 'delete_post' )
:6904  do_action( 'deleted_post' )           ← 结算观察者在这里（附件行已不存在）
:6941  开始删本地原图与各尺寸（-scaled / -rotated / intermediate / original）
```

三条推论：

1. 远端删除观察者必须留在 `delete_attachment`。
2. 结算观察者放 `deleted_post`。
3. 在 `deleted_post` 里**本地文件还在盘上** —— 结算绝不能依赖 `is_file()` 判断「删成功没」，也不能靠它决定扣不扣容量。

### 3.2 状态迁移

```
active ──claim_deleting()──▶ deleting ──settle_purged()──▶ purged
   └──────────────── settle_purged()（WordPress 直接删）──────┘
```

- `Files::claim_deleting( int $file_id ): bool` —— `UPDATE ... SET lifecycle='deleting' WHERE id=%d AND lifecycle='active'`，返回 `affected === 1`。
- `Files::settle_purged( int $file_id ): bool` —— `UPDATE ... SET lifecycle='purged', storage_state='deleted' WHERE id=%d AND lifecycle<>'purged'`，返回 `affected === 1`。
- 两者都是「谁先改到谁赢」，所以内核与观察者可以并发，天然幂等；**不需要任何进程内布尔标记**。

### 3.3 settle() 的两条铁律

- **先决出胜者，再动容量**：`Quota::adjust_used()` 只在 `affected === 1` 时调用，所以绝不会双扣。
- **事务里回滚就整笔回滚**：`artifacts` 删除、`adjust_used`、`set_lifecycle` 必须同事务（沿用 `finalize_deleted_attachment()` 现有的 `Db_Transaction` 写法，`Media_Hooks.php:634-646`）。失败时写 `result='failed'` 事件并让 `wp sakura-s3 health` 类巡检能看见，不允许半结算。

## §4 内核 API

新增 `src/UserFiles/Services/Deletion.php`（内核 + 结算器）与两个值对象：

```php
final class Deletion_Context {
    public string $mode;        // 'full' | 'remote_only' | 'takedown'
    public int    $actor_id;    // 当前用户
    public string $reason;      // operator | request | moderation | cleanup
    public bool   $sync_remote; // true = 交互式同步删远端并校验；false = 交给 Delete_Jobs
    public bool   $notify_owner;
}

final class Deletion_Result {
    // 逐项：target / status(deleted|missing|denied|partial|in_progress) / file_id / attachment_id / error
    // 汇总：deleted / missing / denied / partial 计数
}

final class Deletion {
    public function delete( array $targets, Deletion_Context $ctx ): Deletion_Result;
    public function settle( int $file_id, string $via, int $actor_id = 0, string $reason = 'operator' ): bool;
    public function on_attachment_deleted( $post_id, $post = null ): void;  // 挂 deleted_post
}
```

`delete()` 逐项流程：

1. **解析**：台账行（`Files::get_by_attachment()` `:163` / `Files::get()` `:138`）、附件、对象键（postmeta `_sakura_imgopt_s3_objects`；缺失时用 `Storage_Adapter::attachment_files()` `:274` 推导）。
2. **权限**：`user_can( 'delete_post', $attachment_id )` 且 `current_user_can( Capabilities::DELETE_FILES )`（`src/UserFiles/Capabilities.php:43`）。不符 → `denied`，不写库。
3. **在途申请**：`pending_request_id > 0` 时作废该申请项（`failed / attachment_gone`）并记审计，然后继续删 —— 不是拒绝（D11）。
4. **抢占**：`claim_deleting()`；已 `purged` → `missing`；已是 `deleting` → `in_progress`（别人在做）。
5. **删附件**：`wp_delete_attachment( $id, true )`（`force=true` 才删本地文件）。
6. **远端**：`$ctx->sync_remote` 为真时调 `Storage_Adapter::delete_keys()`（内部已走 `Remote_Operation_Guard`，`Storage_Adapter.php:380`），再 `head` / 列举校验；失败 → `partial / remote_unverified`，交给队列重试并计入 `wp sakura-s3 health`。
7. **结算**：`settle()`。观察者可能已经结算过，这里 `affected=0` 直接返回。
8. **汇总**：`Deletion_Result`。

第 5 步会重入观察者（`deleted_post`）并先结算，第 7 步再结算是幂等的 —— 这正是把「谁负责结算」这个问题消灭掉的做法。

## §5 各入口改造

### 5.1 媒体库与 REST（换判据，不拆闸门）

- `guard_delete()`（`:557-604`）：把「`source=media`」换成「`current_user_can( Capabilities::DELETE_FILES )`」，并去掉 `pending_request_id <= 0` 限制（管理员可以直删正在申请中的文件，在途申请项由 D11 作废，不阻塞管理员）。放行时不再置 `$direct_deletes`。
- `guard_rest_delete()`（`:668` 起）：同样按能力判断；管理员放行，其余返回 `WP_Error`，文案从 `managed_error()`（`:2180`）改为「请在前台文件空间提交删除申请」。
- `finalize_deleted_attachment()`（`:619`）改成薄观察者：`post_type === 'attachment'` → `Files::get_by_attachment()` → `Deletion::settle( $file_id, 'wordpress', get_current_user_id(), 'operator' )`，不再依赖 `$direct_deletes`。
- `adopt_unmanaged()` 保留在 `add_attachment`（`assign_uploaded`）路径上；删除时不再「看见就收养」—— 没有台账意味着从没扣过容量，本来无需结算。
- 「未能删除」文案（`Media_Hooks.php:1219`）保留失败语义，但措辞改成引导：「已提交删除申请，等待管理员执行」；`assets/media-folders.js:520` 的 toast 逻辑保留（它只是读批量删除的返回）。

### 5.2 审核队列

- `purge_file()` 媒体分支：删掉 `sufm_allow_attachment_delete` 注入（`Executor.php:758-762`），改调 `Deletion::delete( [ $attachment_id ], FULL, reason=request )`。
- userfiles 分支：保留 manifest 快照与「产物必须在 uploads 内」的校验（那是防误删的安全边界），然后同样调内核；远端交由 `delete_attachment` 入队。
- `complete_purge()` 改为调 `Deletion::settle()`，保留 `delete_request_items` 行锁（两层互斥各管各的，见 D8）。

### 5.3 同步中心

- `Sync_Actions::delete( $key )` 拆两条路径（D7）：有附件且台账 `active` → 内核 `FULL`；否则 `delete_keys()` + 索引行删除。

- 批量上限 200 项/次，超出分批（避免 PHP 超时）。

### 5.4 新增入口（P3）

- `POST /sufm/v1/admin/files/{id}/delete`（REST，`DELETE_FILES` + `manage_options`），行内按钮在 用户文件 → 全部文件。

## §8 风险与取舍

1. **闸门保留 = 插件成为删除的必经通道。** 这是有意的取舍：除管理员（唯一持有 `sufm_admin_delete_files` 的角色）外，任何删除都会被拒绝——包括作者删自己刚传的图、编辑在媒体库批量清理、第三方插件/脚本直接调 `wp_delete_attachment()`、以及 `wp post delete` 没带 `--user=管理员`。好处是「申请—审核—执行」成为唯一通道；代价是每条新删除路径都要记得带对身份或用内核。**必须配套**：① CLI 文档写明 `wp post delete` 要带 `--user`；② 给管理员一个后台直删入口（§5.4），否则只能在媒体库一张张点；③ 非管理员的提示必须指向申请流程，不能只说失败。权限事实备查：`delete_post` 是 meta 能力，删自己的附件（`post_status=inherit`）只需 `delete_posts`，删别人的要 `delete_others_posts`；默认带 `delete_posts` 的是 administrator / editor / author / contributor，subscriber 没有。**所以闸门真正挡住的是 editor / author / contributor**——他们核心层本来能删自己的附件，现在必须走申请；订阅者本来就删不了，闸门对它没有增量。
2. **在途申请与外部删除冲突。** 用户刚提交申请，管理员又在媒体库删了：内核作废申请项，executor 跑到时看到 `purged` / 附件不存在 → 标 `done / already`。必须补这条测试。
3. **远端删除天生异步。** 媒体库删除后桶里可能还要 1-2 分钟才消失（`delete_attachment` → `Delete_Jobs` → `Delete_Worker`）。同步中心用 `sync_remote=true` 同步删并校验；媒体库用异步（不阻塞）。界面文案要区分「已删除」与「已受理，远端删除进行中」。
4. **CDN 缓存。** 桶对象删掉后 `doge.nboke.com` 上的旧 URL 可能仍可访问到缓存过期。插件没有刷新能力，需要多吉云刷新 API 密钥（另立）。短期在确认框里提示缓存 TTL。
5. **`no_local_saving=true`（上传后删本地）站点**没有本地副本可删，内核要把它当 `missing` 而不是失败。生产当前是 `false`。
6. **批量删除的量。** 同步中心批量上限 200（§5.3）；后台直删无批量入口，先不做。
7. **不删桶里的孤儿。** 本地删除失败但远端已删（`partial / remote_unverified` 的反向）不会产生孤儿；反过来远端删失败会留下孤儿对象，由同步中心「仅云端」行清理，这是允许的第二条路径（D6）。

## §9 验收

- [ ] 不变量：任一删除之后，每个 owner 的 `used_bytes == SUM(charged_bytes) WHERE lifecycle='active'`；用 `/admin/reconcile` 与手写 SQL 各验一次。
- [ ] 并发：同一附件两路同时删（WP 入口 + 内核）只扣一次容量（单测：两次 `settle_purged()` 断言一次 true 一次 false）。
- [ ] 媒体库能删 `source=userfiles` 的附件：附件消失、本地文件消失、前台文件列表消失、容量退回、events 有一条 `via=wordpress`。
- [ ] 管理员身份：REST `DELETE /wp/v2/media/{id}` 与媒体库删除都能删掉 `source=userfiles` 的附件，台账一致、容量退回一次、events 一条 `via=wordpress`。
- [ ] 非管理员身份（用 `author` 与 `editor` 各一个测试账号）：媒体库与 REST 均被拒，提示指向「提交删除申请」，台账与容量都不变。
- [ ] 管理员删除一个正在申请中的文件：不因 `pending_request_id` 被拦，申请项标 `done / already`，容量只退一次。
- [ ] 审核队列：申请 → 审核 → 批次确认 → 执行完成，容量只退一次，events 一条 `via=plugin reason=request`。
- [ ] 同步中心删一条有附件的行：附件、媒体库记录、本地文件、桶对象、索引行、容量全部消失；删一条仅云端行：只有桶对象与索引行消失。
- [ ] `wp sakura-s3 health`：`delete_dead=0`、`delete_stale=0`、`remote_inflight=0`、`remote_uncertain=0`。
- [ ] 失败路径：远端删除失败时 status 为 `partial` 且队列重试可见，不显示「已删除」。
