## §0 为什么需要这一页

四个症状指向同一处结构问题：

1. **管理员删不掉前台用户上传的附件。** 媒体库批量删除提示「已删除 0 个文件，2 个未能删除（可能是用户中心上传的文件）」。**P1 已修**：准入改按操作者能力判定（D1）。
2. **插件自己的删除入口各删各的。** 同步中心「删除远端」原先只删桶对象，本地文件、附件、台账、容量一动不动；审核队列删得比较完整，但必须先有用户提交申请。**P3 已收口**：三者都走 `Deletion::delete()`（D5、§4.2）。
3. **同一件事两套结算。** 官方入口走 `finalize_deleted_attachment()`，审核队列走 `complete_purge()`，靠进程内布尔标记避免双扣。**P1 已收口**：两处都只经 `Files::settle_purged()` 的条件更新决出胜者（D3、§3.4）。
4. **删不干净会复活。** 只删远端后，URL 在 1 小时内仍指 CDN（对象已无 → 404），缓存过期后降级回站点域名 → 本地文件还在 → 内容重新可访问（URL 出口见 07 的 R12 与 `Storage::should_keep_local()`）。**P3 已修**：同步中心删有台账的行走 FULL，附件与本地文件一起删；只有解析不到附件的对象才允许仅删远端。CDN 边缘缓存仍需自然过期（§8 第 4 条）。

根因：**「谁能删」和「删了怎么记账」被塞进同一个钩子，而记账又依赖进程内状态。** 于是要么拦（拦得过头，连管理员也删不掉），要么漏（漏了就永远不平：文件没了、容量不退、没有审计）。

这一页把两件事拆开：**拦截保留、判据改造**（不按文件来源放行，按操作者能力放行——管理员直接删，其余人只能申请）；**结算收敛成一个互斥点**（谁删的都在这里决出胜者，胜者才记账）。

**两个拦截点的问题不在「拦」，而在「判据」：**

- `guard_delete()` 与 `guard_rest_delete()` 是插件否决 WordPress 官方删除的两处入口（媒体列表只判真值，返回 `WP_Error` 会被当成功，注释在 `guard_delete()` 尾部）。
- 放行条件写死成「文件来源是 `source=media`」，于是**是不是管理员根本没参与判断**：管理员删前台用户传的图被拒，而作者删自己的图是否能过，取决于来源而不是角色。
- 容量真正的守卫是**唯一结算点**，不是拒绝删除；所以闸门可以留，判据必须换。

**结算的裂缝：**

- `finalize_deleted_attachment()` 依赖 `$direct_deletes[$post_id]`（`:110` 声明、`:596` 置位、`:623` 判断）。这是**进程内**状态：任何没经过 `guard_delete()` 的删除（脚本、其他插件、CLI、未来的新入口）都会让台账停在 `active` —— 文件没了、容量不退、没有审计。
- 审核队列通过 `sufm_allow_attachment_delete` 绕过同一个闸门，因此不置位，由 `complete_purge()` 自己结算。两套并存，靠「谁也别碰谁」维持正确。

## §2 规则

**D1【已实现 1.28.5-beta-1】删除准入按能力判定，不按文件来源。** 两处闸门共用同一个判定 `Media_Hooks::may_delete_directly()`（`Media_Hooks.php:620`）= 台账 `active` + `current_user_can( Capabilities::DELETE_FILES )` + `current_user_can( 'delete_post', $post_id )`。满足 → 直接删（结算交给 D3）；不满足 → 拒绝并提示「请提交删除申请」。**闸门只做准入，不做记账。** `$direct_deletes` 已删除。两条例外同样放行：① `sufm_allow_attachment_delete` 过滤器为真（审核队列执行器专用）；② 没有台账行或台账已 `purged`（没扣过容量，无账可结）。

**D2【已实现】只有两个观察点，位置固定：**

- `delete_attachment`（`src/S3/Storage.php:156`，P1 前就有）：远端对象入队删除。必须留在这里，因为 WordPress 在这个钩子之后才删 postmeta（见 §3.1），只有这时还能读到 `_sakura_imgopt_s3_objects`（`Sync_Status::OBJECTS_META`，`src/S3/Sync_Status.php:27`）。
- `deleted_post`：台账结算。P1 起是 `Media_Hooks::finalize_deleted_attachment()`（`:605`）→ `Deletion::on_attachment_deleted()`（`src/UserFiles/Services/Deletion.php:88`）。

**D3【已实现】结算只有一个互斥点、一套扣减规则。** 互斥 = `Files::settle_purged( int $file_id ): bool`（`src/UserFiles/Repositories/Files.php:731`，`UPDATE ... SET lifecycle='purged', storage_state='deleted' WHERE id=%d AND lifecycle<>'purged'`，`affected === 1` 才是胜者）。扣减 = `Quota::adjust_used( -charged_bytes )`（`src/UserFiles/Services/Quota.php:484`，带 `GREATEST(0, ...)` 下限），**只有胜者才调**。调用方两处：`Deletion::settle()`（`:122`）与 `Executor::complete_purge()`（`:782`，见 §3.4）；两处都先用 `settle_purged()` 夺权，所以既不会双扣，也不存在「第二个账单」。

**D4【已实现，P3】** 台账状态机：`active → deleting → purged`。`deleting` 由内核 `Deletion::claim()` 调 `Files::claim_deleting()`（`:702`）写入，表示「有人在删」；`claim_deleting()` 之外的唯一出路是 `Files::settle_purged()`（条件 `lifecycle<>'purged'`）。前台列表只查 `lifecycle='active'`，所以 `deleting` 会立刻从用户视野消失。官方入口删除一张正处于 `deleting` 的文件时，闸门对持有 `DELETE_FILES` + `delete_post` 的人放行，由内核幂等收尾。

**D5【已实现，P3】** 插件主动删除只有一个内核：`Deletion::delete( array $targets, ?Deletion_Context $ctx = null ): Deletion_Result`（`src/UserFiles/Services/Deletion.php`），目标可以是 `attachment_id`、`file_id` 或对象 key。审核队列（`Executor::remove_via_kernel()`）、同步中心（`Sync_Actions::delete()`）、后台下架（`Media_Hooks::handle_takedown()`）全部经它。值对象 `Deletion_Context` / `Deletion_Result` 见 §4.2。

**D6【已实现，P3】** 删除必然连带本地附件。`FULL` / `TAKEDOWN` 模式下 `wp_delete_attachment( $id, true )` 是必经步骤，不允许「只删对象」。只有**解析不到附件的对象**（仅云端行、孤儿对象、换桶残留）才走 `REMOTE_ONLY` —— 这时本来就没有本地副本，语义自洽（`Deletion_Context::removes_attachment()`）。

**D7【已实现，P3】** 同步中心的删除升级：`Sync_Actions::removes_attachment()` 判定「能解析到附件（`Storage_Adapter::attachment_id_for_key()` `:228`）且台账 `active`」→ 内核 `MODE_FULL` 并 `sync_remote = true`（同步删远端 + `headObject` 校验）；否则 `MODE_REMOTE_ONLY`。确认文案已按两种范围分开（§5.3）。

**D8【已实现，P3】** 审核队列并入内核，但保留自己的安全边界：`purge_file()` 的租约、快照校验、连续授权、`claim_item_for_delete()`、`recover_deleting()` 全部保留（它们回答「这张申请单执行到哪一步」）；删附件与结算改调内核，并用 `Deletion_Context::$keep_request = true` 告诉内核「在途 item 行归执行器，不要作废」。两层互斥互不干扰：申请单行锁管单据，`files` 行条件更新管容量。

**D9【已实现，P3】** 删除顺序固定（FULL）：① 抢占台账（`deleting`）② 冻结对象键 ③ 删附件与本地文件（`wp_delete_attachment( $id, true )`）④ 远端对象（`sync_remote` 为真时同步删 + `objects_exist()` 校验；否则由 `delete_attachment` 观察者入 `nb_sio_s3_deletes` 异步删）⑤ 结算（观察者或内核，谁先到谁赢）⑥ 索引与缓存（`Sync\Attachment_Indexer` 挂 `delete_attachment` 清本地侧；远端对象真正删除后由 `sakura_imgopt_s3_object_deleted` 删除索引行）。

**先本地后远端**：本地没了，URL 就没有可渲染的对象，不可能触发降级复活；反之会留下「桶里没了、本地还在」的窗口，正是 §0 症状 4。

**D10【已实现，P3】** 审计一条一行。每次结算写 `nb_sufm_events`：`action='delete'`、`safe_detail` 记 `via` 与 `reason`（`wordpress|plugin|executor|cli` × `operator|request|moderation|cleanup`，可再追加 `|备注摘要`）、`actor_id` 记当前用户（系统路径为 0）、`owner_id` 记文件所有者、`subject_id` 记附件 ID。`result` 现为 `purged | failed | missing | partial`：`purged`/`failed` 由 `settle()` 写，`missing`/`partial` 由内核 `audit()` 补（否则「已不存在」「只删了一半」会和「没人调用」混在一起）。事件里不写路径与对象键。

**D11【已实现，P3】** 在途申请与外部删除冲突时以事实为准。台账已被外部删除（`purged`）时，审核队列的该项标 `done / already`；附件已不存在但台账未结算的，先结算再关单。内核抢占成功时（`keep_request` 为假）显式作废在途申请项：`delete_request_items` 置 `state='failed'`、`result='attachment_gone'`，用户不再看到幽灵条目；执行器自己拥有 item 行时置 `keep_request = true`，由 `complete_purge()` 收单。两种情形都有单测（`tests/DeletionKernelTest.php`）。

**D12【已实现，待上线验证】不变量：** 对每个 owner，`nb_sufm_usage.used_bytes` 必须等于 `SUM(charged_bytes) FROM nb_sufm_files WHERE lifecycle <> 'purged' AND owner_id=...`。口径以 `/admin/reconcile` 为准（`src/UserFiles/Rest/Controller.php:2270` 用的就是 `<> 'purged'`，差额由 `adjust_used()` 自动补齐 `:2283`）；P1 没有 `deleting` 行时它与「只算 `active`」等价，P3 引入 `deleting` 后必须按 `<> 'purged'` 理解。任何删除之后都必须成立。

## §3 结算协议

### 3.1 必须记住的 WordPress 顺序

`wp_delete_attachment()` 的实际执行顺序（生产站 `wp-includes/post.php`）：

```
:6875  do_action( 'delete_attachment' )      ← 远端删除观察者在这里（postmeta 还活着）
:6881  delete_metadata '_thumbnail_id'
:6894  delete_metadata_by_mid（逐条删 postmeta）
:6898  do_action( 'delete_post' )
:6904  do_action( 'deleted_post' )           ← 结算观察者在这里（附件行已不存在）
:6941  开始删本地原图与各尺寸（-scaled / -rotated / intermediate / original）
```

三条推论：

1. 远端删除观察者必须留在 `delete_attachment`。
2. 结算观察者放 `deleted_post`。
3. 在 `deleted_post` 里**本地文件还在盘上** —— 结算绝不能依赖 `is_file()` 判断「删成功没」，也不能靠它决定扣不扣容量。

### 3.2 状态迁移

```
active ──claim_deleting()──▶ deleting ──settle_purged()──▶ purged
   └──────────────── settle_purged()（WordPress 直接删）──────┘
```

- `Files::claim_deleting( int $file_id ): bool`（`:702`）—— `UPDATE ... SET lifecycle='deleting' WHERE id=%d AND lifecycle='active'`，返回 `affected === 1`。**P1 无调用方**（D4）。
- `Files::settle_purged( int $file_id ): bool`（`:731`）—— `UPDATE ... SET lifecycle='purged', storage_state='deleted' WHERE id=%d AND lifecycle<>'purged'`，返回 `affected === 1`。注意条件是 `<> 'purged'`，所以 `deleting` 与 `active` 都能被它收尾——这是「内核与观察者并发也幂等」的来源。
- 两者都是「谁先改到谁赢」，所以内核与观察者可以并发，天然幂等；**不需要任何进程内布尔标记**。

### 3.3 settle() 的两条铁律

- **先决出胜者，再动容量**：`Quota::adjust_used()` 只在 `settle_purged()` 返回真时调用，所以绝不会双扣。两个例外不调：`charged_bytes <= 0` 的行（从没占过容量），以及没注入 `Quota` 的调用方（构造函数允许 `null`，只用于测试）。
- **事务里回滚就整笔回滚**：`artifacts` 删除、`settle_purged()`、`adjust_used()` 必须同事务（`Deletion::settle()` 用 `Db_Transaction`）。抢不到互斥 → 回滚并 `return false`（这是正常并发，不是错误）；写库失败 → 回滚 + 写 `result='failed'` 事件。**结算绝不用 `Files::set_lifecycle()`**：它没有互斥语义，只适合流程状态（申请单、单据状态），拿它结账会双扣。

### 3.4 为什么 `Executor::complete_purge()` 不调 `settle()`

`complete_purge()`（`Executor.php:782`）已经在自己开启的 `Db_Transaction` 里，并持有 `delete_request_items` 的行锁；再调用 `settle()` 会嵌套事务（MySQL 里第二次 `START TRANSACTION` 会隐式提交外层），把「单据状态 + 容量」的原子性拆散。所以它复用同一互斥函数与同一条扣减规则：先 `$wpdb->delete()` 删 artifacts，再 `$lifecycle_ok = Files::settle_purged()`（`:811`），**只有 `$lifecycle_ok` 才** `Quota::adjust_used( -charged_bytes )`。抢不到时复查该行：若已是 `purged`（观察者先结算了）→ 标 `done / purged` 并提交；否则整体回滚并标 `failed / ledger`。

还有一种情况：单据行已经被别的 worker 关掉（`state` 不在 `queued / executing / deleting` 三态内），`complete_purge()` 直接 `return true` —— 那是幂等收单，不写任何账。

这条分工回答的问题不同：`settle()` 回答「这次删除该退多少」，`complete_purge()` 回答「这张申请单执行到哪一步」。**容量能不能退，永远由同一个条件更新决定。**

## §4 内核 API

### 4.1 已实现（P1）：`src/UserFiles/Services/Deletion.php`

`settle()` 的流程（`:122-171`）：`Files::get_by_id()` 取行 → 无行或已 `purged` 返回 false → 事务 → 删 `artifacts` → `settle_purged()` 抢互斥，失手即回滚返回 false → 胜者 `adjust_used( owner_id, -1 * charged_bytes )` → 提交 → 写 `purged` 事件（`record()` `:187`）。容量写失败时**先回滚、后写 `failed` 事件**：`record()` 故意留在事务外，否则回滚会把审计一起带走。

### 4.2 已实现（P3，1.28.5-beta-5）：内核与两个值对象

```php
final class Deletion_Context {
    // __construct( $mode = 'full', $actor_id = 0, $reason = 'operator',
    //              $sync_remote = false, $notify_owner = false,
    //              $via = '', $keep_request = false, $note = '' )
    public string $mode;         // 'full' | 'remote_only' | 'takedown'
    public int    $actor_id;     // 当前用户；0 = 系统路径
    public string $reason;       // operator | request | moderation | cleanup
    public bool   $sync_remote;  // true = 同步删远端并逐个 head 校验；false = 交给 Delete_Jobs
    public bool   $notify_owner; // takedown 强制 true
    public string $via;          // 审计来源；空则按 mode/actor 推断
    public bool   $keep_request; // 执行器拥有 item 行时置 true，内核不作废在途申请项
    public string $note;         // 写进审计 `via:reason|note`
}

final class Deletion_Result {
    // 逐项：target / status(deleted|missing|denied|partial|in_progress) / file_id / attachment_id / error
    // 汇总：counts() 给 deleted / missing / denied / partial / in_progress / total
    // 便捷：deleted() / denied() / partial() / succeeded() / first_status() / first_error() / message()
}
```

`Deletion::delete( array $targets, ?Deletion_Context $ctx = null ): Deletion_Result` 逐项流程：

1. **解析**：`int` / 数字串 → 先 `Files::get_by_attachment()`（`:163`）再 `Files::get_by_id()`（`:190`）；字符串 → 对象 key（再反查附件）；数组可显式给 `attachment_id` / `file_id` / `key`。
2. **早退**：行已 `purged` → `missing`（并记审计 `missing`）；什么都没解析到 → `missing` + `unresolved`。
3. **`remote_only`** → `delete_remote_only()`：只删对象键，不动附件与台账。
4. **权限**：`actor_id <= 0`（cron / 队列 / CLI）视为系统路径直接放行；否则 `user_can( $actor, DELETE_FILES )` 且 `user_can( $actor, 'delete_post', $id )`（`src/UserFiles/Capabilities.php:43`），不符 → `denied`，不写库。
5. **抢占**：`claim()` → `Files::claim_deleting()`；`keep_request` 为假时顺手作废在途申请项（`failed / attachment_gone`，D11）。已是 `deleting` → `in_progress`；抢不到再读一次：`purged` → `missing`、`deleting` → `in_progress`、其余 → `denied`（error `claim`）。
6. **冻结对象键**：`collect_keys()` 必须在删附件**之前**跑 —— 观察者会清 `_sakura_imgopt_s3_objects`；缺失时用 `Storage_Adapter::attachment_files()`（`:274`）推导。
7. **删附件**：`remove_attachment()` —— 先 `Deletion::flag()` 记下 reason/note/actor/via，再挂 `sufm_allow_attachment_delete`（`sync_remote` 时再挂 `sufm_skip_remote_enqueue`）包住 `wp_delete_attachment( $id, true )`，结束后摘滤器；附件仍在 → `partial / attachment_kept`。
8. **远端**：`sync_remote` 且有键 → `Storage_Adapter::delete_keys()`（内部走 `Remote_Operation_Guard`）+ `objects_exist()` 逐个 `headObject` 校验；未确认 → `partial` + `enqueue_remote_retry()` 入 `nb_sio_s3_deletes`。
9. **结算**：`settle()`；观察者可能已结算，`settle_purged()` 返回 0 时按幂等处理；结算后仍未 `purged` → `partial / ledger`。
10. **审计**：`settle()` 写 `purged` / `failed`；内核另补 `missing` / `partial`（`audit()`）。

第 7 步会重入观察者（`deleted_post`）并先结算，第 9 步再结算是幂等的 —— 这正是把「谁负责结算」这个问题消灭掉的做法。

## §8 风险与取舍

1. **闸门保留 = 插件成为删除的必经通道。** 这是有意的取舍：除管理员（唯一持有 `sufm_admin_delete_files` 的角色）与插件执行器（走 `sufm_allow_attachment_delete` 放行）外，其余删除都会被拒绝——包括作者删自己刚传的图、编辑在媒体库批量清理、第三方插件/脚本直接调 `wp_delete_attachment()`、以及 `wp post delete` 没带 `--user=管理员`；无台账行或已 `purged` 的附件不受闸门限制（D1）。代价是每条新删除路径都要记得带对身份或用内核。**已配套**：① 管理员可以在媒体库直删（P1）；② P2 给带理由与通知的下架动作；**还缺**：CLI 文档写明 `wp post delete` 要带 `--user`，以及非管理员提示必须指向申请流程。权限事实备查：`delete_post` 是 meta 能力，删自己的附件（`post_status=inherit`）只需 `delete_posts`，删别人的要 `delete_others_posts`；默认带 `delete_posts` 的是 administrator / editor / author / contributor，subscriber 没有。**所以闸门真正挡住的是 editor / author / contributor**——他们核心层本来能删自己的附件，现在必须走申请；订阅者本来就删不了，闸门对它没有增量。
2. **在途申请与外部删除冲突。** 用户刚提交申请，管理员又在媒体库删了：P1 的兜底是执行器读到 `purged` 就收单（D11）；P3 内核再加显式作废（`failed / attachment_gone`）。必须补这条测试。
3. **远端删除天生异步。** 媒体库删除后桶里可能还要 1–2 分钟才消失（`delete_attachment` → `Delete_Jobs` → `Delete_Worker`）。同步中心用 `sync_remote=true` 同步删并校验；媒体库与 P2 的下架用异步（不阻塞）。界面文案要区分「已删除」与「已受理，远端删除进行中」。
4. **CDN 缓存。** 桶对象删掉后 `doge.nboke.com` 上的旧 URL 可能仍可访问到缓存过期。插件没有刷新能力，需要多吉云刷新 API 密钥（另立）。短期在确认框里提示缓存 TTL。**P2 的下架文案不能承诺「立即打不开」。**
5. **`no_local_saving=true`（上传后删本地）站点**没有本地副本可删，内核要把它当 `missing` 而不是失败。生产当前是 `false`。
6. **批量删除的量。** 同步中心批量上限 200（§5.3）；P2 的媒体库下架同样按 200/次分批，超出提示分批执行。
7. **不删桶里的孤儿。** 本地删除失败但远端已删（`partial / remote_unverified` 的反向）不会产生孤儿；反过来远端删失败会留下孤儿对象，由同步中心「仅云端」行清理，这是允许的第二条路径（D6）。
8. **「直删」与「下架」是两种语义，不要混用文案。** P1 的媒体库直删是管理员自助（不写理由、不通知）；P2 的下架是合规手续（必填理由、写审计、通知作者）。审计表里靠 `reason` 区分，界面文案也必须区分，否则事后分不清「清理」与「处置」。
9. **`lifecycle='deleting'` 时闸门曾会拒。** `may_delete_directly()` 只认 `active`；P3 起 `guard_delete()` 对 `deleting` 行放行持有 `DELETE_FILES` + `delete_post` 的人（交给内核幂等收尾），REST 路径返回 `sufm_deleting`（409，「该文件正在删除中，请稍后刷新查看结果。」），不再误用「无权限」文案。
