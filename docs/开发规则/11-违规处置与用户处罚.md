## §0 为什么需要这一页

四个症状，一个根因。

1. **能删不能罚。** 管理员已经能在媒体库把违规文件「违规下架（删除本地与云端）」（`Media_Hooks.php:797` 的批量动作、`:891` 的 `handle_takedown()`），删除、结算、审计、通知一条龙都通。但删完之后没有任何后续手段：上传者收不到一封邮件、账号不受任何影响，换个用户名继续传。
2. **「通知」其实没有通道。** 下架通知走 `Notifications::enqueue()` → `Notifier::deliver_due()` → `Notifier::theme_message()`，而 `theme_message()` 只调 `\ZibMsg`（`Services/Notifier.php:225-254`，类名与方法的过滤器在 `:230-231`）。非子比主题下取不到 → 返回 0 → `mark_failed('no_adapter')`（`:211`）→ 退避重试 6 次后置 `dead`（`Repositories/Notifications.php:124`）。**所以「没有邮件通知」不是缺一个开关，是 outbox 从一开始就只有一条腿。**
3. **子比的「小黑屋」不等于「禁止登录」。** 主题的登录限制只挂在 `template_redirect`（`zibll/inc/functions/user/user-ban.php:840`），把前台页面替换成禁封页；全主题没有任何 `authenticate` / `determine_current_user` 钩子 → 它**拦不住 wp-login.php、wp-admin、REST 与 XML-RPC**。`[已验证 user-ban.php:802-841、default-filters.php:516-522]`
4. **换主题即失效。** 前台的文件空间面板是挂在主题过滤器 `main_user_tab_content_files` 上的（`Space_Panel.php:28`），换个主题这个钩子根本不会触发；zibll 的封禁函数也随主题消失。

根因：**「处置」（删文件）、「判决」（罚账号）、「执行」（拦行为）三件事被塞进了同一个主题内功能。** 于是要么依赖 zibll（换主题就断），要么什么都不做。

这一页只解决第二、第三件：**判决与执行**。处置仍归 09，本页不改删除内核、不改结算、不改下架入口的判据。

## §1 结论（先看这十条）

**S1 三层解耦，不做单体「封禁按钮」。** 处置 = 删除（09 已有）；判决 = 在 `nb_sufm_sanctions` 写一行带期限、理由、操作者的处罚；执行 = 在四个固定点读这张表并拦截。判决表是唯一权威，执行点只是读者，主题只是可选执行器。`[设计决定]`

**S2 主题无关的底线在插件自己的上传入口，不是砍能力。** 处罚期**不动** `sufm_manage_own_files`、不动 `Rest\Controller::can_use_files()`（`:615`）。封禁期用户必须仍然能列文件、删文件、看容量——否则他连清理自己的东西都做不到，等于把人锁死在违规内容旁边。规则是「禁增、允许删」。`[已验证 Controller.php:615；Uploader.php:109-145]`

**S3 执行点只有四个半，位置固定。**

| 代号 | 拦截点 | 拦什么 | 主题依赖 |
|---|---|---|---|
| E1 | `Services/Uploader.php:109 handle()` 入口 | 文件空间上传（REST、编辑器 Picker、前台表单） | 无 |
| E2 | `Media/Media_Hooks.php:1112 guard_media_upload()` | 媒体库 / 主题上传 | 无 |
| E3 | `authenticate` 过滤器（priority < 20） | 用户名密码、邮箱、应用密码登录 | 无 |
| E4 | `determine_current_user`（priority 99） | 已登录会话立即失效 | 无 |
| E5 | `wp_authenticate_application_password_errors`（`user.php:478`） | REST Basic Auth / 应用密码绕过 | 无 |
| E6 | `zib_updata_user_ban()` | 站点级镜像（可选） | **仅 zibll** |
| E7 | `Space_Panel` 前台提示 | 告知处罚与申诉入口 | **仅 zibll**（见 §5.5） |

**S4 下架 ≠ 处罚。** 版权投诉场景上传者可能无辜，默认只通知、不处罚；处罚必须在弹窗里显式勾选。`[设计决定]`

**S5 处罚必须有期限、可撤销、可申诉、有审计。** 没有期限的封禁等于把账号判死刑，而管理员三个月后早忘了这回事。永久处罚必须二次确认，并且**对 `manage_options` 用户直接拒绝**（防自锁）。

**S6 到期必须懒判定，cron 只补状态。** 项目已定「不用 WP-Cron 承担关键兜底」；而且封禁到期后用户下一次上传就该立刻放行，不能等 `sufm_tick`。做法：每次读都判 `ends_at`，命中过期就地 `UPDATE ... SET state='expired'`（条件更新判胜负），`Module::tick()`（`:326-353`）里再跑一遍 `expire_due()` 只负责「补状态 + 发到期通知」。`[已验证 Module.php:326-353；参照 Files::settle_purged 的条件更新写法，见 09 的 D3]`

**S7 站点级登录封禁由插件原生兜底，zibll 只做镜像。** 理由见 §0 第 3 条：主题拦不住登录。把登录封禁交给 zibll 等于没封——用户照样进 wp-admin、照样用 REST。所以 E3/E4/E5 是主力，E6 只负责「让前台显示禁封页 + 让主题的用户中心一致」。

**S8 邮件是可选通道，而且必须「可见」。** 本站 `wp_mail()` 今天必然失败（§7.1，决定性事实）。所以 P1 不承诺邮件可达：先做 in-app 通知 + 后台「发送测试邮件」+ 失败计数暴露，邮件通道等 SMTP 装好再开。

**S9 批量按 owner 聚合。** 一批 200 个文件可能属于 N 个用户。现在的 `notify_takedown()`（`:1005-1026`）每个附件 enqueue 一条，200 文件就是 200 条通知——处罚必须改成「按 owner 聚合成 1 个 sanction + 1 条通知 + 1 个 operation_id」。只有 `Deletion_Result::DELETED` 的项进处罚，`missing` / `partial` 不进。

**S10 只按用户，不做 IP 关联。** IP 是共享的（校园网、公司出口、移动基站），按 IP 封会误伤整栋楼；账号才是可申诉的主体。`[设计决定]`

## §2 术语与边界

| 术语 | 指什么 | 归谁 |
|---|---|---|
| 处置 / 下架（takedown） | 删除本地文件 + 桶对象 + 附件 + 台账结算 + 审计 | 09，本页不动 |
| 判决 / 处罚（sanction） | `nb_sufm_sanctions` 的一行：类型、范围、理由、起止、状态 | 本页 |
| 执行器（enforcer） | 把判决变成实际拦截的代码或主题函数 | 本页 |
| 申诉（appeal） | 被罚用户请求复核，独立于处罚状态的一条轴 | 本页（P2） |

**本页明确不做的事：**

1. 不做「案件表 + 处罚表」两张表（理由见 §3.5）。
2. 不改删除内核、不改 `Deletion_Context`、不改下架的准入判据（那属于 09）。
3. 不做自动封禁。阶梯只提供**预选值**，永远由管理员点确认。
4. 不做 IP 关联、不做设备指纹、不做跨站处罚（多站点只写 `blog_id`，不继承）。
5. 不在处罚期回收用户已有内容（不隐藏他的文章、不删他的评论）——那是另一个域，且会扩大误伤面。
6. 不新增 cron（复用 `sufm_tick`），因此也不需要动 `Deactivation`；但**新增表必须进 `Schema::tables()`**，卸载会自动 DROP（`Uninstaller.php:160-168` 遍历 `Schema::tables()`）。

## §3 数据模型

### 3.1 表 `nb_sufm_sanctions`

表名走 `Schema::table( 'sanctions' )`（`Schema.php:67`）。DDL 草图（`$charset` 与其余表一致，取自 `Schema.php:401-417` 的写法）：

```sql
CREATE TABLE {prefix}sufm_sanctions (
    id bigint(20) unsigned NOT NULL AUTO_INCREMENT,
    blog_id bigint(20) unsigned NOT NULL DEFAULT 0,
    owner_id bigint(20) unsigned NOT NULL DEFAULT 0,
    actor_id bigint(20) unsigned NOT NULL DEFAULT 0,
    operation_id varchar(64) NOT NULL DEFAULT '',
    type varchar(20) NOT NULL DEFAULT '',
    scope varchar(20) NOT NULL DEFAULT 'plugin',
    reason_code varchar(32) NOT NULL DEFAULT '',
    note text NOT NULL,
    starts_at datetime NOT NULL DEFAULT '0000-00-00 00:00:00',
    ends_at datetime NULL DEFAULT NULL,
    state varchar(20) NOT NULL DEFAULT 'active',
    source varchar(20) NOT NULL DEFAULT 'manual',
    enforcer varchar(20) NOT NULL DEFAULT 'native',
    adapter_ref varchar(64) NOT NULL DEFAULT '',
    appeal_state varchar(20) NOT NULL DEFAULT 'none',
    appeal_note text NOT NULL,
    appeal_at datetime NULL DEFAULT NULL,
    appeal_decided_by bigint(20) unsigned NOT NULL DEFAULT 0,
    appeal_decided_at datetime NULL DEFAULT NULL,
    notified_at datetime NOT NULL DEFAULT '0000-00-00 00:00:00',
    expired_notified_at datetime NOT NULL DEFAULT '0000-00-00 00:00:00',
    created_at datetime NOT NULL DEFAULT '0000-00-00 00:00:00',
    updated_at datetime NOT NULL DEFAULT '0000-00-00 00:00:00',
    revoked_at datetime NULL DEFAULT NULL,
    revoked_by bigint(20) unsigned NOT NULL DEFAULT 0,
    meta longtext NOT NULL,
    PRIMARY KEY  (id),
    KEY owner_state (owner_id,state,ends_at),
    KEY state_ends (state,ends_at),
    KEY operation (operation_id)
) {$charset};
```

**`ends_at` 用 NULL 表示永久，不用 `'0000-00-00'`。** 依据：`Schema.php:453-478` 的 `space_grants.expires_at` 已经是 `datetime NULL` 语义，仓库里「可空时间」的先例就是它；零日期会让 `ends_at > '2026-11-22 00:00:00'` 这类比较在多处产生歧义。`[已验证 Schema.php:453-478]`

**为什么表结构这么像 `space_grants`：** 它已经是这个仓库里「带期限、带状态、带 attempts/last_error、可撤销」的成熟形态，处罚是同一个模式。不要去发明第二套字段风格。`[已验证 Schema.php:453-478]`

### 3.3 索引与查询

- 唯一的读路径是 `owner_id + state`，所以 `KEY owner_state (owner_id,state,ends_at)` 必建；它的形状照抄 `space_grants` 的 `KEY owner_state (owner_id,state,expires_at)`（`Schema.php:474`）。它是每个请求都可能踩的路径（E1/E2 每次上传都查一次）。
- `KEY state_ends (state,ends_at)` 只服务 `expire_due()` 的扫描（`WHERE state='active' AND ends_at <= now LIMIT 50`）——`owner_state` 以 `owner_id` 开头，覆盖不到这种全表扫描。两个索引不冗余。
- **不要** `SELECT *` 后丢弃。E1 只需要一行 `id`（判断是否有 active 行），用 `SELECT id ... LIMIT 1`。
- 判定函数签名建议：`Sanctions::blocks( int $owner_id, string $type ): bool`，一次查询同时处理 E1/E2（`upload_ban` 与 `full_ban` 合并成一个 IN 列表）。
- **不要走对象缓存。** 生产站启用了 `object-cache-pro`（`wp plugin list` 已确认）；处罚状态是「秒级要生效」的数据，撤销后必须立刻放行。直接 `$wpdb` 查表（与 `Files::settle_purged()` 的写法一致），不要 `wp_cache_get`，也不要用 `get_option`。`[已验证生产插件清单]`

### 3.4 与 events 的关系：用 `operation_id` 当批次号，**不要用 `batch_id`**

`nb_sufm_events` 的 `batch_id`（`Schema.php:407`）语义已经被**审核批次**占用：`Executor.php:203-209` 建批次行、`:262` 写事件、`Requests.php:987` 读它。下架批次如果也写 `batch_id`，两类批次会在同一个整数字段里撞车。

正确做法：`operation_id`（`varchar(64)`，`Schema.php:408`；`Events::log()` 会 `substr(...,0,64)`，`Events.php:43`）本来就是给「跨行串联」用的字符串，`Media_Mover.php:153` 已经在用 `'media:' . $id` 的先例。下架批次号建议 `takedown:{YmdHis}-{actor_id}`，同批的每条 `delete` 事件与每条 `sanction` 事件都写同一个值。`[已验证 Executor.php:203-209/262、Requests.php:987、Events.php:43、Media_Mover.php:153]`

**实现要点：** `Deletion_Context` 没有 `operation_id` 字段（构造签名 `Deletion_Context.php:112` 只有 mode/actor/reason/sync_remote/notify_owner/via/keep_request/note），所以批次号必须在 `handle_takedown()` 内部生成，然后分别传给 `log_takedown()`（`:1038`）与新的处罚写入函数。**不要去改 `Deletion_Context`**——那会把 09 的核心值对象拖进本页的改动面。

### 3.5 为什么不做案件表

一张 `sanctions` 就够，因为「证据」已经存在别处：

- 谁在什么时候以什么理由删了什么 → `nb_sufm_events`（`action=delete`、`safe_detail=plugin:moderation|理由：备注`，`Media_Hooks.php:1038-1053`）。
- 谁在什么时候罚了谁、多久、什么理由 → 同一张 events（`action=sanction`，`subject_id` = 被罚用户）。
- 两者靠 `operation_id` 串起来，一条 SQL 就能还原整件事。

单独建「案件表」只会多一份需要同步的状态，而它记的东西没有一条是 events 里没有的。`[设计决定；依据 09 §6「审计一条一行」]`

## §4 状态机与懒到期

```
           ┌──────────┐  ends_at <= now（读时或 tick）  ┌──────────┐
  新建 ──▶ │  active  │ ───────────────────────────▶ │ expired  │
           └────┬─────┘                              └──────────┘
                │ 管理员撤销（带理由）
                ▼
           ┌──────────┐
           │ revoked  │
           └──────────┘
```

规则（**P1 已实现并验收，实测修正了下面第 2、3 条的原设计**）：

1. **`active` 是唯一会被执行器读取的状态**；`expired` / `revoked` 一律视为「没有处罚」。
2. **过期是懒判定，而且读路径只翻状态、不做别的事。** `Sanctions::blocking()` 在 SELECT 之前先跑一条按谓词的 UPDATE：
   `UPDATE ... SET state='expired', updated_at=... WHERE owner_id=%d AND state='active' AND ends_at IS NOT NULL AND ends_at <= %s`，然后照常 `SELECT ... WHERE state='active' AND (ends_at IS NULL OR ends_at > %s)`。
   **这条 UPDATE 是有意不带 `type IN (...)` 的**：过期就是过期，不因为调用方问的是哪一类就只清那一类（否则 `login_ban` 会以不同方式腐烂）。`[P1 实测：`src/UserFiles/Repositories/Sanctions.php` 的 blocking()；曾经只在 SELECT 之后补 expire()，永远不可能命中，因为 SELECT 已把过期行过滤掉了]`
   **读路径不写审计、不发通知**：`expire_due()` 才是收尾的人（第 3 条）。理由见第 3 条的水位设计。
3. **`sufm_tick` 是唯一收尾者，水位只有 `expired_notified_at` 一个。** `due_to_expire()` 的候选条件是
   `state IN ('active','expired') AND ends_at IS NOT NULL AND ends_at <= now AND (expired_notified_at = 零值 OR IS NULL)`；
   `expire_due()` 对每行先做幂等的 `expire()`（active→expired，已是 expired 时是无操作），读回确认 `state='expired'`，再看 `expired_notified_at` 是否为空——为空才「写一条 `sanction/expired` 审计 + 排一条到期通知 + 打水位」。
   **为什么候选集不能只查 `state='active'`**：每一个被拦下的上传都会先经 `blocking()` 把行翻成 `expired`，所以「用户自己在封禁期试着上传一次」就会让这行从 tick 的视野里消失，那条「你的处罚已到期」永远发不出去。水位必须挂在 `expired_notified_at` 上，不能挂在状态上。
   **为什么审计与通知共用同一个水位**：分成两个水位的话，中间崩一次就会出现「有审计没通知」或「有通知没审计」。`[P1 实测验收：/tmp/sufm-sanction-accept7.php 的「tick() 补写 expired 审计」「tick() 写了 expired_notified_at」「tick() 幂等，不重复通知」]`
   对 `enforcer='zibll'` 的行，tick 另做一次 `function_exists` 守卫下的镜像清理（§6）。
   **tick 不参与拦截判断**——它挂了用户也该被拦（懒判定兜底）。
4. **撤销**：只允许 `active → revoked`；已 `expired` 的不能撤销（没有意义，且会让审计出现「先过期又撤销」）。撤销写 `sanction/revoked` 审计 + 一条通知，并同时清镜像（§6 的顺序）。
5. **永久处罚**（`ends_at IS NULL`）不会被 tick 碰，只能人工撤销。所以界面上永久档位必须比 30 天档位难点到（二次确认 + 输入用户名）。
6. **警告（`warn`）没有窗口。** `apply()` 对 warn 强制 `days = 0` 且**不写 `ends_at`**，所以「`ends_at` 为空」在这里同时代表「永久」和「警告」两种情况——`describe()` / `badge()` 必须在判断 `ends_at` **之前**先按类型分支，否则用户页签会出现「已警告 · 永久」。`[P1 实测并已修：`src/UserFiles/Services/Sanction_Service.php` 的 describe()/badge()]`

## §5 执行点

### 5.1 E1 文件空间上传（主力）

位置：`Services/Uploader.php:109 handle()` 的**最前面**，在 `:112-145` 的容量/文件夹/文件数/限流判定之前。

```php

    return new \WP_Error( 'sufm_sanction_upload', '账号当前处于处罚期，暂时不能上传新文件。你仍可删除已有文件。', array( 'status' => 403 ) );
```

要点：

- **不要**改 `Rest\Controller::can_use_files()`（`:615`）。它是 `Settings::entry_enabled() && Capabilities::can_manage_own()`，一旦在处罚期返回 false，整个文件空间（列表、删除、容量、申请）全部失能。`[已验证 Controller.php:615]`
- 错误文案必须写清「仍可删除已有文件」，否则用户以为账号废了。

### 5.2 E2 媒体库 / 主题上传

位置：`Media_Hooks::guard_media_upload()`（`:1112`），放在 `:1124` 的能力判断**之后**、类型白名单 `:1140` **之前**。


- 返回的是**原数组 + `$file['error']`**，不是 `WP_Error`——`wp_handle_upload_prefilter` 的契约就是改 `error` 字段（WordPress 会把它显示在上传失败提示里）。

### 5.3 E3 / E4 / E5 登录（P3）

**E4 `determine_current_user`，priority 99。**


## §6 子比适配器契约

只用已验证的函数与字段，逐条列清，避免「以为主题会替我们做」。

**调用前必须 `function_exists( 'zib_updata_user_ban' )`。** 函数在 `zibll/inc/functions/user/user-ban.php:86`，通过 `inc/functions/user/user.php:15-27` 的 `zib_require` 无条件加载（`inc/inc.php:67-81` 就是裸 `require`），因此 wp-admin、admin-ajax、REST、WP-Cron 里都可用；**但换主题就没有**。`[已验证]`

**写入：**

```php
zib_updata_user_ban( $owner_id, 2, array(
    'time'          => current_time( 'mysql' ),
    'banned_time'   => $ends_at ? $ends_at : '',   // ''/0 = 永久
    'operator_id'   => get_current_user_id(),
    'reason'        => $reason_text,
    'desc'          => $note,
    'no_appeal'     => $no_appeal,          // 可选
    'no_appeal_desc'=> $no_appeal_desc,     // 可选
) );
```

- `$type`：`1` = 小黑屋（失去发布/评论等权限），`2` = 禁封（不能登录）。**站点级登录封禁用 `2`。** `[已验证 user-ban.php:607-614]`
- 字段默认值在 `:96-107`：`type` / `time` / `banned_time` / `operator_id` / `reason` / `desc` / `no_appeal` / `no_appeal_desc`；写 `banned` / `banned_time` 在 `:93-94`，追加 `banned_log` 在 `:110-116`，最后 `:118 do_action('updata_user_ban', ...)`。
- **`type=2` 不会发主题站内信**：`zib_updata_user_ban_msg()` 的 `:173 if ( 2 != $type )` 只对 `0` / `1` 发 `ZibMsg::add()`。但**邮件不受这个 if 保护**：`:179-182` 仍然 `@wp_mail(...)`（`_pz('email_updata_user_ban', true)`，默认开）。而本站没有 MTA → 这封邮件静默失败。`[已验证 user-ban.php:122-184]`
- **`type=0`（解封）会发一封「已解封」站内信**（`:137-139`），也会 `do_action`（`:118` 在 if 外）。
- **`banned_log` 不是独立的 usermeta 行。** 它在 `zibll/inc/dependent.php:272` 的特殊键表里，由 `zib_get_user_meta()` / `zib_update_user_meta()`（`:328-348`）改走 option meta（`:425-487`），实际存在 usermeta 键 **`zib_other_data`** 的数组里。**不要**写 `get_user_meta( $uid, 'banned_log', true )` 然后当数组用——你会永远拿到空。`[已验证 dependent.php:272/328-348/425-487]`
- **不要用 `zib_user_is_ban()` 做探测。** 它是带副作用的读函数：`:37-40` 发现过期会直接调 `zib_updata_user_ban($uid, 0, ...)`，触发「到期自动解封」站内信 + 邮件。我们的判定只读自己的表。`[已验证 user-ban.php:29-43]`

**镜像带来的重复通知：** 若我们同时发自己的 in-app 通知，`type=2` 不会重复（主题不发）；`type=0` 解封会重复一条——解封时把 `enforcer='zibll'` 的行交给主题发，我们不再发。

**写入/清除顺序（重要）：**

- 建处罚：**先写权威表 → 再写镜像 → 最后发通知**。镜像失败只记日志，不回滚处罚（表是权威，用户仍被 E1/E2 拦）。
- 解封：**先清镜像 → 再改表 → 最后发通知**。理由：镜像残留的后果是「前台还显示禁封页」，比「表已解但前台仍封」更严重；先清镜像让用户立刻可用。

**换主题后的「幽灵封禁」：** 切到非 zibll 后，`banned` / `banned_time` / `zib_other_data.banned_log` 都还在库里，但没有读者 → 无害。切回 zibll 时它们会立刻复活（主题的 `zib_user_is_ban()` 只看 meta）→ 所以我们自己写镜像时必须把 `banned_time` 写成真实到期时间，让主题的懒到期（`:37-40`）能自己清掉。**不要**让镜像变成永久，除非处罚本身是永久。

**不改 `zib_user_can` 过滤器。** 主题在 `user-ban.php:744-751` 挂了 `zib_ban_user_can_filter`，被封用户 `zib_user_can()` 全 false。这是主题自己的体系，插件不参与；我们要封的是「上传」而不是「整套能力」，混进去会让排查变难。

## §7 通知与邮件

### 7.1 本站发信能力：今天一定是坏的

`[已验证 2026-11-22 生产站]`

- `sendmail_path` 指向 `/usr/sbin/sendmail -t -i`，但**这个文件不存在**；25 / 587 端口无监听；没有 `/etc/postfix`、`/etc/exim`。
- `wp-config.php` 里没有任何 `SMTP_*`、`WP_MAIL_*`、`DISABLE_WP_CRON` 常量。
- 启用插件只有 4 个（tinymce-advanced、object-cache-pro、query-monitor、sakura-tools），**没有 SMTP 插件**。
- 子比主题里 20 处 `@wp_mail(...)`（含封禁邮件 `user-ban.php:181`、注册/找回密码 `zib-email.php` 多处）全部带 `@` 抑制错误 → 全部静默失败。

结论：**「加个邮件通知」不等于加一行 `wp_mail()`。** 必须先解决发信通道（装 SMTP 插件或装 MTA），插件侧要做的是：**把「发不出去」这件事变成可见的**。

### 7.2 `notifications` 加 `channel` 列

现在的表（`Schema.php:418-438`）没有 channel 列，一行一个事件。如果 in-app 与 email 共用一行，状态会互相污染——`mark_sent()` 把 `attempts` 硬写 1（`Notifications.php:97`），`mark_failed()` 走指数退避（`:124`），两边各算一半，最后谁也说不清。

做法：

- `ALTER TABLE ... ADD channel varchar(10) NOT NULL DEFAULT 'inapp'`，Schema `VERSION` 从 `1.6.0`（`Schema.php:29`）升到 `1.7.0`。**不需要手写 ALTER**：`install()` 对每条语句调 `dbDelta()`（`Schema.php:99`），建表与加列走同一条路，只要 bump `VERSION`，`maybe_install()`（`:78`）就会跑一遍。`[已验证 Schema.php:78-100]`
- `dedupe_key` 组成改成 `sanction:{id}:{channel}`；下架那边从「每附件一条」改成聚合后 `takedown:{blog_id}:{owner_id}:{batch}`（§7.3）。
- `Notifications::enqueue()`（`Notifications.php:35`）加第 6 个参数 `$channel = 'inapp'`；`Notifier::deliver_due()` 按 channel 分派：`inapp` → `theme_message()`（现状），`email` → 新的 `mail_message()`。
- 失败原因分开记：没有主题适配器仍然是 `no_adapter`；邮件失败记 `mail_failed`（配合 `wp_mail_failed` 动作抓真实原因）。两种都必须在后台可见。

### 7.3 聚合与限频

- **聚合**：`handle_takedown()`（`Media_Hooks.php:891`）现在逐条 `notify_takedown()`（`:1005-1026`，dedupe 里带 `attachment_id`），200 文件 = 200 条。改成先收集 `$by_owner[ $owner_id ] = array( 'count' => n, 'reason' => $detail )`，循环结束后每个 owner enqueue 一条。只有 `Deletion_Result::DELETED` 进集合（`:981` 已经是这个判据）。
- **处罚通知**：一次处罚 = 一条通知（`sanction:{id}:inapp`），文案含类型、起止时间、理由。
- **限频**：同一用户 24h 内同类邮件最多 1 封。复用 `Rate_Limiter::exceeded()`（`Services/Rate_Limiter.php:64`，签名 `( int $owner_id, string $bucket, string $period, int $count, int $bytes, int $add=1, int $add_bytes=0 ): bool`），bucket 用 `sanction_mail`、period 用 `day`；`rate_limits` 表已有 `UNIQUE owner_bucket_period`（`Schema.php:450`），不用新表。`[已验证 Rate_Limiter.php:64、Schema.php:439-452]`

### 7.4 邮件内容（不含文件名/路径）

与 09 §6「审计不写路径与对象键」同一口径，邮件也不列文件名——列了等于把违规内容再传播一次，而且收件人自己知道传了什么。

必含：站点名、被下架的文件数（不给清单）、下架理由文案（`takedown_reasons()` 的 6 种，`Media_Hooks.php:66-75`）、处罚类型与起止时间、申诉方式、客服联系方式。

不写：文件名、路径、对象 key、附件 ID。

### 7.5 「发送测试邮件」按钮（P3，但建议提前）

后台加一个按钮：调 `wp_mail()` 发到当前管理员邮箱，同时挂 `wp_mail_failed` 抓错误并显示。**这一条比任何邮件功能都优先**——没有它，「通知发了没」永远是个谜。

## §8 处罚阶梯

只做**预选**，不自动执行。

| 30 天内第几次 | 预选档位 | 理由 |
|---|---|---|
| 1 | `warn`（只通知，不拦） | 首次可能是误传、可能是版权方投诉而作者无辜（§1 S4） |
| 2 | `upload_ban` 7 天 | 短期、可感知、不影响已发布内容 |
| 3 或 `reason_code=copyright/illegal` | `upload_ban` 30 天，或 `login_ban` 7 天（需显式勾选） | 重复违规或性质严重 |
| 永久 | `full_ban`，`ends_at=NULL` | **必须**输入用户名二次确认；对 `manage_options` 用户直接拒绝 |

计数来源：`nb_sufm_sanctions` 里该用户 `created_at >= now - 30 days` 的行数（`warn` 也算一次，因为它是已确认的处置）。**不要**用 events 计数——events 里一次下架可能有多行（按文件），会把次数放大。

**对 `manage_options` 用户直接拒绝**，不是「弹个警告」。自锁是这类功能最典型的事故：管理员罚了另一个管理员，然后对方把你也罚了，最后没人能进后台。要解只能用数据库。

**永久处罚的入口只放在「用户」页签**（§10），不放在下架弹窗里——弹窗里前端根本不知道上传者是谁（§10.1）。

```php
$this->events->log( array(
    'actor_id'     => get_current_user_id(),
    'owner_id'     => $target_id,     // 便于按用户查（KEY owner_id (owner_id,id)，Schema.php:416）
    'subject_id'   => $target_id,
    'operation_id' => 'sanction:' . $id,   // 上限 64，Events.php:43 会截断
    'action'       => 'sanction',
    'result'       => 'applied',           // applied | revoked | expired | appeal_accepted | appeal_rejected
    'safe_detail'  => 'plugin:sanction|' . $type . '|' . $days . '|' . $reason_code,
) );
```

下架那一批事件的 `operation_id` 用 `takedown:{YmdHis}-{actor}`，同批的每条 sanction 事件也写它（而不是 `sanction:{id}`）——这样「这批下架 + 这批处罚」一条 SQL 全出来。处罚自身的生命周期事件（撤销/到期）再写 `sanction:{id}`。

### 10.1 下架弹窗（`assets/media-folders.js:594 askTakedown`）

现状：理由下拉（`:600-604`，选项来自 `strings.takedownReasons`）、备注 textarea（`:605-606`，maxLength 120）、确认时追加隐藏字段 `sufm_takedown_reason` / `sufm_takedown_note` 再 `form.submit()`（`:607-613`，`takedownBypass` 防重入），提交拦截在 `:617-622`。服务端从 `$_REQUEST` 读（`Media_Hooks.php:901/912`，因为列表表格是 GET 提交）。

**P1 已实现**：一个复选框「同时处罚上传者（可选）」（默认不勾），勾上后展开类型（`warn` / `upload_ban`）与时长（7 / 30 天），理由沿用同一个 `reason_code` + 备注。提示文案明写「下架本身不代表上传者一定违规（例如版权投诉可能是误传）」。**`login_ban` 不在这个弹窗里**——它属于 P3 的站点级执行器。

**这里有一个无法回避的 UX 事实：** 弹窗只知道选中的附件 ID 列表，**不知道这些附件属于谁**（JS 里没有 owner 数据）。所以：

- 弹窗里**不能**做「输用户名确认永久」——前端拿不到用户名，只能提交后才知道。
- **P1 选择：弹窗内只允许 ≤30 天的处罚**，永久处罚必须去「用户」页签对该用户单独操作。这既绕开了未知 owner 的问题，也降低了「一次误点永久封 200 个文件的所有者」的风险。
- **服务端必须再夹一次天数**：`if ( Sanctions::TYPE_WARN === $ban ) { $ban_days = 0; } else { $ban_days = max( 1, min( 30, $ban_days ) ); }`。因为 `apply()` 把 `days=0` 解释为**永久**，而 `$_REQUEST` 是前端可控的——不夹的话手工构造 `?sufm_takedown_sanction_days=0` 就能把一次批量下架升级成永久封禁。`[P1 实测发现并已修，注释在 Media_Hooks.php 的 handle_takedown() 里]`
- 结果反馈并入现有 toast：`takedown_result_notice()`（`:1776`）现在只把结果塞 `sufmFolders.notice` 由 `media-folders.js` 弹 toast（后台样式未入队，`admin_notices` 会被文件夹栏盖住）。文案改成「已下架 N 个文件；已处罚 M 名上传者」。`[P1 已实现，URL 参数 sufm_takedown_sanctioned]`

### 10.2 用户页签（`assets/ui/js/pages/files-users.js:262 renderUsers`）

现状：4 列（用户、用量、文件数、容量输入+保存），数据来自 `GET /sufm/v1/admin/users` → `Controller::admin_users()`（`:2051`），行字段见 `:2091-2102`。该函数已经用「一次批量查询代替每行一查」的写法（`:2074-2079`）。

**P1 已实现**：

- 第 5 列「处罚」：一个按钮 + 徽标（有 active 处罚时显示「禁上传 · 剩 7 天」）。数据在 `admin_users()` 里**一次批量查**（`Sanctions::active_map( $ids )`，一条 SQL 带 `owner_id IN (...)`），不每行一查。行里还带 `can_sanction`——服务端算，UI 不渲染必然会被拒的按钮。
- 按钮打开一个自建 `<dialog class="sakura-dialog">`：类型、时长（7/30/永久）、理由、备注、阶梯建议、以及「撤销当前处罚」入口。永久档位要求输入该用户的 `user_login` 才启用确认按钮（`admin.ui.confirm` 没有表单能力，这个弹窗是手写的）。

**两个 P1 实测踩到的坑**（改这块前先读）：

1. **期限下拉的默认值不能无条件跟随阶梯建议。** 服务端 `durations` 的顺序是 7/30/0（0=永久），首项不是「默认」；而阶梯对首次违规返回 `days=0`（那是 `warn` 的语义，不是永久）。无条件执行 `daysSelect.value = suggestion.days` 会让新管理员一打开就看到「永久（需输入用户名确认）」。正确做法：先选第一个**有限值**，且只在 `type !== 'warn'` 时才套用建议天数。
2. **`warn` 时期限控件必须 `disabled`，提交时也必须强制 `days=0`。** 否则一个已经从「禁止上传」切回「仅警告」的表单会把之前选的 30 天一起提交上去。

### 10.4 媒体管理页（1.28.7-beta-21 新增，与媒体库并行的第二个下架入口）

**为什么再开一个入口，而不是把媒体库改造到底。** 媒体库的批量动作要经过 WordPress 自己的三层：网格与列表是两套选中模型（网格靠 `media-views` 的 Backbone `selection`，列表靠 `.tablenav` 的 checkbox），批量下拉要靠 `common.js` 的 `marryControls()` 把顶部与底部配成一对，下架又必须在 submit 前拦下来填理由。`assets/media-folders.js`（706 行）就是「在 core 的 DOM 上做加法」的产物，beta-20 修的那个 bug——树形导航用 AJAX 替换 `.tablenav` 整块，`marryControls()` 的绑定随之消失，底部下拉停在 `-1`，于是拦截器不认这次提交——正是这种耦合的代价（见 10-静态资源手册 §8）。**任何一次 WordPress 后台改版都可能重演。**

所以新页面从零渲染，**不读也不改 core 的任何 DOM**：数据全部来自 REST，交互全部是自己的。代价是媒体库里的下架入口继续存在（它现在是薄薄的一层映射，见 10.1），两个入口共用同一份服务层实现。

**页面身份**

| 项 | 值 |
|---|---|
| 模块 / 页签 | `files` / `media`（`admin.php?page=sakura-tools-files&t=media`） |
| 页面 id | `files-media`（决定 `assets/ui/{css,js}/pages/files-media.*` 的加载与 `[data-sakura-page]`） |
| 控制器 | `src/UserFiles/Admin/Media_Manager.php`（`TAB='media'`） |
| 视图 | `includes/views/userfiles-media.php`（`tests/ViewManifestTest.php` 的 `VIEWS` 清单里必须有一行） |
| 前端 | `assets/ui/js/pages/files-media.js`（883 行）+ `assets/ui/pages/files-media.css`（647 行） |
| gate | `'gate' => array( 'caps' => 'review' )` ⇒ `Capabilities::can_review()`。**只有 `'review'` 与 `'execute'` 两个字符串被 `Registry::tab_gate()` 认识，写别的会让页签永远不可见。** |
| 页头标语 | `src/Admin/UI/Hero.php::taglines()` 的 `files-media` 键，必须恰好一个 `<em>`（`HeroTaglineTest` 会断言） |

**注册方式与「五处」的关系。** 它没有走 `Layout::PAGES`——这个页面不用卡片布局，整页就是一块左右分栏。所以「新增页签要动五处」在这里是四处：`Registry::modules()` 的 tabs、`Media_Manager::register_hooks()` 里**立即**调用的 `Registry::register_renderer( 'files', self::TAB, ... )`（必须在 `register_hooks()` 里同步执行，不能等 `admin_init`：`Admin\Menu` 在 `admin_menu` 时就要解析 renderer）、`Media_Manager::render()`、`includes/views/userfiles-media.php`。`Page::register_renderers()`（`src/UserFiles/Admin/Page.php`）的跳过清单要从 `'zibll'` 扩到 `array( 'zibll', 'media' )`，否则两个控制器会给同一个页签各注册一次。

**页面结构**：左侧账户树（搜索框、`全部账户` + 每个 owner 一行、`加载更多`），右侧文件区（面包屑、文件搜索、列表/卡片切换、刷新、选中后的工具条、文件列表、`加载更多`）。下架用一块自建 `<dialog class="sakura-dialog">`，字段与 10.1 的媒体库弹窗一致（理由、备注、可选的「同时处罚上传者」+ 类型 + 天数），只是这里**知道 owner**，所以结果提示能直接说「已处罚 N 名上传者」。

**三个必须记住的实现约束**（都是实测踩出来的）：

1. **两栏容器用 `height`，不用 `min-height`。** auto 高度的 grid 会随内容长高，左树就跟着整页滚走，用户看到的是「点了没反应」。`height: clamp(440px, 74vh, 860px)` + 两栏各自 `overflow: auto`。
2. **`[hidden]` 必须自己写一条 `display:none`。** WordPress 的 `.button { display: inline-block }` 特异性高于 UA 的 `[hidden]`，于是「加载更多」在没有更多数据时仍然画出来。`.sufm-mm [hidden] { display: none; }` 一行解决。
3. **缩略图不能用附件存下来的 `guid`。** `guid` 是入库那一刻的 URL，换桶、换域名之后它指向旧主机（实验站里存的就是生产域名，于是整页在 console 里刷 CORS 错误）。服务端用 `wp_get_attachment_image_url( $attachment, 'thumbnail' )` 现算（`Controller::thumb_url()`），前端 `file.thumb || file.url`，加载失败退化成扩展名方块。

**REST（都在 `sufm/v1` 命名空间，`Controller` 里）**

| 路由 | 方法 | permission | 返回 |
|---|---|---|---|
| `/admin/media` | GET | `can_use_files`（`review`） | `{owner_id, folder, scope, breadcrumb, folders, files, total, next, reasons}`；参数 `owner_id` / `folder_id` / `type` / `search` / `cursor` / `per_page`（上限 200） |
| `/admin/media/takedown` | POST | `can_takedown()` = `current_user_can('upload_files') && Capabilities::can_execute()` | `{done, partial, skipped, sanctioned, operation_id, denied, owners}`；body 要 `ids[]` / `reason` / `note` / `punish` / `sanction_type` / `sanction_days` |

`/admin/media` 只给 `folder_id` 不给 `owner_id` 时，用 `Folders::owner_of()` 反查；两者不一致返回 404 `sufm_folder_missing`（不然越权读别人的文件夹）。

**服务层是唯一实现：`src/UserFiles/Services/Takedown.php`。** 媒体库的 `Media_Hooks::handle_takedown()`（约 55 行）与这个 REST 端点都只是把各自的请求形状翻译成 `Takedown::run( array $ids, array $args )`。**不要在两个入口各写一份循环**——两份循环的差异不会被任何测试看见，只会在半年后表现为「媒体库下架会通知、新页面下架不通知」。`Takedown` 里集中了三件不能分叉的事：`operation_id` 的生成（`takedown:{YmdHis}-{actor}`）、按 owner 聚合（只有 `Deletion_Result::DELETED` 计入 `$done`，`PARTIAL` 单独计）、以及"先通知、再判决"的顺序。

**`Takedown::normalise()` 是整个处罚入口的唯一夹取点**：`warn` 恒 `days=0`；其余 `max(1, min(30, $days))`；`note` 走 `sanitize_text_field` + `mb_substr(...,0,120)`；非法 `type` 回落 `warn`，非法 `reason` 回落 `other`。理由是 10.1 记的那条：`apply()` 把 `days=0` 解释成永久，而这个值来自请求体。

**树行上的处罚徽标**：`Controller::admin_folders()` 用 `Sanctions::active_map( $ids )` **一次**查完所有 owner，再给每行补 `sanction` 字段；`Files::admin_query()` 同理不按行查。树行顺序固定为「名称 → 文件数 → 徽标」，徽标必须在最后——把计数放在徽标之后会让它读成徽标的一部分（实测渲染出「剩 7 天0」）。

**P1 实测推翻的五处原设计**（都在正文里改了，这里列出来是因为它们最容易被重新犯）：
1. 懒到期不能在 SELECT 之后补 `expire()`——SELECT 已经把过期行过滤掉了，那段永远不执行。必须**先 UPDATE 再 SELECT**。
2. 到期收尾不能只查 `state='active'`——任何一次被拦的上传都会先把行翻成 `expired`，于是那行永远收不到到期通知。水位要挂在 `expired_notified_at`。
3. `warn` 没有窗口，但 `ends_at` 为空同时代表「永久」；`describe()` / `badge()` 必须先按类型分支。
4. 处罚弹窗的期限下拉默认值是服务端 `durations` 的第一项，而阶梯对首次违规建议 `days=0`（warn 语义）——无条件套用建议会让默认值变成「永久」。只有非 warn 才套用建议天数。
5. 下架弹窗的 `days` 从前端可控，而 `apply()` 把 `days=0` 当永久——必须 `max(1, min(30, $days))` 夹住，否则一次批量下架可被手工参数升级成永久封禁。`[已修并有注释]`

**不新增 cron**：复用 `sufm_tick`（`Module.php:39/297-319`、`Deactivation.php:37-38`、`Uninstaller.php:77` 都已经在管它），所以这一轮不需要动停用/卸载的排程清单——但**新增的表必须进 `Schema::tables()`**，卸载自动覆盖。
